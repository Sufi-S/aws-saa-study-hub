VPC Design: Subnets, Route Tables, Internet Gateway & NAT

How architects design reliable AWS network foundations — IP addressing, routing, internet connectivity, and resilient outbound paths.

Learn from Zero

Part 1A — VPC Fundamentals

What is an Amazon VPC? A Virtual Private Cloud (VPC) is your own logically isolated network inside AWS. Think of it as renting an empty building in a data center — you decide the floor plan (IP addresses), which rooms are public-facing (public subnets), which are internal-only (private subnets), and how traffic moves between them (route tables).

Why do AWS applications use VPCs? Every production workload needs network isolation, controlled access, and predictable addressing. A VPC provides all three. Without a VPC, your resources would share a flat network with no boundaries — no control over who can reach what.

VPC CIDR block. When you create a VPC, you assign it an IPv4 CIDR block such as 10.0.0.0/16. This defines the pool of private IP addresses available inside the VPC. The /16 means the first 16 bits are fixed, leaving 65,536 total addresses. This is the maximum a single primary CIDR provides.

Subnets. A subnet is a smaller slice of the VPC CIDR placed in one specific Availability Zone. You divide the VPC range into non-overlapping subnets — for example, 10.0.1.0/24 (256 addresses) in AZ-a and 10.0.2.0/24 in AZ-b. Every EC2 instance, Lambda ENI, or RDS instance lives inside a subnet.

Availability Zones and distribution. An Availability Zone (AZ) is one or more physically separate data centers within a region. Distributing resources across at least two AZs protects against single-AZ failures — if AZ-a goes down, resources in AZ-b keep running. This is the foundation of resilient AWS architecture.

Public vs. private subnet. The words “public” and “private” are not labels you assign. A subnet is effectively public when its route table sends internet-bound traffic (0.0.0.0/0) to an Internet Gateway and the resources in it have public IPv4 addresses (or Elastic IPs). A subnet is private when it has no such route — or its route points to a NAT Gateway instead. Naming a subnet “public” in the console proves nothing about its actual connectivity.

Route tables. A route table is a set of rules (routes) that tells the VPC where to send traffic based on the destination IP. Every subnet is associated with exactly one route table. The route table decides whether traffic goes to the local VPC, the internet, a NAT Gateway, a VPC endpoint, or nowhere at all.

Network interfaces and private IPs. Every instance gets at least one elastic network interface (ENI) with a private IPv4 address drawn from its subnet’s CIDR. This private IP is how resources communicate within the VPC. It never changes for the life of the interface.

Public IPv4 and Elastic IPs. A public IPv4 address maps to the instance’s private IP through the Internet Gateway. It changes if you stop and start the instance. An Elastic IP (EIP) is a static public IPv4 address you allocate and associate explicitly — it persists across stops.

The relationship between routing, addressing, security groups, and NACLs. For internet connectivity to work, all four must cooperate:

  1. Routing — the subnet’s route table must have a path to the destination.
  2. Addressing — the resource must have a suitable IP (public IPv4 for direct internet access).
  3. Security groups — the instance’s stateful firewall must allow the traffic direction and port.
  4. NACLs — the subnet’s stateless firewall must allow both the request and the response.

A missing route means traffic has no path. A missing security-group rule means traffic is dropped at the instance. A missing NACL rule means traffic is dropped at the subnet boundary. These are independent checks — satisfying one does not bypass the others.

Network reachability does not imply permission. Even if all networking layers allow the connection, IAM policies, resource policies, and application-level authentication still control whether the AWS resource accepts the request. A network path is necessary but not sufficient.

Part 1B — CIDR Blocks and Subnet Design

CIDR notation. CIDR (Classless Inter-Domain Routing) describes an IP range as a base address plus a prefix length. 10.0.0.0/16 means “all addresses where the first 16 bits match” — that gives you 10.0.0.0 through 10.0.255.255 (65,536 addresses). 10.0.1.0/24 means the first 24 bits are fixed, giving 256 addresses (10.0.1.0–10.0.1.255).

How prefix length determines range. Shorter prefix = larger range. /16 = 65,536 addresses. /24 = 256 addresses. /28 = 16 addresses. Each additional bit halves the range.

Dividing a VPC CIDR into subnets. You carve the VPC CIDR into smaller, non-overlapping subnet CIDRs. If your VPC is 10.0.0.0/16, you might create 10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24, etc. The ranges must not overlap — AWS rejects a subnet CIDR that overlaps with an existing one.

Planning for growth. Good architects reserve address space for future subnets. If you use only 10.0.1.0/24 through 10.0.4.0/24 today, you still have 10.0.5.0/24 through 10.0.255.0/24 available for expansion. Using a /16 VPC CIDR gives you room; a /24 VPC CIDR does not.

AWS-reserved addresses. AWS reserves 5 IP addresses in every subnet:

AddressReserved for
.0Network address
.1VPC router
.2DNS server
.3Reserved for future use
Last address (.255 for /24)Network broadcast (not supported, but reserved)

A /24 subnet has 256 total addresses minus 5 reserved = 251 usable host addresses. A /28 subnet (16 total) has only 11 usable.

Why capacity matters. Every ENI consumes an IP. ECS tasks, Lambda functions in a VPC, and managed services like RDS all consume IPs. Under-sized subnets can cause launch failures when you run out of addresses.

IPv6 addressing. You can optionally assign a /56 IPv6 CIDR to a VPC (from Amazon’s pool or your own). IPv6 subnets are /64, providing an enormous address space. IPv6 addresses are globally unique — there is no concept of “private” IPv6 NAT in the same way as IPv4. IPv6 connectivity uses an Internet Gateway (for full bidirectional) or an Egress-Only Internet Gateway (for outbound-only). IPv6 NAT and IPv4 NAT are not interchangeable — they serve different protocol stacks and have different design patterns.

Part 1C — Route Tables and Route Selection

What a route table does. A route table is a list of rules evaluated whenever traffic leaves a resource in the subnet. Each rule (route) has a destination (a CIDR range) and a target (where to send matching traffic).

The VPC local route. Every route table automatically includes a local route for the VPC CIDR. For a 10.0.0.0/16 VPC, this route is: destination 10.0.0.0/16, target local. It allows all subnets in the VPC to communicate with each other. You cannot remove this route.

Main vs. custom route tables. Every VPC has a main route table that is the implicit default. Any subnet without an explicit association uses the main route table. Custom route tables are ones you create and explicitly associate with specific subnets. Best practice: leave the main route table restrictive (private) and create custom public route tables only for subnets that need internet access.

Route table association. Each subnet is associated with exactly one route table at a time. If you don’t explicitly associate a custom route table, the subnet uses the main route table. Different subnets can use different route tables — this is how public and private subnets get different routing behavior.

Longest-prefix matching. When multiple routes match a destination, AWS uses the most specific (longest prefix) route. A packet to 10.0.1.5 matches both 10.0.0.0/16 (local) and 10.0.1.0/24 if such a route exists. The /24 wins because it’s more specific. For internet traffic, 0.0.0.0/0 is the least specific route possible — it only matches when nothing more specific applies.

A missing route prevents connectivity. If there is no route matching the destination, the packet is dropped. Security groups and NACLs cannot compensate for a missing route — without a path, there is no traffic to allow or deny.

Worked Example: Route Tables for Public and Private Subnets

Public subnet route table:

The database subnet has only the local route — no internet access at all. It communicates with the application tier through VPC-internal routing. If it needs access to AWS services like S3, a VPC endpoint can be added without adding an internet route.

Part 1D — Internet Gateway (IGW)

What an Internet Gateway is. An IGW is a horizontally scaled, redundant, highly available VPC component that enables communication between your VPC and the internet. It performs network address translation for instances that have public IPv4 addresses.

Attachment model. You attach an IGW to a VPC, not to a subnet or instance. One VPC can have one IGW. The IGW serves the entire VPC, but only subnets with a route pointing to it can use it.

What makes a resource internet-accessible. Four conditions must be met for an EC2 instance to communicate directly with the internet:

  1. An IGW is attached to the VPC.
  2. The subnet’s route table has a route to the IGW (e.g., 0.0.0.0/0 → igw-xxxx).
  3. The instance has a public IPv4 address or Elastic IP (or an appropriate IPv6 address).
  4. Security groups and NACLs permit the traffic.

Removing any one of these breaks the connection. Adding an IGW alone does not make resources internet-accessible — routing, addressing, and security must all cooperate.

Unsolicited inbound vs. response traffic. When a security group allows inbound traffic on port 443, external clients can initiate HTTPS connections. When an instance initiates an outbound connection, the security group automatically allows the response (stateful). NACLs, being stateless, require explicit rules for both directions.

Why private resources should not be directly internet-exposed. A database server has no reason to accept connections from arbitrary internet addresses. Placing it in a private subnet with no IGW route eliminates this attack surface entirely at the network layer.

Worked Example: Public EC2 Web Server

  1. VPC 10.0.0.0/16 with IGW igw-abc123 attached.
  2. Public subnet 10.0.1.0/24 in AZ-a with route table: 0.0.0.0/0 → igw-abc123.
  3. EC2 instance launched with auto-assign public IP enabled → gets private IP 10.0.1.15 and public IP 54.x.x.x.
  4. Security group allows inbound TCP 443 from 0.0.0.0/0.
  5. Default NACL allows all traffic (or custom NACL allows 443 inbound + ephemeral port outbound).

An internet user sends HTTPS to 54.x.x.x:443. The IGW translates the public IP to the private IP, the route table delivers the packet to the subnet, the NACL allows it, and the security group allows it. The response follows the reverse path — the security group is stateful so the response is automatically allowed.

Part 1E — NAT Gateway

What a NAT Gateway is. A NAT (Network Address Translation) Gateway allows instances in private subnets to initiate outbound connections to the internet (or other external destinations) over IPv4, while preventing unsolicited inbound connections from reaching those instances. It translates private source IPs to the NAT Gateway’s own public Elastic IP.

Why private workloads need outbound access. Private EC2 instances often need to download OS patches, pull container images, call external APIs, or reach AWS service endpoints. They need outbound connectivity without being directly reachable from the internet.

How it works — placement and routing.

  1. The NAT Gateway lives in a public subnet (a subnet with a route to the IGW).
  2. The NAT Gateway has an Elastic IP for the standard public NAT pattern.
  3. The private subnet’s route table has 0.0.0.0/0 → nat-xxxx.
  4. When a private instance sends traffic to the internet, the packet goes to the NAT GW, which replaces the source IP with its own EIP, forwards the packet through the IGW, and maps the response back.

NAT Gateway vs. Internet Gateway.

FeatureInternet GatewayNAT Gateway
ScopeVPC-levelAZ-level (per subnet)
EnablesBidirectional internet accessOutbound-initiated only
AddressingInstance needs public IP/EIPNAT GW has EIP; instances stay private
Inbound from internetYes, if security rules allowNo unsolicited inbound
CostFree (data transfer charges apply)Hourly charge + per-GB processing

NAT Gateway vs. NAT instance. A NAT instance is an EC2 instance you manage yourself running NAT software. A NAT Gateway is a managed service — no patching, automatic bandwidth scaling up to 100 Gbps, and built-in redundancy within its AZ. The exam almost always prefers NAT Gateway over NAT instance for production workloads.

Security rules still apply. Even though the NAT Gateway handles address translation, security groups on the private instances and NACLs on both the private and public subnets still control what traffic is allowed.

VPC endpoints as an alternative. For traffic to supported AWS services (S3, DynamoDB, CloudWatch, etc.), a VPC endpoint can route traffic directly without going through the NAT Gateway. This can reduce NAT costs and keep traffic on the AWS network.

Worked Example: Private EC2 Downloads a Software Package

Outbound path:

  1. Private EC2 (10.0.11.20) sends HTTPS request to packages.example.com.
  2. Private route table: 0.0.0.0/0 → nat-gw-a. Packet goes to the NAT Gateway in the public subnet.
  3. NAT Gateway replaces source IP 10.0.11.20 with its EIP 52.x.x.x and forwards via the public subnet’s route: 0.0.0.0/0 → igw-abc123.
  4. Packet exits through the IGW to the internet.

Return path:

  1. Response arrives at the IGW addressed to the NAT Gateway’s EIP.
  2. NAT Gateway maps the response back to 10.0.11.20 and forwards to the private subnet.
  3. The private instance receives the response.

The private instance never had a public IP. The internet only sees the NAT Gateway’s EIP.

Part 1F — NAT Gateway High Availability and Resiliency

A NAT Gateway is an AZ resource. When you create a NAT Gateway, you place it in a specific subnet in a specific AZ. It is redundant within that AZ (AWS manages the underlying instances), but it does not span AZs. If AZ-a becomes unavailable, a NAT Gateway in AZ-a becomes unavailable too.

The single-NAT-Gateway risk. If you route all private subnets (across both AZs) through one NAT Gateway in AZ-a:

  • AZ-a failure takes down the NAT Gateway.
  • Private subnets in AZ-b lose outbound internet connectivity even though AZ-b is healthy.
  • Cross-AZ traffic from AZ-b to the NAT Gateway in AZ-a also incurs data-transfer charges.

The resilient pattern: one NAT Gateway per AZ.

  • Deploy a NAT Gateway in each AZ’s public subnet.
  • Each private subnet’s route table points to the NAT Gateway in its own AZ.
  • If AZ-a fails, AZ-b’s private subnets still reach the internet through AZ-b’s NAT Gateway.
  • No cross-AZ data-transfer charges for NAT traffic.

Cost trade-off. Each NAT Gateway costs ~$0.045/hour (~$32/month). A two-AZ design doubles this to ~$64/month. For development environments, a single NAT Gateway may be acceptable. For production, the per-AZ pattern is the standard recommendation.

There is no automatic failover. If a NAT Gateway in AZ-a goes down and you have a second in AZ-b, the private subnets in AZ-a do not automatically reroute to AZ-b’s NAT Gateway. You would need to manually (or via automation) update AZ-a’s route table to point to AZ-b’s NAT Gateway. This is why the per-AZ design is preferred — it avoids the need for failover entirely.

Failure Scenario: Single NAT Gateway

Setup: One NAT Gateway in AZ-a public subnet. Both AZ-a and AZ-b private subnets route 0.0.0.0/0 → nat-gw-a.

AZ-a goes down:

  1. NAT Gateway in AZ-a becomes unreachable.
  2. Private instances in AZ-a are already affected by the AZ failure.
  3. Private instances in AZ-b are healthy but lose outbound internet — their route still points to the now-unavailable nat-gw-a.
  4. To recover AZ-b connectivity, an operator must update AZ-b’s route table to point to a different NAT Gateway.

With per-AZ NAT Gateways: AZ-b’s private subnets use nat-gw-b in AZ-b. When AZ-a fails, AZ-b connectivity is unaffected. No manual intervention required.

Part 1G — IPv6 and Egress-Only Internet Gateways

IPv4 vs. IPv6 routes. IPv4 uses 0.0.0.0/0 for the default route. IPv6 uses ::/0. They are separate entries in the route table and evaluated independently.

Egress-Only Internet Gateway (EIGW). For IPv6, AWS provides an Egress-Only Internet Gateway. It allows instances to initiate outbound IPv6 connections to the internet but prevents the internet from initiating unsolicited inbound IPv6 connections. It serves a similar purpose to a NAT Gateway for IPv4 outbound — but the mechanism is different because IPv6 addresses are globally routable (no address translation needed).

Why an EIGW is not a NAT Gateway.

FeatureNAT Gateway (IPv4)Egress-Only IGW (IPv6)
ProtocolIPv4 onlyIPv6 only
TranslationYes — rewrites source IPNo — IPv6 addresses are globally unique
Elastic IP requiredYesNo
CostHourly + per-GBNo hourly charge (data transfer charges apply)
Prevents inbound initiationYesYes

When to use which. If your workloads are IPv4 and need outbound internet from private subnets, use a NAT Gateway. If your workloads are IPv6 and need outbound-only internet access, use an Egress-Only Internet Gateway. They are not interchangeable — each handles its protocol stack only.

Part 1H — Putting the Pieces Together

Complete three-tier network design:

Inbound user request path:

  1. Internet user sends HTTPS request.
  2. Request reaches the Internet Gateway.
  3. IGW routes to the public subnet where the ALB lives.
  4. ALB forwards the request to a target in the private application subnet (via VPC-internal routing, the local route).
  5. Application instance queries the private database subnet (again via the local route).
  6. Response flows back: database → app → ALB → IGW → internet user.

Independent outbound path (private instance to internet):

  1. Private app instance (10.0.11.20) needs to reach a public API.
  2. Private route table: 0.0.0.0/0 → nat-gw-a.
  3. NAT Gateway in the public subnet translates source IP to its EIP.
  4. Public subnet route table: 0.0.0.0/0 → igw-abc123.
  5. Packet exits through the IGW to the internet destination.

Route-table comparison:

Subnet tierDestinationTargetWhy
Public10.0.0.0/16localVPC-internal communication
0.0.0.0/0igw-xxxxDirect internet access
Private App10.0.0.0/16localVPC-internal communication
0.0.0.0/0nat-xxxxOutbound internet via NAT
Private DB10.0.0.0/16localVPC-internal only — no internet

VPC endpoints for AWS services. If the application tier frequently accesses S3 or DynamoDB, adding a gateway endpoint (free, no hourly charge) keeps that traffic off the NAT Gateway — reducing cost and latency. For services like Secrets Manager or CloudWatch Logs, an interface endpoint (powered by PrivateLink) provides a similar private path. This was covered in detail in Topic 6 (VPC Endpoints & PrivateLink).

The correct architecture depends on requirements. Not every subnet needs a default internet route, and not every workload needs NAT. Assign routes based on what each tier actually needs to communicate with.

Part 1I — Troubleshooting and Architecture Decisions

When connectivity fails, work through this systematic checklist:

SymptomLikely causeCheck
Public instance unreachable from internetMissing IGW, missing route, no public IP, SG/NACL blockingVerify IGW attached → route table has 0.0.0.0/0 → igw → instance has public IP → SG allows inbound port → NACL allows inbound + ephemeral outbound
Private instance can’t reach internetMissing NAT GW, wrong route, NAT GW in wrong subnetVerify NAT GW exists in a public subnet → private route table has 0.0.0.0/0 → nat → NAT GW’s subnet has route to IGW
Private instance gets timeout to S3No route to S3 (no NAT, no endpoint)Add a VPC gateway endpoint for S3, or ensure NAT path is working
Connectivity works in AZ-a but not AZ-bDifferent route-table associations, NAT GW only in AZ-aCompare route tables for each AZ → verify NAT GW exists per AZ or shared route is correct
Instance reachable but gets 403 / Access DeniedNetwork path works, but IAM or resource policy deniesThis is an authorization failure, not a networking failure — check IAM policies, bucket policies, or resource-based policies
New instances fail to launch in subnetSubnet out of IP addressesCheck subnet’s available IP count — resize or add a new subnet
Traffic to 10.0.x.x works but traffic to 172.16.x.x does notMissing route for the destination CIDRCheck if a route exists for the peered VPC or on-premises CIDR in the route table
DNS resolution failsVPC DNS settings disabledVerify enableDnsSupport and enableDnsHostnames are set to true

Key principle: Diagnose layer by layer. Route first (does a path exist?), then addressing (does the resource have the right IP?), then security (are SGs and NACLs allowing the traffic?), then authorization (does IAM permit the action?). A routing failure looks like a timeout. A security-group block looks like a timeout. An IAM denial returns an explicit error message. The symptom tells you which layer to investigate.

When Real Architects Actually Use This

Scenario A — Public Web Servers and a Private Database

Business requirement: A company runs a public-facing e-commerce site backed by application servers and an RDS PostgreSQL database. The database must not be accessible from the internet.

Architecture:

  • VPC 10.0.0.0/16 with two AZs.
  • Public subnets (10.0.1.0/24, 10.0.2.0/24) host the ALB. Route table: 0.0.0.0/0 → igw.
  • Private app subnets (10.0.11.0/24, 10.0.12.0/24) host EC2 application instances. Route table: 0.0.0.0/0 → nat-gw (for outbound patches).
  • Private DB subnets (10.0.21.0/24, 10.0.22.0/24) host RDS in a Multi-AZ deployment. Route table: only the local route.
  • RDS security group allows inbound PostgreSQL (5432) only from the app-tier security group.

Why not put the database in a public subnet? Even with a restrictive security group, a public subnet with an IGW route gives the database an attack surface it doesn’t need. A private subnet with no internet route eliminates this risk at the network layer.

Exam clue: “Database must not be directly accessible from the internet” → private subnet, no IGW route, security group restricted to the app tier.

Scenario B — Private EC2 Needs Software Updates

Business requirement: EC2 instances in private subnets must download OS patches from public repositories. They must not have public IP addresses.

Architecture:

  • NAT Gateway deployed in the public subnet with an Elastic IP.
  • Private subnet route table: 0.0.0.0/0 → nat-gw.
  • Instance security group allows outbound HTTPS (443) to 0.0.0.0/0 (or a more specific range).
  • The instance initiates the connection — responses flow back through the NAT Gateway.

Alternative for AWS services: If the instance needs to reach S3 (e.g., for yum repos hosted in S3), a gateway endpoint for S3 avoids NAT entirely — free, lower latency, and traffic stays on the AWS network.

Why not assign a public IP? A public IP makes the instance directly reachable from the internet, violating the requirement. The NAT Gateway provides outbound-only connectivity — the instance initiates, but the internet cannot initiate back.

Exam clue: “Private instances need outbound internet, no public IPs” → NAT Gateway in public subnet.

Scenario C — Multi-AZ Production Application

Business requirement: A production application spans two AZs. Private workloads must maintain outbound internet access even if one AZ fails.

Option 1 — Single NAT Gateway (lower cost, lower resilience):

  • One NAT Gateway in AZ-a’s public subnet.
  • Both AZ-a and AZ-b private subnets route through it.
  • Cost: ~$32/month for the gateway.
  • Risk: AZ-a failure kills outbound internet for AZ-b private subnets. Cross-AZ data transfer charges apply.

Option 2 — NAT Gateway per AZ (recommended for production):

  • NAT Gateway in AZ-a’s public subnet + NAT Gateway in AZ-b’s public subnet.
  • AZ-a private subnets route to nat-gw-a. AZ-b private subnets route to nat-gw-b.
  • Cost: ~$64/month for two gateways.
  • Benefit: AZ-independent. No cross-AZ data transfer for NAT. No failover needed.

Exam clue: “Highly available outbound internet from private subnets” → NAT Gateway in each AZ.

Scenario D — Public EC2 Is Not Reachable

Business requirement: An EC2 instance is in a subnet named “public,” but users cannot SSH into it.

Troubleshooting checklist:

  1. IGW attached? Verify the VPC has an IGW and it’s in the attached state.
  2. Route table? Check the subnet’s associated route table for 0.0.0.0/0 → igw-xxxx. If the subnet uses the main route table (which may not have this route), it’s effectively private.
  3. Public IP? Check whether the instance has a public IPv4 address or EIP. Without one, the IGW cannot translate traffic.
  4. Security group? Verify inbound rule allows SSH (TCP 22) from the user’s IP.
  5. NACL? Verify the subnet’s NACL allows inbound TCP 22 and outbound ephemeral ports (1024–65535).
  6. Service listening? Confirm SSHD is running on the instance.

Key lesson: The name “public” is just a label. What makes it public is the route to the IGW, a public IP on the instance, and security rules that permit the traffic.

Exam clue: “Instance in public subnet is unreachable” → check route table, public IP, security group, NACL.

Scenario E — Designing CIDR Ranges for Growth

Business requirement: A company needs a VPC for an application that will grow to include application, database, caching, and shared-service subnets across three AZs.

Architecture:

  • Choose a /16 VPC CIDR (65,536 addresses) to leave room for growth.
  • Assign /24 subnets (251 usable each) for standard tiers.
  • Use a numbering scheme: public = 10.0.1-3, app = 10.0.11-13, DB = 10.0.21-23, cache = 10.0.31-33.
  • Leave 10.0.100.0/22 and above unallocated for future services.
  • Avoid 172.31.0.0/16 (default VPC range) if you might peer VPCs later.

Why overlap matters: VPC peering and Transit Gateway cannot work with overlapping CIDRs. If two VPCs both use 10.0.0.0/16, they cannot peer. Plan unique ranges across your organization.

Exam clue: “Plan for future growth and VPC connectivity” → use a large CIDR, non-overlapping ranges, structured subnet numbering.

Scenario F — Reduce Unnecessary NAT Costs

Business requirement: A company processes large data volumes. Most outbound traffic from private subnets goes to S3 and DynamoDB, costing hundreds of dollars monthly in NAT Gateway data-processing fees.

Architecture:

  • Add a gateway VPC endpoint for S3 — free, no hourly charge, no per-GB processing fee.
  • Add a gateway VPC endpoint for DynamoDB — same benefits.
  • S3 and DynamoDB traffic now routes directly via the endpoint, bypassing NAT entirely.
  • Keep the NAT Gateway for traffic to destinations that don’t have endpoints (external APIs, third-party services).

Limitations: Gateway endpoints only work for S3 and DynamoDB. For other AWS services, interface endpoints (PrivateLink) are available but have their own hourly + per-GB charges — evaluate whether the cost trade-off makes sense for each service.

Exam clue: “Reduce NAT costs for AWS service traffic” → VPC gateway endpoints for S3/DynamoDB.

Scenario G — Secure IPv6 Outbound Connectivity

Business requirement: A company uses dual-stack (IPv4 + IPv6) instances. IPv6-enabled resources need outbound internet access for external API calls, but must not accept unsolicited inbound connections over IPv6.

Architecture:

  • Assign an IPv6 CIDR to the VPC and /64 IPv6 CIDRs to each subnet.
  • Create an Egress-Only Internet Gateway (EIGW).
  • Private subnet IPv6 route: ::/0 → eigw-xxxx.
  • The EIGW allows outbound-initiated IPv6 traffic but blocks unsolicited inbound initiation.

Why not a NAT Gateway? NAT Gateways handle IPv4 address translation. IPv6 addresses are globally unique and don’t need translation. An EIGW provides the outbound-only behavior without the cost and complexity of NAT. They are separate tools for separate protocols.

Exam clue: “IPv6 outbound-only internet access” → Egress-Only Internet Gateway, not a NAT Gateway.

Scenario H — Troubleshooting Multi-AZ Connectivity

Business requirement: An application works perfectly in AZ-a but private instances in AZ-b cannot reach the internet.

Investigation:

  1. Route-table association: AZ-b’s private subnet may be associated with the main route table (which has only the local route) instead of a custom route table with a NAT route.
  2. NAT Gateway placement: There may be no NAT Gateway in AZ-b, and AZ-b’s route table may point to a NAT Gateway in AZ-a that has been deleted or is in a failed state.
  3. Wrong route target: AZ-b’s route table may point to a NAT Gateway ID that doesn’t exist anymore (shows as a “blackhole” route).
  4. NACL difference: AZ-b’s subnet may have a different NACL that blocks the required traffic.

Resolution: Compare route-table associations, route targets, NAT Gateway status, and NACL rules between the two AZs. The most common cause is a missing or incorrect route-table association — the subnet is using the wrong route table.

Exam clue: “Works in one AZ, fails in another” → check route-table associations and NAT Gateway placement per AZ.

Two-AZ VPC Architecture

Inbound: Internet traffic enters through the Internet Gateway, reaches the ALB in public subnets, which forwards to application instances in private subnets. The app tier queries the database tier via VPC-internal routing. Outbound: When private instances need internet access (dashed green lines), traffic routes through the NAT Gateway in the same AZ, then through the IGW. Each AZ has its own NAT Gateway for independent resilience. The database tier has no internet route — it communicates only within the VPC.

22 Exam Gotchas

  1. A subnet named “public” is not automatically public — what makes a subnet public is a route to an Internet Gateway in its associated route table, not its name. The exam will test whether you know the difference.
  2. Attaching an IGW does not make every resource internet-accessible — the IGW must be attached, the subnet needs a route to it, the instance needs a public IPv4 address, and security groups/NACLs must allow the traffic. All four conditions are required.
  3. A public IPv4 address or EIP is required for direct internet access — a resource in a public subnet with a route to the IGW still cannot communicate with the internet if it has no public IP. The IGW needs a public IP to perform NAT translation.
  4. An IGW is not a NAT Gateway — the IGW enables bidirectional internet access for resources with public IPs. A NAT Gateway enables outbound-only internet access for private instances. They are different components with different purposes.
  5. A NAT Gateway does not provide unsolicited inbound access — if the exam says “users must access an EC2 instance from the internet,” a NAT Gateway is the wrong answer. You need a public subnet with IGW access or a load balancer.
  6. A standard public NAT Gateway belongs in a public subnet — it needs a route to the IGW and an Elastic IP. Placing it in a private subnet breaks the outbound path because the NAT Gateway itself cannot reach the internet.
  7. Private instances do not need public IPs to use NAT — the NAT Gateway has the EIP, not the instance. The instance stays fully private. If the exam suggests assigning public IPs to private instances to enable outbound access, that contradicts the purpose of NAT.
  8. The private subnet’s default route goes to NAT, not to the IGW — 0.0.0.0/0 → nat-gw in a private subnet. 0.0.0.0/0 → igw in a public subnet. Swapping these is a common exam trap.
  9. Route-table associations determine routing, not subnet names — if a subnet has no explicit custom route-table association, it uses the main route table. A subnet you intended to be public may behave as private if it inherited the main route table without an IGW route.
  10. Longest-prefix matching selects routes — a packet destined for 10.0.1.5 matches 10.0.0.0/16 (local) and 10.0.1.0/24 (more specific). The /24 wins. For internet traffic, 0.0.0.0/0 is the least specific route and only matches when nothing else does.
  11. Security groups cannot compensate for a missing route — if no route exists for the destination, the packet is dropped before any security-group evaluation. A permissive security group with no route is useless.
  12. Routing does not override security rules — a route to the IGW creates a path, but security groups and NACLs still control whether traffic is permitted. Having a route and having permission are independent checks.
  13. One NAT Gateway does not provide AZ-independent redundancy — a NAT Gateway is an AZ-scoped resource. If that AZ fails, all subnets routing through it lose outbound internet — including subnets in healthy AZs.
  14. NAT Gateway failover is not automatic — AWS does not redirect private-subnet routes to a different NAT Gateway if one becomes unavailable. You must update route tables manually or via automation. The per-AZ design avoids the need for failover entirely.
  15. Cross-AZ NAT traffic incurs extra cost — routing AZ-b’s private subnets through a NAT Gateway in AZ-a adds cross-AZ data-transfer charges on top of NAT processing fees. The per-AZ pattern eliminates this.
  16. An Egress-Only IGW is not an IPv4 NAT Gateway — the Egress-Only IGW handles IPv6 outbound-only traffic. It does not perform address translation (IPv6 addresses are globally unique). It cannot replace a NAT Gateway for IPv4 traffic.
  17. IPv6 outbound design should not default to IPv4 NAT — if the exam specifies IPv6 outbound-only internet access, the answer is an Egress-Only Internet Gateway, not a NAT Gateway.
  18. Overlapping CIDRs prevent VPC peering and Transit Gateway connections — plan unique, non-overlapping CIDR ranges across all VPCs that might need to communicate. The 172.31.0.0/16 default VPC range is commonly duplicated and causes peering conflicts.
  19. AWS reserves 5 addresses per subnet — .0 (network), .1 (router), .2 (DNS), .3 (reserved), and last address (broadcast). A /24 has 251 usable IPs, not 256. A /28 has 11, not 16.
  20. Not every destination requires NAT — traffic to supported AWS services (S3, DynamoDB) can use a free VPC gateway endpoint, bypassing NAT entirely. The exam frequently tests this as a cost-optimization answer.
  21. A private database subnet does not need a default internet route — databases communicate with the application tier via VPC-internal routing (the local route). Adding 0.0.0.0/0 to a database subnet introduces unnecessary attack surface.
  22. A missing route produces a timeout, not an access-denied error — if traffic times out, check routes first. If traffic returns a 403 or Access Denied, the network path works but IAM or resource policies are blocking. The error type tells you which layer to investigate.

Quick-Fire Practice

Q1. A company runs EC2 instances in private subnets that need to download software updates from public internet repositories. The instances must not have public IP addresses. The VPC has an Internet Gateway attached. What additional configuration is required?

  • A. Enable auto-assign public IP on the private subnets so the instances can reach the internet through the IGW.
  • B. Create a NAT Gateway in a private subnet and update the private route table to route 0.0.0.0/0 to the NAT Gateway.
  • C. Create a NAT Gateway in a public subnet with an Elastic IP. Update the private subnet route table to route 0.0.0.0/0 to the NAT Gateway.
  • D. Add a route for 0.0.0.0/0 pointing to the Internet Gateway in the private subnet route table.

Correct Answer: C

A NAT Gateway must be placed in a public subnet (one with a route to the IGW) and needs an Elastic IP for the standard public NAT pattern. The private subnet’s route table then sends 0.0.0.0/0 to the NAT Gateway. A is wrong because assigning public IPs violates the requirement. B is wrong because a NAT Gateway in a private subnet cannot reach the internet. D is wrong because routing private instances directly to the IGW requires public IP addresses, which the instances don’t have.

Memory rule: NAT Gateway lives in public, serves private. Private route points to NAT, not to IGW.

Q2. A production application runs in private subnets across two Availability Zones. A single NAT Gateway in AZ-a provides outbound internet access for both AZs. The operations team is concerned about resilience. What change provides the MOST highly available outbound internet design?

  • A. Deploy a NAT Gateway in each AZ. Update each AZ’s private route table to use the NAT Gateway in its own AZ.
  • B. Add a second route in AZ-b’s route table pointing to the NAT Gateway in AZ-a as a backup path.
  • C. Replace the NAT Gateway with a NAT instance in an Auto Scaling group spanning both AZs.
  • D. Configure an AWS Lambda function to update route tables automatically when the NAT Gateway health check fails.

Correct Answer: A

Deploying a NAT Gateway in each AZ and routing each AZ’s private subnets to its own NAT Gateway provides AZ-independent resilience. If AZ-a fails, AZ-b’s connectivity is unaffected. B doesn’t help because a route table can only have one route per destination — you can’t add a backup 0.0.0.0/0 route. C introduces operational complexity; NAT instances require patching and don’t scale as well as managed NAT Gateways. D adds custom automation that still depends on detecting the failure first, introducing delay and complexity.

Memory rule: One NAT Gateway per AZ = AZ-independent. One shared NAT Gateway = single point of failure.

Q3. An EC2 instance in a subnet named “public-web” cannot be reached from the internet over HTTPS. The instance has a security group allowing inbound TCP 443 from 0.0.0.0/0. The VPC has an Internet Gateway attached. What should the solutions architect check FIRST?

  • A. Whether the instance’s security group allows outbound traffic on ephemeral ports.
  • B. Whether the subnet’s route table has a route to the Internet Gateway and whether the instance has a public IPv4 address.
  • C. Whether AWS Shield Standard is enabled for the VPC to allow inbound HTTPS traffic.
  • D. Whether the VPC’s DNS hostnames setting is enabled so the instance can receive external connections.

Correct Answer: B

A subnet name is just a label. For an instance to be reachable from the internet, the subnet’s route table must have 0.0.0.0/0 → igw and the instance must have a public IPv4 address or Elastic IP. These are the most common missing pieces when a “public” instance isn’t reachable. A is wrong because security groups are stateful — response traffic is automatically allowed. C is wrong because Shield Standard is always enabled automatically and does not control HTTPS access. D is wrong because DNS hostnames are unrelated to network reachability.

Memory rule: “Public subnet” = name only. Check route table + public IP first.

Multi-AZ vs Multi-Region: High Availability & Disaster Recovery

How architects design for AZ-level resilience, Regional disaster recovery, and everything in between.

Learn from Zero

Part 1A — What Is Resilience?

Resilience is the ability of a system to continue providing its intended function even when components fail. In cloud architecture, failure is not a question of “if” but “when” — hardware degrades, networks experience issues, entire data centers can be disrupted. A resilient system is designed so that these failures do not take down the application.

Why systems fail even when code is correct. Your application code might be perfect, but it runs on servers, disks, network links, and power supplies that can fail independently. A database server might restart, a network switch might drop packets, or an entire facility might lose power. Resilience means your architecture handles these events gracefully.

Key resilience concepts:

ConceptDefinitionExample
AvailabilityThe percentage of time a system is operational and accessible99.99% availability = ~4.3 minutes of downtime per month
ReliabilityThe ability to perform the intended function correctly and consistentlyA payment system that processes every transaction without errors
DurabilityThe likelihood that stored data will not be lostS3 provides 99.999999999% (11 nines) durability
Fault toleranceThe ability to continue operating despite specific component failuresAn application that keeps serving requests when one server crashes
Disaster recoveryThe process of restoring a system after a major disruptionRebuilding an application in another Region after a Regional outage

Redundancy is necessary but not sufficient. Simply copying a server does not guarantee resilience. You also need health checks (to detect failures), load balancing (to route away from failed resources), data replication (so the replacement has current data), and tested recovery procedures (so the team knows what to do).

Small failure vs. major disruption. Keeping an application running when a single EC2 instance crashes (high availability) is fundamentally different from restoring service after an entire AWS Region becomes unavailable (disaster recovery). Both require planning, but at different scales and costs.

Example: Online Shopping Application

Small failure: One of three web servers crashes. The load balancer detects the failure via health checks and routes traffic to the remaining two servers. Users never notice. This is high availability.

Major disruption: The primary Region experiences a widespread outage. The team activates their disaster recovery plan, promoting a database replica in another Region and redirecting DNS. Service is restored within the targeted recovery time. This is disaster recovery.

Part 1B — Availability, RTO, and RPO

High Availability (HA) means designing a system so that it continues operating when individual components fail. Key ingredients:

  • Redundant resources across multiple Availability Zones eliminate single points of failure.
  • Health checks detect unhealthy instances automatically.
  • Load balancing distributes requests only to healthy targets.
  • Data availability — the database must also be resilient, not just the application servers.

HA depends on the entire stack — servers, data, networking, and health detection — not just server count.

Fault Tolerance goes further: the system continues operating with zero interruption despite a failure. True fault tolerance often requires more redundancy and automation than a standard HA design — for example, synchronous data replication so no transactions are lost, and instant failover with no observable downtime.

Recovery Time Objective (RTO) is the maximum acceptable time to restore service after an interruption. RTO = 10 minutes means the business requires the application to be operational within 10 minutes of an outage. Lower RTO demands faster detection, more prepared standby environments, and greater operational readiness.

Recovery Point Objective (RPO) is the maximum acceptable amount of recent data loss, measured in time. RPO = 1 minute means you can lose at most 1 minute of committed data. Lower RPO demands more frequent replication or continuous synchronous replication.

Concrete Examples

ApplicationRTORPOWhat this means
E-commerce website10 minutes1 minuteMust recover fast; can lose at most 1 minute of orders. Needs warm standby + near-real-time replication.
Internal reporting tool24 hours12 hoursCan tolerate a day of downtime and half a day of data loss. Backup and restore is likely sufficient.

These are business requirements, not AWS guarantees. The architecture must be designed, implemented, and tested to meet them.

Remember: RTO measures recovery time (how fast you’re back). RPO measures data loss (how much you lose). They are independent — you can have a short RTO with a long RPO, or vice versa.

Part 1C — Availability Zones vs AWS Regions

Availability Zones (AZs) are one or more discrete data centers with independent power, cooling, and networking within a Region. They are connected to each other through low-latency links but are physically separated to reduce correlated failures. Deploying across AZs protects against single-AZ disruptions like power outages or network failures in one facility.

AWS Regions are separate geographic locations, each with multiple AZs. Regions are fully independent infrastructure — a disruption in us-east-1 does not affect eu-west-1. Multi-Region architecture protects against the rare scenario of a complete Regional outage and can serve users closer to their geographic location.

Multi-AZ and multi-Region solve different problems and can be combined. A production application might use multi-AZ for daily HA and multi-Region for catastrophic DR.

Part 1D — Single-AZ, Multi-AZ, and Multi-Region Architectures

Single-AZ

  • All resources in one AZ. Simplest and cheapest.
  • Acceptable for development, testing, or low-criticality workloads.
  • An AZ disruption can affect every resource in that deployment.
  • No AZ-level redundancy by design.

Multi-AZ

  • Application, data, and networking resources distributed across 2+ AZs in one Region.
  • Load balancers route traffic to healthy targets; health checks detect failures.
  • Database tier uses Multi-AZ replication (e.g., RDS Multi-AZ) or distributed storage (Aurora).
  • Can survive most AZ-level failures without manual intervention.
  • Does not protect against a complete Regional outage.

Multi-Region

  • Application environments in 2+ AWS Regions.
  • Data must be replicated, backed up, or otherwise recoverable across Regions.
  • Failover may require DNS changes (Route 53), traffic shifting (Global Accelerator), or manual procedures.
  • Supports Regional DR, data residency requirements, and global latency optimization.
  • Significantly higher cost and operational complexity.

Multi-Region is not automatically better. Choose based on business requirements: What is the RTO? What is the RPO? What are the compliance constraints? What can the budget support? A well-designed multi-AZ architecture covers the vast majority of production workloads.

Part 1E — Disaster Recovery Strategies

AWS teaches four DR strategies, ordered from lower to higher preparedness and cost:

1. Backup and Restore

  • Before disaster: Data is backed up to another Region (S3 cross-Region replication, RDS snapshots, AWS Backup). Infrastructure is defined as code (CloudFormation) but not deployed.
  • During recovery: Deploy infrastructure from templates, restore data from backups, configure networking, start application.
  • RTO: Hours (provisioning + restoration time).
  • RPO: Depends on backup frequency — minutes to hours.
  • Cost: Lowest — you pay only for backup storage until a disaster occurs.
  • Best for: Non-critical workloads where hours of downtime are acceptable.

2. Pilot Light

  • Before disaster: Core data infrastructure (database replicas, data stores) runs continuously in the DR Region. Application servers and other non-core resources are not deployed (or are stopped).
  • During recovery: Provision/start application servers, scale up, switch traffic.
  • RTO: Tens of minutes (provisioning app servers takes time).
  • RPO: Near-zero if using continuous replication; depends on replication lag.
  • Cost: Low to moderate — data tier is always running, but compute is off.
  • Best for: Workloads needing faster recovery than backup/restore but not immediate.

3. Warm Standby

  • Before disaster: A scaled-down but fully functional copy of the production environment runs in the DR Region. All tiers are live — just at reduced capacity.
  • During recovery: Scale up to production capacity and switch traffic.
  • RTO: Minutes (scaling up, not provisioning from scratch).
  • RPO: Near-zero with continuous replication.
  • Cost: Moderate to high — a smaller version of production is always running.
  • Best for: Business-critical workloads needing fast recovery.

4. Multi-Site Active/Active

  • Before disaster: Full production environments run in multiple Regions simultaneously, serving traffic concurrently.
  • During recovery: Traffic is already distributed. A failing Region is removed from rotation. Remaining Regions absorb the load.
  • RTO: Near-zero for infrastructure failures (traffic shifts automatically).
  • RPO: Near-zero with synchronous or near-synchronous replication (but data corruption still requires backups).
  • Cost: Highest — full production infrastructure in multiple Regions.
  • Best for: Mission-critical global applications with near-zero downtime tolerance.

Part 1F — Active/Passive vs Active/Active

Active/Passive

  • One environment (primary) serves all production traffic.
  • A second environment (standby) is ready for recovery — ranging from backups to a warm standby.
  • Failover involves redirecting traffic to the standby and ensuring it is ready.
  • Simpler to reason about data ownership — writes happen in one place.
  • Requires a tested failover process; the standby is useless if recovery has never been practiced.

Active/Active

  • Multiple environments serve production traffic simultaneously.
  • Better utilization and potentially lower latency for geographically distributed users.
  • Introduces challenges: data consistency, conflicting writes, session management, eventual consistency.
  • Write strategies: write global (all writes to one Region), write local (writes to nearest Region with conflict resolution), or write partitioned (writes routed by partition key).
  • Not inherently better — the added complexity must be justified by the business requirement.
PatternMulti-AZ exampleMulti-Region example
Active/PassiveRDS Multi-AZ: primary in AZ-a, standby in AZ-b, automatic failoverPrimary Region serves traffic; DR Region has warm standby, failover via Route 53
Active/ActiveALB distributes traffic to targets in both AZs simultaneouslyBoth Regions serve users; DynamoDB global tables or Aurora global database for data

When to choose active/passive: The application has a single authoritative data source, the team wants simpler operations, or the DR Region is purely for recovery. When to choose active/active: The business needs global low latency, the data model supports multi-Region writes, and the team can handle the operational complexity.

Part 1G — Data Replication and Consistency

Failover is only useful when the data and dependencies are ready at the recovery site. Infrastructure without data is an empty shell.

Synchronous vs. asynchronous replication:

TypeHow it worksData loss riskLatency impact
SynchronousWrite is acknowledged only after both primary and replica confirmNear-zero (both copies are identical)Higher — write waits for both confirmations
AsynchronousWrite is acknowledged after primary confirms; replica updated laterPossible — replica may lag behind primaryLower — write returns quickly

Replication lag. With asynchronous replication, the replica is always some amount of time behind the primary. If the primary fails and you promote the replica, any transactions committed on the primary but not yet replicated are lost. This gap is the practical RPO.

Backups vs. replicas. A replica mirrors the primary, including unwanted changes (accidental deletes, data corruption). A point-in-time backup lets you restore to a moment before the corruption. Both are needed — replicas for fast failover, backups for data recovery.

Beyond the database. Application state, user sessions, uploaded files, configuration, secrets, message queues, and caches all need replication or recovery strategies. Failing over the database alone may leave the application broken if other dependencies are missing.

Cross-Region replication is not instant readiness. Having a database replica in another Region does not mean the entire application stack is ready to serve traffic. Application servers, networking, secrets, permissions, service quotas, and DNS must all be prepared.

Note: Detailed RDS Multi-AZ and read-replica behavior will be covered in Topic 11.

Part 1H — Traffic Management and Failover

Resilience requires directing users to healthy resources. This happens at multiple levels:

Within a Region — load balancing and health checks:

  • An ALB or NLB distributes traffic across targets in multiple AZs.
  • Health checks detect unhealthy targets and stop sending traffic to them.
  • Auto Scaling replaces failed instances automatically.

Across Regions — DNS and global routing:

  • Route 53 failover routing: Health checks monitor the primary Region endpoint. If it becomes unhealthy, Route 53 returns the DR Region’s endpoint instead.
  • AWS Global Accelerator: Uses anycast IPs to route traffic to the nearest healthy endpoint, including cross-Region failover.
  • CloudFront origin failover: If the primary origin returns errors, CloudFront tries a secondary origin on a per-request basis.

DNS caching and TTL. When Route 53 switches a DNS record, clients using cached DNS responses continue reaching the old endpoint until the TTL expires. Lower TTLs enable faster failover but increase DNS query volume. DNS failover is not instantaneous for all clients.

Failover is more than DNS. Switching traffic to a second Region only works if that Region is ready:

  • Database promoted and accepting writes.
  • Application servers running and configured.
  • Secrets, certificates, and IAM roles in place.
  • Network paths (VPC, subnets, security groups) configured.
  • Service quotas sufficient for production load.
  • Downstream dependencies (APIs, queues, caches) available.

Example: Two-Region Failover

Normal operation: Route 53 points app.example.com to the ALB in us-east-1 (primary). Health checks monitor the primary endpoint every 30 seconds.

Primary fails: Health checks detect failure. Route 53 returns the us-west-2 (DR) ALB IP. Clients with expired DNS cache connect to us-west-2. The DR environment’s database replica is promoted to primary. Application servers in us-west-2 begin handling requests.

Reality check: Clients with cached DNS may take minutes to switch. Database promotion takes seconds to minutes depending on the engine. Application startup, secret loading, and dependency verification add time. The actual RTO is the sum of all these steps.

When Real Architects Actually Use This

Scenario A — Web Application Must Survive an AZ Failure

Business requirement: An e-commerce application must remain available if one AZ experiences a disruption.

Architecture:

  • EC2 instances across at least two AZs behind an Application Load Balancer with health checks.
  • Auto Scaling Group spans both AZs — replaces failed instances automatically.
  • RDS Multi-AZ provides a synchronous standby with automatic failover (60–120 seconds).
  • ElastiCache Multi-AZ (Redis) for session storage so sessions survive an AZ failure.

Why not two instances in the same AZ? If the AZ itself is disrupted, both go down. Multi-AZ distributes across independent failure domains.

Exam clue: “Remain available during an AZ failure” → resources in multiple AZs + load balancer + Multi-AZ database.

Scenario B — Regional Disaster Recovery

Business requirement: Production runs in us-east-1. If the Region becomes unavailable, recover in us-west-2 within 30 minutes (RTO) with at most 5 minutes of data loss (RPO).

Architecture:

  • Strategy: Warm standby. Scaled-down but fully functional environment in us-west-2.
  • Aurora global database replicates with typical lag under 1 second.
  • Application servers at reduced capacity in us-west-2.
  • Route 53 failover routing with health checks on the primary endpoint.
  • On failover: promote Aurora secondary (<1 min), scale ASG, Route 53 shifts traffic.

Why not pilot light? Pilot light requires provisioning app servers during recovery, adding time. Warm standby is faster for the 30-minute target.

Exam clue: “RTO 30 min, RPO 5 min, Regional DR” → warm standby + continuous replication.

Scenario C — Minimize Recovery Time

Business requirement: A financial application has near-zero RTO. Any downtime causes regulatory failures.

Architecture:

  • Strategy: Multi-site active/active. Both Regions serve traffic simultaneously.
  • Route 53 latency-based routing or Global Accelerator distributes traffic.
  • DynamoDB global tables for multi-Region read/write.
  • If one Region fails, the other absorbs all traffic — no failover delay.

Trade-off: Highest cost, most complex data model, requires write-conflict handling.

Exam clue: “Near-zero RTO, cannot tolerate any downtime” → multi-site active/active.

Scenario D — Minimize Disaster Recovery Cost

Business requirement: An analytics platform can tolerate 8 hours of downtime (RTO) and 4 hours of data loss (RPO). Cheapest DR approach needed.

Architecture:

  • Strategy: Backup and restore.
  • RDS snapshots every 4 hours, copied to DR Region via AWS Backup.
  • S3 cross-Region replication for data files.
  • CloudFormation templates ready in DR Region.
  • On disaster: deploy stack, restore RDS, update DNS.

Critical: Test the restore procedure regularly. An untested backup is not a recovery plan.

Exam clue: “Lowest cost DR, hours of downtime acceptable” → backup and restore.

Scenario E — Global Low-Latency Application

Business requirement: Users across three continents need sub-100ms responses. The app must survive a Regional failure.

Architecture:

  • Multi-Region active/active in us-east-1, eu-west-1, ap-northeast-1.
  • Route 53 latency-based routing sends users to the nearest Region.
  • DynamoDB global tables replicate across all three Regions.
  • CloudFront for static content caching at edge locations.

Data consistency: DynamoDB global tables use eventual consistency across Regions. The application must tolerate brief inconsistency windows.

Exam clue: “Global users, low latency, multi-Region” → active/active with latency-based routing.

Scenario F — Application Database Has Replication Lag

Business requirement: After failing over to a cross-Region replica, users report missing recent orders.

Root cause: The cross-Region read replica uses asynchronous replication. At failover, the replica was 45 seconds behind. Those 45 seconds of transactions were lost.

Lessons:

  • Asynchronous replication always has a lag window. RPO = replication lag at time of failure.
  • Monitor ReplicaLag in CloudWatch continuously.
  • Aurora global database typically replicates under 1 second.
  • Point-in-time backups protect against data corruption that replication would propagate.

Exam clue: “Recent data missing after failover” → asynchronous replication lag.

Scenario G — Active/Active Design With Conflicting Writes

Business requirement: Both us-east-1 and eu-west-1 must accept user profile updates simultaneously.

Options:

  • DynamoDB global tables: Last-writer-wins. Simple but may silently discard a concurrent update.
  • Aurora global database (write global): All writes to one Region. No conflicts but adds write latency for remote users.
  • Write partitioned: Each user writes to their “home” Region. Eliminates same-record conflicts but requires routing logic.

Key lesson: Multi-Region infrastructure does not solve data consistency. The data model and conflict resolution strategy must be designed explicitly.

Exam clue: “Active/active writes” → address conflict resolution strategy.

Scenario H — Failover Does Not Restore the Application

Business requirement: DNS failover to DR Region succeeds, but the application returns errors.

Root causes found:

  • Database replica not promoted — app could not write.
  • Secrets not replicated to DR Region — app could not authenticate.
  • IAM roles had stale policies.
  • Service quotas at default limits — ASG could not scale.
  • External API had only primary Region IP whitelisted.

Key lesson: DNS failover is just traffic redirection. The entire stack — database, secrets, permissions, quotas, networking, external dependencies — must be ready and tested.

Exam clue: “Failover succeeds but app still fails” → check all dependencies, not just DNS.

Multi-AZ vs Multi-Region Architecture

Left: A multi-AZ architecture distributes resources across AZs within one Region for high availability. The load balancer, application, database, and cache all span AZs with automatic failover. This handles most production failures but does not protect against a complete Regional outage. Right: A multi-Region architecture adds a recovery Region with replicated data and a standby (or active) environment. Route 53 failover or Global Accelerator shifts traffic during a Regional disaster. Actual recovery time depends on the DR strategy chosen, data replication lag, and full-stack readiness. Bottom: The four DR strategies form a spectrum — greater readiness and lower RTO/RPO come with increased cost and complexity.

20 Exam Gotchas

  1. An AZ failure is not a Regional failure — an AZ disruption affects one data center cluster. A Regional failure affects all AZs in that Region. Multi-AZ protects against the first; multi-Region protects against the second. The exam tests whether you know which scope the scenario describes.
  2. Multi-AZ alone does not protect against a complete Regional outage — if all AZs in a Region are disrupted, multi-AZ resources in that Region are all affected. Regional disaster recovery requires infrastructure in a second Region.
  3. Multi-Region does not automatically mean zero downtime — a second Region must be ready: data replicated, app servers running, secrets and permissions in place, DNS switched. The actual RTO depends on the DR strategy and implementation, not just having a second Region.
  4. RTO and RPO are different measurements — RTO is how fast you recover (time to restore service). RPO is how much data you can lose (time since last good data point). Confusing them changes the correct architecture. The exam uses specific RTO/RPO numbers to guide the answer.
  5. A backup is not a replica — backups are point-in-time snapshots used to restore to a specific moment. Replicas continuously mirror the primary (including unwanted changes). Backups protect against data corruption; replicas provide fast failover. Both are needed.
  6. Pilot light is not warm standby — pilot light keeps only the data tier running; application servers are off and must be provisioned during recovery. Warm standby keeps all tiers running at reduced capacity. Warm standby recovers faster but costs more.
  7. Warm standby is not active/active — warm standby is a scaled-down passive environment that does not serve production traffic. Active/active serves traffic from multiple Regions simultaneously. The exam may describe warm standby as “reduced capacity in standby Region.”
  8. Active/active does not eliminate data consistency challenges — concurrent writes from multiple Regions require conflict resolution (last-writer-wins, write-global, write-partitioned). Active/active infrastructure without a data consistency strategy leads to data conflicts.
  9. Asynchronous replication means potential data loss — if the primary fails before a replica catches up, transactions committed during the lag window are lost. RPO for async replication = the replication lag at the moment of failure, not zero.
  10. Application servers in separate AZs do not guarantee resilience — if the database is in a single AZ, or session state is lost, or health checks are missing, distributing servers across AZs only partially addresses availability. The entire stack must be resilient.
  11. Stateful dependencies must be handled during failover — user sessions, caches, uploaded files, message queues, and configuration all need replication or recovery strategies. Failing over compute without state leaves users with errors.
  12. DNS failover is not instant for every client — clients cache DNS responses based on TTL. After Route 53 changes a record, clients with cached responses continue using the old IP until TTL expires. Lower TTL enables faster switching but increases query volume.
  13. Health checks do not prove the entire application is ready — a health check may confirm that a load balancer responds on port 443. It does not verify that the database is promoted, secrets are loaded, downstream APIs are reachable, or service quotas allow scaling.
  14. A multi-Region app does not automatically replicate every resource — databases may be replicated, but secrets, IAM policies, VPC configurations, service quotas, certificate deployments, and external API whitelists are often separate. DR planning must cover all dependencies.
  15. Secrets, permissions, quotas, and networking must be pre-staged — the DR Region needs Secrets Manager entries, IAM roles, VPC/subnet configuration, security groups, and sufficient service quotas before a disaster occurs. Provisioning these during a crisis adds to RTO.
  16. The lowest-cost DR strategy cannot satisfy the strictest RTO/RPO — backup and restore is cheapest but has hours of RTO. If the business requires minutes of RTO, warm standby or active/active is needed. The exam maps RTO/RPO requirements to the appropriate strategy.
  17. A secondary Region is useless without tested recovery procedures — infrastructure that has never been tested for DR may have configuration drift, stale credentials, or missing dependencies. Regular DR drills are essential. The exam values “tested recovery.”
  18. High availability, fault tolerance, and disaster recovery are different — HA keeps the system running during small failures (multi-AZ). Fault tolerance continues without interruption despite a failure (zero-downtime design). DR restores service after a major disruption. The exam uses precise language to distinguish them.
  19. Route 53 alone is not a complete DR solution — Route 53 failover routing redirects DNS traffic. It does not provision infrastructure, promote databases, replicate secrets, or verify application readiness. It is one component of a DR plan, not the entire plan.
  20. More copies of infrastructure do not always mean better resilience — deploying in 5 Regions does not help if data replication, failover automation, and recovery testing are not in place. Resilience comes from design, not just duplication.

Quick-Fire Practice

Q1. A company runs a web application on EC2 instances behind an Application Load Balancer. The application must remain available if one Availability Zone experiences a disruption. The database is Amazon RDS MySQL in a single AZ. Which change provides the MOST resilient architecture?

  • A. Add more EC2 instances in the same AZ and increase the instance size for higher throughput.
  • B. Deploy EC2 instances across two AZs, configure the ALB to span both AZs, and enable RDS Multi-AZ for the database.
  • C. Create a cross-Region read replica of the RDS database and configure Route 53 failover routing.
  • D. Move all resources to a larger instance type in a single AZ and enable enhanced monitoring.

Correct Answer: B

Multi-AZ deployment distributes application instances and provides automatic database failover. The ALB routes traffic to healthy targets across AZs, and RDS Multi-AZ maintains a synchronous standby that promotes automatically during an AZ disruption. A adds capacity but not AZ resilience. C addresses Regional DR (overkill for AZ-level HA) and does not fix the single-AZ application tier. D increases capacity but remains a single point of failure.

Memory rule: “Survive AZ failure” = multi-AZ deployment for both compute and database.

Q2. A company requires a disaster recovery solution for a critical application. The business defines an RTO of 30 minutes and an RPO of 5 minutes. The recovery site must be in a different AWS Region. Which disaster recovery strategy BEST meets these requirements at the lowest cost?

  • A. Backup and restore: copy daily RDS snapshots to the DR Region and redeploy infrastructure from CloudFormation during a disaster.
  • B. Pilot light: continuously replicate the database to the DR Region, but keep application servers off until needed.
  • C. Warm standby: run a scaled-down but fully functional environment in the DR Region with continuous database replication.
  • D. Multi-site active/active: run full production environments in both Regions with DynamoDB global tables.

Correct Answer: C

With an RTO of 30 minutes and RPO of 5 minutes, backup and restore (A) is too slow — daily snapshots give RPO of up to 24 hours, and restoring infrastructure takes hours. Pilot light (B) could meet the RPO with continuous replication but provisioning application servers from scratch may push past 30 minutes for complex applications. Warm standby (C) meets both targets: continuous replication achieves near-zero RPO, and all tiers are already running so scaling up takes minutes. Active/active (D) meets the targets but is far more expensive than necessary.

Memory rule: Match the DR strategy to the RTO/RPO. Warm standby = minutes RTO, near-zero RPO. Don’t over-spend on active/active when warm standby suffices.

Q3. A company uses an Aurora global database with a primary cluster in us-east-1 and a secondary cluster in eu-west-1. During a Regional failover drill, the secondary cluster is promoted successfully and Route 53 redirects traffic. However, the application in eu-west-1 returns authentication errors. What is the MOST likely cause?

  • A. Route 53 failover routing does not work with Aurora global database endpoints.
  • B. Aurora global database does not support cross-Region failover and the secondary cluster cannot accept writes.
  • C. The application’s database connection strings are hardcoded to the us-east-1 endpoint and cannot reach the promoted cluster.
  • D. The application depends on secrets stored in AWS Secrets Manager in us-east-1 that were not replicated to eu-west-1.

Correct Answer: D

Aurora global database fully supports cross-Region promotion (B is wrong). Route 53 works with any endpoint (A is wrong). If the application successfully reaches the DR Region and the database is promoted, authentication errors point to missing credentials. Secrets Manager secrets are Regional — if database passwords, API keys, or certificates were not replicated to eu-west-1, the application cannot authenticate. C is plausible but the scenario states DNS was redirected successfully, implying the application is reaching the correct Region. The authentication error specifically points to missing secrets.

Memory rule: DR is more than database + DNS. Secrets, IAM, quotas, and external dependencies must all be pre-staged in the recovery Region.
