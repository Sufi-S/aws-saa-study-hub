VPC Design: Subnets, Route Tables, Internet Gateway & NAT

How architects design reliable AWS network foundations — IP addressing, routing, internet connectivity, and resilient outbound paths.

Learn from Zero

Part 1A — VPC Fundamentals

What is an Amazon VPC? A Virtual Private Cloud (VPC) is your own logically isolated network inside AWS. Think of it as renting an empty building in a data center — you decide the floor plan (IP addresses), which rooms are public-facing (public subnets), which are internal-only (private subnets), and how traffic moves between them (route tables).

Why do AWS applications use VPCs? Every production workload needs network isolation, controlled access, and predictable addressing. A VPC provides all three. Without a VPC, your resources would share a flat network with no boundaries — no control over who can reach what.

VPC CIDR block. When you create a VPC, you assign it an IPv4 CIDR block such as 10.0.0.0/16. This defines the pool of private IP addresses available inside the VPC. The /16 means the first 16 bits are fixed, leaving 65,536 total addresses. This is the maximum a single primary CIDR provides.

Subnets. A subnet is a smaller slice of the VPC CIDR placed in one specific Availability Zone. You divide the VPC range into non-overlapping subnets — for example, 10.0.1.0/24 (256 addresses) in AZ-a and 10.0.2.0/24 in AZ-b. Every EC2 instance, Lambda ENI, or RDS instance lives inside a subnet.

Availability Zones and distribution. An Availability Zone (AZ) is one or more physically separate data centers within a region. Distributing resources across at least two AZs protects against single-AZ failures — if AZ-a goes down, resources in AZ-b keep running. This is the foundation of resilient AWS architecture.

Public vs. private subnet. The words “public” and “private” are not labels you assign. A subnet is effectively public when its route table sends internet-bound traffic (0.0.0.0/0) to an Internet Gateway and the resources in it have public IPv4 addresses (or Elastic IPs). A subnet is private when it has no such route — or its route points to a NAT Gateway instead. Naming a subnet “public” in the console proves nothing about its actual connectivity.

Route tables. A route table is a set of rules (routes) that tells the VPC where to send traffic based on the destination IP. Every subnet is associated with exactly one route table. The route table decides whether traffic goes to the local VPC, the internet, a NAT Gateway, a VPC endpoint, or nowhere at all.

Network interfaces and private IPs. Every instance gets at least one elastic network interface (ENI) with a private IPv4 address drawn from its subnet’s CIDR. This private IP is how resources communicate within the VPC. It never changes for the life of the interface.

Public IPv4 and Elastic IPs. A public IPv4 address maps to the instance’s private IP through the Internet Gateway. It changes if you stop and start the instance. An Elastic IP (EIP) is a static public IPv4 address you allocate and associate explicitly — it persists across stops.

The relationship between routing, addressing, security groups, and NACLs. For internet connectivity to work, all four must cooperate:

  1. Routing — the subnet’s route table must have a path to the destination.
  2. Addressing — the resource must have a suitable IP (public IPv4 for direct internet access).
  3. Security groups — the instance’s stateful firewall must allow the traffic direction and port.
  4. NACLs — the subnet’s stateless firewall must allow both the request and the response.

A missing route means traffic has no path. A missing security-group rule means traffic is dropped at the instance. A missing NACL rule means traffic is dropped at the subnet boundary. These are independent checks — satisfying one does not bypass the others.

Network reachability does not imply permission. Even if all networking layers allow the connection, IAM policies, resource policies, and application-level authentication still control whether the AWS resource accepts the request. A network path is necessary but not sufficient.

Part 1B — CIDR Blocks and Subnet Design

CIDR notation. CIDR (Classless Inter-Domain Routing) describes an IP range as a base address plus a prefix length. 10.0.0.0/16 means “all addresses where the first 16 bits match” — that gives you 10.0.0.0 through 10.0.255.255 (65,536 addresses). 10.0.1.0/24 means the first 24 bits are fixed, giving 256 addresses (10.0.1.0–10.0.1.255).

How prefix length determines range. Shorter prefix = larger range. /16 = 65,536 addresses. /24 = 256 addresses. /28 = 16 addresses. Each additional bit halves the range.

Dividing a VPC CIDR into subnets. You carve the VPC CIDR into smaller, non-overlapping subnet CIDRs. If your VPC is 10.0.0.0/16, you might create 10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24, etc. The ranges must not overlap — AWS rejects a subnet CIDR that overlaps with an existing one.

Planning for growth. Good architects reserve address space for future subnets. If you use only 10.0.1.0/24 through 10.0.4.0/24 today, you still have 10.0.5.0/24 through 10.0.255.0/24 available for expansion. Using a /16 VPC CIDR gives you room; a /24 VPC CIDR does not.

AWS-reserved addresses. AWS reserves 5 IP addresses in every subnet:

AddressReserved for
.0Network address
.1VPC router
.2DNS server
.3Reserved for future use
Last address (.255 for /24)Network broadcast (not supported, but reserved)

A /24 subnet has 256 total addresses minus 5 reserved = 251 usable host addresses. A /28 subnet (16 total) has only 11 usable.

Why capacity matters. Every ENI consumes an IP. ECS tasks, Lambda functions in a VPC, and managed services like RDS all consume IPs. Under-sized subnets can cause launch failures when you run out of addresses.

IPv6 addressing. You can optionally assign a /56 IPv6 CIDR to a VPC (from Amazon’s pool or your own). IPv6 subnets are /64, providing an enormous address space. IPv6 addresses are globally unique — there is no concept of “private” IPv6 NAT in the same way as IPv4. IPv6 connectivity uses an Internet Gateway (for full bidirectional) or an Egress-Only Internet Gateway (for outbound-only). IPv6 NAT and IPv4 NAT are not interchangeable — they serve different protocol stacks and have different design patterns.

Part 1C — Route Tables and Route Selection

What a route table does. A route table is a list of rules evaluated whenever traffic leaves a resource in the subnet. Each rule (route) has a destination (a CIDR range) and a target (where to send matching traffic).

The VPC local route. Every route table automatically includes a local route for the VPC CIDR. For a 10.0.0.0/16 VPC, this route is: destination 10.0.0.0/16, target local. It allows all subnets in the VPC to communicate with each other. You cannot remove this route.

Main vs. custom route tables. Every VPC has a main route table that is the implicit default. Any subnet without an explicit association uses the main route table. Custom route tables are ones you create and explicitly associate with specific subnets. Best practice: leave the main route table restrictive (private) and create custom public route tables only for subnets that need internet access.

Route table association. Each subnet is associated with exactly one route table at a time. If you don’t explicitly associate a custom route table, the subnet uses the main route table. Different subnets can use different route tables — this is how public and private subnets get different routing behavior.

Longest-prefix matching. When multiple routes match a destination, AWS uses the most specific (longest prefix) route. A packet to 10.0.1.5 matches both 10.0.0.0/16 (local) and 10.0.1.0/24 if such a route exists. The /24 wins because it’s more specific. For internet traffic, 0.0.0.0/0 is the least specific route possible — it only matches when nothing more specific applies.

A missing route prevents connectivity. If there is no route matching the destination, the packet is dropped. Security groups and NACLs cannot compensate for a missing route — without a path, there is no traffic to allow or deny.

Part 1D — Internet Gateway (IGW)

What an Internet Gateway is. An IGW is a horizontally scaled, redundant, highly available VPC component that enables communication between your VPC and the internet. It performs network address translation for instances that have public IPv4 addresses.

Attachment model. You attach an IGW to a VPC, not to a subnet or instance. One VPC can have one IGW. The IGW serves the entire VPC, but only subnets with a route pointing to it can use it.

What makes a resource internet-accessible. Four conditions must be met for an EC2 instance to communicate directly with the internet:

  1. An IGW is attached to the VPC.
  2. The subnet’s route table has a route to the IGW (e.g., 0.0.0.0/0 → igw-xxxx).
  3. The instance has a public IPv4 address or Elastic IP (or an appropriate IPv6 address).
  4. Security groups and NACLs permit the traffic.

Removing any one of these breaks the connection. Adding an IGW alone does not make resources internet-accessible — routing, addressing, and security must all cooperate.

Unsolicited inbound vs. response traffic. When a security group allows inbound traffic on port 443, external clients can initiate HTTPS connections. When an instance initiates an outbound connection, the security group automatically allows the response (stateful). NACLs, being stateless, require explicit rules for both directions.

Why private resources should not be directly internet-exposed. A database server has no reason to accept connections from arbitrary internet addresses. Placing it in a private subnet with no IGW route eliminates this attack surface entirely at the network layer.

Worked Example: Public EC2 Web Server

  1. VPC 10.0.0.0/16 with IGW igw-abc123 attached.
  2. Public subnet 10.0.1.0/24 in AZ-a with route table: 0.0.0.0/0 → igw-abc123.
  3. EC2 instance launched with auto-assign public IP enabled → gets private IP 10.0.1.15 and public IP 54.x.x.x.
  4. Security group allows inbound TCP 443 from 0.0.0.0/0.
  5. Default NACL allows all traffic (or custom NACL allows 443 inbound + ephemeral port outbound).

An internet user sends HTTPS to 54.x.x.x:443. The IGW translates the public IP to the private IP, the route table delivers the packet to the subnet, the NACL allows it, and the security group allows it. The response follows the reverse path — the security group is stateful so the response is automatically allowed.

Part 1E — NAT Gateway

What a NAT Gateway is. A NAT (Network Address Translation) Gateway allows instances in private subnets to initiate outbound connections to the internet (or other external destinations) over IPv4, while preventing unsolicited inbound connections from reaching those instances. It translates private source IPs to the NAT Gateway’s own public Elastic IP.

Why private workloads need outbound access. Private EC2 instances often need to download OS patches, pull container images, call external APIs, or reach AWS service endpoints. They need outbound connectivity without being directly reachable from the internet.

How it works — placement and routing.

  1. The NAT Gateway lives in a public subnet (a subnet with a route to the IGW).
  2. The NAT Gateway has an Elastic IP for the standard public NAT pattern.
  3. The private subnet’s route table has 0.0.0.0/0 → nat-xxxx.
  4. When a private instance sends traffic to the internet, the packet goes to the NAT GW, which replaces the source IP with its own EIP, forwards the packet through the IGW, and maps the response back.

NAT Gateway vs. Internet Gateway.

NAT Gateway vs. NAT instance. A NAT instance is an EC2 instance you manage yourself running NAT software. A NAT Gateway is a managed service — no patching, automatic bandwidth scaling up to 100 Gbps, and built-in redundancy within its AZ. The exam almost always prefers NAT Gateway over NAT instance for production workloads.

Security rules still apply. Even though the NAT Gateway handles address translation, security groups on the private instances and NACLs on both the private and public subnets still control what traffic is allowed.

VPC endpoints as an alternative. For traffic to supported AWS services (S3, DynamoDB, CloudWatch, etc.), a VPC endpoint can route traffic directly without going through the NAT Gateway. This can reduce NAT costs and keep traffic on the AWS network.

Worked Example: Private EC2 Downloads a Software Package

Outbound path:

  1. Private EC2 (10.0.11.20) sends HTTPS request to packages.example.com.
  2. Private route table: 0.0.0.0/0 → nat-gw-a. Packet goes to the NAT Gateway in the public subnet.
  3. NAT Gateway replaces source IP 10.0.11.20 with its EIP 52.x.x.x and forwards via the public subnet’s route: 0.0.0.0/0 → igw-abc123.
  4. Packet exits through the IGW to the internet.

Return path:

  1. Response arrives at the IGW addressed to the NAT Gateway’s EIP.
  2. NAT Gateway maps the response back to 10.0.11.20 and forwards to the private subnet.
  3. The private instance receives the response.

The private instance never had a public IP. The internet only sees the NAT Gateway’s EIP.

Part 1F — NAT Gateway High Availability and Resiliency

A NAT Gateway is an AZ resource. When you create a NAT Gateway, you place it in a specific subnet in a specific AZ. It is redundant within that AZ (AWS manages the underlying instances), but it does not span AZs. If AZ-a becomes unavailable, a NAT Gateway in AZ-a becomes unavailable too.

The single-NAT-Gateway risk. If you route all private subnets (across both AZs) through one NAT Gateway in AZ-a:

  • AZ-a failure takes down the NAT Gateway.
  • Private subnets in AZ-b lose outbound internet connectivity even though AZ-b is healthy.
  • Cross-AZ traffic from AZ-b to the NAT Gateway in AZ-a also incurs data-transfer charges.

The resilient pattern: one NAT Gateway per AZ.

  • Deploy a NAT Gateway in each AZ’s public subnet.
  • Each private subnet’s route table points to the NAT Gateway in its own AZ.
  • If AZ-a fails, AZ-b’s private subnets still reach the internet through AZ-b’s NAT Gateway.
  • No cross-AZ data-transfer charges for NAT traffic.

Cost trade-off. Each NAT Gateway costs ~$0.045/hour (~$32/month). A two-AZ design doubles this to ~$64/month. For development environments, a single NAT Gateway may be acceptable. For production, the per-AZ pattern is the standard recommendation.

There is no automatic failover. If a NAT Gateway in AZ-a goes down and you have a second in AZ-b, the private subnets in AZ-a do not automatically reroute to AZ-b’s NAT Gateway. You would need to manually (or via automation) update AZ-a’s route table to point to AZ-b’s NAT Gateway. This is why the per-AZ design is preferred — it avoids the need for failover entirely.

Failure Scenario: Single NAT Gateway

Setup: One NAT Gateway in AZ-a public subnet. Both AZ-a and AZ-b private subnets route 0.0.0.0/0 → nat-gw-a.

AZ-a goes down:

  1. NAT Gateway in AZ-a becomes unreachable.
  2. Private instances in AZ-a are already affected by the AZ failure.
  3. Private instances in AZ-b are healthy but lose outbound internet — their route still points to the now-unavailable nat-gw-a.
  4. To recover AZ-b connectivity, an operator must update AZ-b’s route table to point to a different NAT Gateway.

With per-AZ NAT Gateways: AZ-b’s private subnets use nat-gw-b in AZ-b. When AZ-a fails, AZ-b connectivity is unaffected. No manual intervention required.

Part 1G — IPv6 and Egress-Only Internet Gateways

IPv4 vs. IPv6 routes. IPv4 uses 0.0.0.0/0 for the default route. IPv6 uses ::/0. They are separate entries in the route table and evaluated independently.

Egress-Only Internet Gateway (EIGW). For IPv6, AWS provides an Egress-Only Internet Gateway. It allows instances to initiate outbound IPv6 connections to the internet but prevents the internet from initiating unsolicited inbound IPv6 connections. It serves a similar purpose to a NAT Gateway for IPv4 outbound — but the mechanism is different because IPv6 addresses are globally routable (no address translation needed).

Why an EIGW is not a NAT Gateway.

When to use which. If your workloads are IPv4 and need outbound internet from private subnets, use a NAT Gateway. If your workloads are IPv6 and need outbound-only internet access, use an Egress-Only Internet Gateway. They are not interchangeable — each handles its protocol stack only.

Part 1H — Putting the Pieces Together

Complete three-tier network design:

Inbound user request path:

  1. Internet user sends HTTPS request.
  2. Request reaches the Internet Gateway.
  3. IGW routes to the public subnet where the ALB lives.
  4. ALB forwards the request to a target in the private application subnet (via VPC-internal routing, the local route).
  5. Application instance queries the private database subnet (again via the local route).
  6. Response flows back: database → app → ALB → IGW → internet user.

Independent outbound path (private instance to internet):

  1. Private app instance (10.0.11.20) needs to reach a public API.
  2. Private route table: 0.0.0.0/0 → nat-gw-a.
  3. NAT Gateway in the public subnet translates source IP to its EIP.
  4. Public subnet route table: 0.0.0.0/0 → igw-abc123.
  5. Packet exits through the IGW to the internet destination.

Route-table comparison:

Subnet tierDestinationTargetWhy

0.0.0.0/0igw-xxxxDirect internet access
Private App10.0.0.0/16localVPC-internal communication

VPC endpoints for AWS services. If the application tier frequently accesses S3 or DynamoDB, adding a gateway endpoint (free, no hourly charge) keeps that traffic off the NAT Gateway — reducing cost and latency. For services like Secrets Manager or CloudWatch Logs, an interface endpoint (powered by PrivateLink) provides a similar private path. This was covered in detail in Topic 6 (VPC Endpoints & PrivateLink).

The correct architecture depends on requirements. Not every subnet needs a default internet route, and not every workload needs NAT. Assign routes based on what each tier actually needs to communicate with.

Key principle: Diagnose layer by layer. A routing failure looks like a timeout. A security-group block looks like a timeout. An IAM denial returns an explicit error message. The symptom tells you which layer to investigate.

When Real Architects Actually Use This

Scenario A — Public Web Servers and a Private Database

Business requirement: A company runs a public-facing e-commerce site backed by application servers and an RDS PostgreSQL database. The database must not be accessible from the internet.

Architecture:

  • VPC 10.0.0.0/16 with two AZs.
  • Public subnets (10.0.1.0/24, 10.0.2.0/24) host the ALB. Route table: 0.0.0.0/0 → igw.
  • Private app subnets (10.0.11.0/24, 10.0.12.0/24) host EC2 application instances. Route table: 0.0.0.0/0 → nat-gw (for outbound patches).
  • Private DB subnets (10.0.21.0/24, 10.0.22.0/24) host RDS in a Multi-AZ deployment. Route table: only the local route.
  • RDS security group allows inbound PostgreSQL (5432) only from the app-tier security group.

Why not put the database in a public subnet? Even with a restrictive security group, a public subnet with an IGW route gives the database an attack surface it doesn’t need. A private subnet with no internet route eliminates this risk at the network layer.

Exam clue: “Database must not be directly accessible from the internet” → private subnet, no IGW route, security group restricted to the app tier.

Scenario B — Private EC2 Needs Software Updates

Business requirement: EC2 instances in private subnets must download OS patches from public repositories. They must not have public IP addresses.

Architecture:

  • NAT Gateway deployed in the public subnet with an Elastic IP.
  • Private subnet route table: 0.0.0.0/0 → nat-gw.
  • Instance security group allows outbound HTTPS (443) to 0.0.0.0/0 (or a more specific range).
  • The instance initiates the connection — responses flow back through the NAT Gateway.

Alternative for AWS services: If the instance needs to reach S3 (e.g., for yum repos hosted in S3), a gateway endpoint for S3 avoids NAT entirely — free, lower latency, and traffic stays on the AWS network.

Why not assign a public IP? A public IP makes the instance directly reachable from the internet, violating the requirement. The NAT Gateway provides outbound-only connectivity — the instance initiates, but the internet cannot initiate back.

Exam clue: “Private instances need outbound internet, no public IPs” → NAT Gateway in public subnet.

Scenario C — Multi-AZ Production Application

Business requirement: A production application spans two AZs. Private workloads must maintain outbound internet access even if one AZ fails.

Option 1 — Single NAT Gateway (lower cost, lower resilience):

  • One NAT Gateway in AZ-a’s public subnet.
  • Both AZ-a and AZ-b private subnets route through it.
  • Cost: ~$32/month for the gateway.
  • Risk: AZ-a failure kills outbound internet for AZ-b private subnets. Cross-AZ data transfer charges apply.

Option 2 — NAT Gateway per AZ (recommended for production):

  • NAT Gateway in AZ-a’s public subnet + NAT Gateway in AZ-b’s public subnet.
  • AZ-a private subnets route to nat-gw-a. AZ-b private subnets route to nat-gw-b.
  • Cost: ~$64/month for two gateways.
  • Benefit: AZ-independent. No cross-AZ data transfer for NAT. No failover needed.

Exam clue: “Highly available outbound internet from private subnets” → NAT Gateway in each AZ.

Scenario D — Public EC2 Is Not Reachable

Business requirement: An EC2 instance is in a subnet named “public,” but users cannot SSH into it.

Troubleshooting checklist:

  1. IGW attached? Verify the VPC has an IGW and it’s in the attached state.
  2. Route table? Check the subnet’s associated route table for 0.0.0.0/0 → igw-xxxx. If the subnet uses the main route table (which may not have this route), it’s effectively private.
  3. Public IP? Check whether the instance has a public IPv4 address or EIP. Without one, the IGW cannot translate traffic.
  4. Security group? Verify inbound rule allows SSH (TCP 22) from the user’s IP.
  5. NACL? Verify the subnet’s NACL allows inbound TCP 22 and outbound ephemeral ports (1024–65535).
  6. Service listening? Confirm SSHD is running on the instance.

Key lesson: The name “public” is just a label. What makes it public is the route to the IGW, a public IP on the instance, and security rules that permit the traffic.

Exam clue: “Instance in public subnet is unreachable” → check route table, public IP, security group, NACL.

Scenario E — Designing CIDR Ranges for Growth

Business requirement: A company needs a VPC for an application that will grow to include application, database, caching, and shared-service subnets across three AZs.

Architecture:

  • Choose a /16 VPC CIDR (65,536 addresses) to leave room for growth.
  • Assign /24 subnets (251 usable each) for standard tiers.
  • Use a numbering scheme: public = 10.0.1-3, app = 10.0.11-13, DB = 10.0.21-23, cache = 10.0.31-33.
  • Leave 10.0.100.0/22 and above unallocated for future services.
  • Avoid 172.31.0.0/16 (default VPC range) if you might peer VPCs later.

Why overlap matters: VPC peering and Transit Gateway cannot work with overlapping CIDRs. If two VPCs both use 10.0.0.0/16, they cannot peer. Plan unique ranges across your organization.

Exam clue: “Plan for future growth and VPC connectivity” → use a large CIDR, non-overlapping ranges, structured subnet numbering.

Scenario F — Reduce Unnecessary NAT Costs

Business requirement: A company processes large data volumes. Most outbound traffic from private subnets goes to S3 and DynamoDB, costing hundreds of dollars monthly in NAT Gateway data-processing fees.

Architecture:

  • Add a gateway VPC endpoint for S3 — free, no hourly charge, no per-GB processing fee.
  • Add a gateway VPC endpoint for DynamoDB — same benefits.
  • S3 and DynamoDB traffic now routes directly via the endpoint, bypassing NAT entirely.
  • Keep the NAT Gateway for traffic to destinations that don’t have endpoints (external APIs, third-party services).

Limitations: Gateway endpoints only work for S3 and DynamoDB. For other AWS services, interface endpoints (PrivateLink) are available but have their own hourly + per-GB charges — evaluate whether the cost trade-off makes sense for each service.

Exam clue: “Reduce NAT costs for AWS service traffic” → VPC gateway endpoints for S3/DynamoDB.

Scenario G — Secure IPv6 Outbound Connectivity

Business requirement: A company uses dual-stack (IPv4 + IPv6) instances. IPv6-enabled resources need outbound internet access for external API calls, but must not accept unsolicited inbound connections over IPv6.

Architecture:

  • Assign an IPv6 CIDR to the VPC and /64 IPv6 CIDRs to each subnet.
  • Create an Egress-Only Internet Gateway (EIGW).
  • Private subnet IPv6 route: ::/0 → eigw-xxxx.
  • The EIGW allows outbound-initiated IPv6 traffic but blocks unsolicited inbound initiation.

Why not a NAT Gateway? NAT Gateways handle IPv4 address translation. IPv6 addresses are globally unique and don’t need translation. An EIGW provides the outbound-only behavior without the cost and complexity of NAT. They are separate tools for separate protocols.

Exam clue: “IPv6 outbound-only internet access” → Egress-Only Internet Gateway, not a NAT Gateway.

Scenario H — Troubleshooting Multi-AZ Connectivity

Business requirement: An application works perfectly in AZ-a but private instances in AZ-b cannot reach the internet.

Investigation:

  1. Route-table association: AZ-b’s private subnet may be associated with the main route table (which has only the local route) instead of a custom route table with a NAT route.
  2. NAT Gateway placement: There may be no NAT Gateway in AZ-b, and AZ-b’s route table may point to a NAT Gateway in AZ-a that has been deleted or is in a failed state.
  3. Wrong route target: AZ-b’s route table may point to a NAT Gateway ID that doesn’t exist anymore (shows as a “blackhole” route).
  4. NACL difference: AZ-b’s subnet may have a different NACL that blocks the required traffic.

Resolution: Compare route-table associations, route targets, NAT Gateway status, and NACL rules between the two AZs. The most common cause is a missing or incorrect route-table association — the subnet is using the wrong route table.

Exam clue: “Works in one AZ, fails in another” → check route-table associations and NAT Gateway placement per AZ.

22 Exam Gotchas

  1. A subnet named “public” is not automatically public — what makes a subnet public is a route to an Internet Gateway in its associated route table, not its name. The exam will test whether you know the difference.
  2. Attaching an IGW does not make every resource internet-accessible — the IGW must be attached, the subnet needs a route to it, the instance needs a public IPv4 address, and security groups/NACLs must allow the traffic. All four conditions are required.
  3. A public IPv4 address or EIP is required for direct internet access — a resource in a public subnet with a route to the IGW still cannot communicate with the internet if it has no public IP. The IGW needs a public IP to perform NAT translation.
  4. An IGW is not a NAT Gateway — the IGW enables bidirectional internet access for resources with public IPs. A NAT Gateway enables outbound-only internet access for private instances. They are different components with different purposes.
  5. A NAT Gateway does not provide unsolicited inbound access — if the exam says “users must access an EC2 instance from the internet,” a NAT Gateway is the wrong answer. You need a public subnet with IGW access or a load balancer.
  6. A standard public NAT Gateway belongs in a public subnet — it needs a route to the IGW and an Elastic IP. Placing it in a private subnet breaks the outbound path because the NAT Gateway itself cannot reach the internet.
  7. Private instances do not need public IPs to use NAT — the NAT Gateway has the EIP, not the instance. The instance stays fully private. If the exam suggests assigning public IPs to private instances to enable outbound access, that contradicts the purpose of NAT.
  8. The private subnet’s default route goes to NAT, not to the IGW — 0.0.0.0/0 → nat-gw in a private subnet. 0.0.0.0/0 → igw in a public subnet. Swapping these is a common exam trap.
  9. Route-table associations determine routing, not subnet names — if a subnet has no explicit custom route-table association, it uses the main route table. A subnet you intended to be public may behave as private if it inherited the main route table without an IGW route.
  10. Longest-prefix matching selects routes — a packet destined for 10.0.1.5 matches 10.0.0.0/16 (local) and 10.0.1.0/24 (more specific). The /24 wins. For internet traffic, 0.0.0.0/0 is the least specific route and only matches when nothing else does.
  11. Security groups cannot compensate for a missing route — if no route exists for the destination, the packet is dropped before any security-group evaluation. A permissive security group with no route is useless.
  12. Routing does not override security rules — a route to the IGW creates a path, but security groups and NACLs still control whether traffic is permitted. Having a route and having permission are independent checks.
  13. One NAT Gateway does not provide AZ-independent redundancy — a NAT Gateway is an AZ-scoped resource. If that AZ fails, all subnets routing through it lose outbound internet — including subnets in healthy AZs.
  14. NAT Gateway failover is not automatic — AWS does not redirect private-subnet routes to a different NAT Gateway if one becomes unavailable. You must update route tables manually or via automation. The per-AZ design avoids the need for failover entirely.
  15. Cross-AZ NAT traffic incurs extra cost — routing AZ-b’s private subnets through a NAT Gateway in AZ-a adds cross-AZ data-transfer charges on top of NAT processing fees. The per-AZ pattern eliminates this.
  16. An Egress-Only IGW is not an IPv4 NAT Gateway — the Egress-Only IGW handles IPv6 outbound-only traffic. It does not perform address translation (IPv6 addresses are globally unique). It cannot replace a NAT Gateway for IPv4 traffic.
  17. IPv6 outbound design should not default to IPv4 NAT — if the exam specifies IPv6 outbound-only internet access, the answer is an Egress-Only Internet Gateway, not a NAT Gateway.
  18. Overlapping CIDRs prevent VPC peering and Transit Gateway connections — plan unique, non-overlapping CIDR ranges across all VPCs that might need to communicate. The 172.31.0.0/16 default VPC range is commonly duplicated and causes peering conflicts.
  19. AWS reserves 5 addresses per subnet — .0 (network), .1 (router), .2 (DNS), .3 (reserved), and last address (broadcast). A /24 has 251 usable IPs, not 256. A /28 has 11, not 16.
  20. Not every destination requires NAT — traffic to supported AWS services (S3, DynamoDB) can use a free VPC gateway endpoint, bypassing NAT entirely. The exam frequently tests this as a cost-optimization answer.
  21. A private database subnet does not need a default internet route — databases communicate with the application tier via VPC-internal routing (the local route). Adding 0.0.0.0/0 to a database subnet introduces unnecessary attack surface.
  22. A missing route produces a timeout, not an access-denied error — if traffic times out, check routes first. If traffic returns a 403 or Access Denied, the network path works but IAM or resource policies are blocking. The error type tells you which layer to investigate.

Quick-Fire Practice

Q1. A company runs EC2 instances in private subnets that need to download software updates from public internet repositories. The instances must not have public IP addresses. The VPC has an Internet Gateway attached. What additional configuration is required?

  • A. Enable auto-assign public IP on the private subnets so the instances can reach the internet through the IGW.
  • B. Create a NAT Gateway in a private subnet and update the private route table to route 0.0.0.0/0 to the NAT Gateway.
  • C. Create a NAT Gateway in a public subnet with an Elastic IP. Update the private subnet route table to route 0.0.0.0/0 to the NAT Gateway.
  • D. Add a route for 0.0.0.0/0 pointing to the Internet Gateway in the private subnet route table.

Correct Answer: C

A NAT Gateway must be placed in a public subnet (one with a route to the IGW) and needs an Elastic IP for the standard public NAT pattern. The private subnet’s route table then sends 0.0.0.0/0 to the NAT Gateway. A is wrong because assigning public IPs violates the requirement. B is wrong because a NAT Gateway in a private subnet cannot reach the internet. D is wrong because routing private instances directly to the IGW requires public IP addresses, which the instances don’t have.

Memory rule: NAT Gateway lives in public, serves private. Private route points to NAT, not to IGW.

Q2. A production application runs in private subnets across two Availability Zones. A single NAT Gateway in AZ-a provides outbound internet access for both AZs. The operations team is concerned about resilience. What change provides the MOST highly available outbound internet design?

  • A. Deploy a NAT Gateway in each AZ. Update each AZ’s private route table to use the NAT Gateway in its own AZ.
  • B. Add a second route in AZ-b’s route table pointing to the NAT Gateway in AZ-a as a backup path.
  • C. Replace the NAT Gateway with a NAT instance in an Auto Scaling group spanning both AZs.
  • D. Configure an AWS Lambda function to update route tables automatically when the NAT Gateway health check fails.

Correct Answer: A

Deploying a NAT Gateway in each AZ and routing each AZ’s private subnets to its own NAT Gateway provides AZ-independent resilience. If AZ-a fails, AZ-b’s connectivity is unaffected. B doesn’t help because a route table can only have one route per destination — you can’t add a backup 0.0.0.0/0 route. C introduces operational complexity; NAT instances require patching and don’t scale as well as managed NAT Gateways. D adds custom automation that still depends on detecting the failure first, introducing delay and complexity.

Memory rule: One NAT Gateway per AZ = AZ-independent. One shared NAT Gateway = single point of failure.

Q3. An EC2 instance in a subnet named “public-web” cannot be reached from the internet over HTTPS. The instance has a security group allowing inbound TCP 443 from 0.0.0.0/0. The VPC has an Internet Gateway attached. What should the solutions architect check FIRST?

  • A. Whether the instance’s security group allows outbound traffic on ephemeral ports.
  • B. Whether the subnet’s route table has a route to the Internet Gateway and whether the instance has a public IPv4 address.
  • C. Whether AWS Shield Standard is enabled for the VPC to allow inbound HTTPS traffic.
  • D. Whether the VPC’s DNS hostnames setting is enabled so the instance can receive external connections.

Correct Answer: B

A subnet name is just a label. For an instance to be reachable from the internet, the subnet’s route table must have 0.0.0.0/0 → igw and the instance must have a public IPv4 address or Elastic IP. These are the most common missing pieces when a “public” instance isn’t reachable. A is wrong because security groups are stateful — response traffic is automatically allowed. C is wrong because Shield Standard is always enabled automatically and does not control HTTPS access. D is wrong because DNS hostnames are unrelated to network reachability.

Memory rule: “Public subnet” = name only. Check route table + public IP first.

Multi-AZ vs Multi-Region: High Availability & Disaster Recovery

How architects design for AZ-level resilience, Regional disaster recovery, and everything in between.

Learn from Zero

Part 1A — What Is Resilience?

Resilience is the ability of a system to continue providing its intended function even when components fail. In cloud architecture, failure is not a question of “if” but “when” — hardware degrades, networks experience issues, entire data centers can be disrupted. A resilient system is designed so that these failures do not take down the application.

Why systems fail even when code is correct. Your application code might be perfect, but it runs on servers, disks, network links, and power supplies that can fail independently. A database server might restart, a network switch might drop packets, or an entire facility might lose power. Resilience means your architecture handles these events gracefully.

Key resilience concepts:

ConceptDefinitionExample
AvailabilityThe percentage of time a system is operational and accessible99.99% availability = ~4.3 minutes of downtime per month
ReliabilityThe ability to perform the intended function correctly and consistentlyA payment system that processes every transaction without errors
DurabilityThe likelihood that stored data will not be lostS3 provides 99.999999999% (11 nines) durability
Fault toleranceThe ability to continue operating despite specific component failuresAn application that keeps serving requests when one server crashes
Disaster recoveryThe process of restoring a system after a major disruptionRebuilding an application in another Region after a Regional outage

Redundancy is necessary but not sufficient. Simply copying a server does not guarantee resilience. You also need health checks (to detect failures), load balancing (to route away from failed resources), data replication (so the replacement has current data), and tested recovery procedures (so the team knows what to do).

Small failure vs. major disruption. Keeping an application running when a single EC2 instance crashes (high availability) is fundamentally different from restoring service after an entire AWS Region becomes unavailable (disaster recovery). Both require planning, but at different scales and costs.

Example: Online Shopping Application

Small failure: One of three web servers crashes. The load balancer detects the failure via health checks and routes traffic to the remaining two servers. Users never notice. This is high availability.

Major disruption: The primary Region experiences a widespread outage. The team activates their disaster recovery plan, promoting a database replica in another Region and redirecting DNS. Service is restored within the targeted recovery time. This is disaster recovery.

Part 1B — Availability, RTO, and RPO

High Availability (HA) means designing a system so that it continues operating when individual components fail. Key ingredients:

  • Redundant resources across multiple Availability Zones eliminate single points of failure.
  • Health checks detect unhealthy instances automatically.
  • Load balancing distributes requests only to healthy targets.
  • Data availability — the database must also be resilient, not just the application servers.

HA depends on the entire stack — servers, data, networking, and health detection — not just server count.

Fault Tolerance goes further: the system continues operating with zero interruption despite a failure. True fault tolerance often requires more redundancy and automation than a standard HA design — for example, synchronous data replication so no transactions are lost, and instant failover with no observable downtime.

Recovery Time Objective (RTO) is the maximum acceptable time to restore service after an interruption. RTO = 10 minutes means the business requires the application to be operational within 10 minutes of an outage. Lower RTO demands faster detection, more prepared standby environments, and greater operational readiness.

Recovery Point Objective (RPO) is the maximum acceptable amount of recent data loss, measured in time. RPO = 1 minute means you can lose at most 1 minute of committed data. Lower RPO demands more frequent replication or continuous synchronous replication.

Concrete Examples

These are business requirements, not AWS guarantees. The architecture must be designed, implemented, and tested to meet them.

Remember: RTO measures recovery time (how fast you’re back). RPO measures data loss (how much you lose). They are independent — you can have a short RTO with a long RPO, or vice versa.

Part 1C — Availability Zones vs AWS Regions

Availability Zones (AZs) are one or more discrete data centers with independent power, cooling, and networking within a Region. They are connected to each other through low-latency links but are physically separated to reduce correlated failures. Deploying across AZs protects against single-AZ disruptions like power outages or network failures in one facility.

AWS Regions are separate geographic locations, each with multiple AZs. Regions are fully independent infrastructure — a disruption in us-east-1 does not affect eu-west-1. Multi-Region architecture protects against the rare scenario of a complete Regional outage and can serve users closer to their geographic location.

Part 1D — Single-AZ, Multi-AZ, and Multi-Region Architectures

Single-AZ

  • All resources in one AZ. Simplest and cheapest.
  • Acceptable for development, testing, or low-criticality workloads.
  • An AZ disruption can affect every resource in that deployment.
  • No AZ-level redundancy by design.

Multi-AZ

  • Application, data, and networking resources distributed across 2+ AZs in one Region.
  • Load balancers route traffic to healthy targets; health checks detect failures.
  • Database tier uses Multi-AZ replication (e.g., RDS Multi-AZ) or distributed storage (Aurora).
  • Can survive most AZ-level failures without manual intervention.
  • Does not protect against a complete Regional outage.

Multi-Region

  • Application environments in 2+ AWS Regions.
  • Data must be replicated, backed up, or otherwise recoverable across Regions.
  • Failover may require DNS changes (Route 53), traffic shifting (Global Accelerator), or manual procedures.
  • Supports Regional DR, data residency requirements, and global latency optimization.
  • Significantly higher cost and operational complexity.

Multi-Region is not automatically better. Choose based on business requirements: What is the RTO? What is the RPO? What are the compliance constraints? What can the budget support? A well-designed multi-AZ architecture covers the vast majority of production workloads.

Part 1E — Disaster Recovery Strategies

AWS teaches four DR strategies, ordered from lower to higher preparedness and cost:

1. Backup and Restore

  • Before disaster: Data is backed up to another Region (S3 cross-Region replication, RDS snapshots, AWS Backup). Infrastructure is defined as code (CloudFormation) but not deployed.
  • During recovery: Deploy infrastructure from templates, restore data from backups, configure networking, start application.
  • RTO: Hours (provisioning + restoration time).
  • RPO: Depends on backup frequency — minutes to hours.
  • Cost: Lowest — you pay only for backup storage until a disaster occurs.
  • Best for: Non-critical workloads where hours of downtime are acceptable.

2. Pilot Light

  • Before disaster: Core data infrastructure (database replicas, data stores) runs continuously in the DR Region. Application servers and other non-core resources are not deployed (or are stopped).
  • During recovery: Provision/start application servers, scale up, switch traffic.
  • RTO: Tens of minutes (provisioning app servers takes time).
  • RPO: Near-zero if using continuous replication; depends on replication lag.
  • Cost: Low to moderate — data tier is always running, but compute is off.
  • Best for: Workloads needing faster recovery than backup/restore but not immediate.

3. Warm Standby

  • Before disaster: A scaled-down but fully functional copy of the production environment runs in the DR Region. All tiers are live — just at reduced capacity.
  • During recovery: Scale up to production capacity and switch traffic.
  • RTO: Minutes (scaling up, not provisioning from scratch).
  • RPO: Near-zero with continuous replication.
  • Cost: Moderate to high — a smaller version of production is always running.
  • Best for: Business-critical workloads needing fast recovery.

4. Multi-Site Active/Active

  • Before disaster: Full production environments run in multiple Regions simultaneously, serving traffic concurrently.
  • During recovery: Traffic is already distributed. A failing Region is removed from rotation. Remaining Regions absorb the load.
  • RTO: Near-zero for infrastructure failures (traffic shifts automatically).
  • RPO: Near-zero with synchronous or near-synchronous replication (but data corruption still requires backups).
  • Cost: Highest — full production infrastructure in multiple Regions.
  • Best for: Mission-critical global applications with near-zero downtime tolerance.

Part 1F — Active/Passive vs Active/Active

Active/Passive

  • One environment (primary) serves all production traffic.
  • A second environment (standby) is ready for recovery — ranging from backups to a warm standby.
  • Failover involves redirecting traffic to the standby and ensuring it is ready.
  • Simpler to reason about data ownership — writes happen in one place.
  • Requires a tested failover process; the standby is useless if recovery has never been practiced.

Active/Active

  • Multiple environments serve production traffic simultaneously.
  • Better utilization and potentially lower latency for geographically distributed users.
  • Introduces challenges: data consistency, conflicting writes, session management, eventual consistency.
  • Write strategies: write global (all writes to one Region), write local (writes to nearest Region with conflict resolution), or write partitioned (writes routed by partition key).
  • Not inherently better — the added complexity must be justified by the business requirement.
PatternMulti-AZ exampleMulti-Region example
Active/PassiveRDS Multi-AZ: primary in AZ-a, standby in AZ-b, automatic failoverPrimary Region serves traffic; DR Region has warm standby, failover via Route 53
Active/ActiveALB distributes traffic to targets in both AZs simultaneouslyBoth Regions serve users; DynamoDB global tables or Aurora global database for data

When to choose active/passive: The application has a single authoritative data source, the team wants simpler operations, or the DR Region is purely for recovery. When to choose active/active: The business needs global low latency, the data model supports multi-Region writes, and the team can handle the operational complexity.

Part 1G — Data Replication and Consistency

Failover is only useful when the data and dependencies are ready at the recovery site. Infrastructure without data is an empty shell.

Synchronous vs. asynchronous replication:

TypeHow it worksData loss riskLatency impact
SynchronousWrite is acknowledged only after both primary and replica confirmNear-zero (both copies are identical)Higher — write waits for both confirmations
AsynchronousWrite is acknowledged after primary confirms; replica updated laterPossible — replica may lag behind primaryLower — write returns quickly

Replication lag. With asynchronous replication, the replica is always some amount of time behind the primary. If the primary fails and you promote the replica, any transactions committed on the primary but not yet replicated are lost. This gap is the practical RPO.

Backups vs. replicas. A replica mirrors the primary, including unwanted changes (accidental deletes, data corruption). A point-in-time backup lets you restore to a moment before the corruption. Both are needed — replicas for fast failover, backups for data recovery.

Beyond the database. Application state, user sessions, uploaded files, configuration, secrets, message queues, and caches all need replication or recovery strategies. Failing over the database alone may leave the application broken if other dependencies are missing.

Cross-Region replication is not instant readiness. Having a database replica in another Region does not mean the entire application stack is ready to serve traffic. Application servers, networking, secrets, permissions, service quotas, and DNS must all be prepared.

Part 1H — Traffic Management and Failover

Resilience requires directing users to healthy resources. This happens at multiple levels:

Within a Region — load balancing and health checks:

  • An ALB or NLB distributes traffic across targets in multiple AZs.
  • Health checks detect unhealthy targets and stop sending traffic to them.
  • Auto Scaling replaces failed instances automatically.

Across Regions — DNS and global routing:

  • Route 53 failover routing: Health checks monitor the primary Region endpoint. If it becomes unhealthy, Route 53 returns the DR Region’s endpoint instead.
  • AWS Global Accelerator: Uses anycast IPs to route traffic to the nearest healthy endpoint, including cross-Region failover.
  • CloudFront origin failover: If the primary origin returns errors, CloudFront tries a secondary origin on a per-request basis.

DNS caching and TTL. When Route 53 switches a DNS record, clients using cached DNS responses continue reaching the old endpoint until the TTL expires. Lower TTLs enable faster failover but increase DNS query volume. DNS failover is not instantaneous for all clients.

Failover is more than DNS. Switching traffic to a second Region only works if that Region is ready:

  • Database promoted and accepting writes.
  • Application servers running and configured.
  • Secrets, certificates, and IAM roles in place.
  • Network paths (VPC, subnets, security groups) configured.
  • Service quotas sufficient for production load.
  • Downstream dependencies (APIs, queues, caches) available.

Example: Two-Region Failover

Normal operation: Route 53 points app.example.com to the ALB in us-east-1 (primary). Health checks monitor the primary endpoint every 30 seconds.

Primary fails: Health checks detect failure. Route 53 returns the us-west-2 (DR) ALB IP. Clients with expired DNS cache connect to us-west-2. The DR environment’s database replica is promoted to primary. Application servers in us-west-2 begin handling requests.

Reality check: Clients with cached DNS may take minutes to switch. Database promotion takes seconds to minutes depending on the engine. Application startup, secret loading, and dependency verification add time. The actual RTO is the sum of all these steps.

When Real Architects Actually Use This

Scenario A — Web Application Must Survive an AZ Failure

Business requirement: An e-commerce application must remain available if one AZ experiences a disruption.

Architecture:

  • EC2 instances across at least two AZs behind an Application Load Balancer with health checks.
  • Auto Scaling Group spans both AZs — replaces failed instances automatically.
  • RDS Multi-AZ provides a synchronous standby with automatic failover (60–120 seconds).
  • ElastiCache Multi-AZ (Redis) for session storage so sessions survive an AZ failure.

Why not two instances in the same AZ? If the AZ itself is disrupted, both go down. Multi-AZ distributes across independent failure domains.

Exam clue: “Remain available during an AZ failure” → resources in multiple AZs + load balancer + Multi-AZ database.

Scenario B — Regional Disaster Recovery

Business requirement: Production runs in us-east-1. If the Region becomes unavailable, recover in us-west-2 within 30 minutes (RTO) with at most 5 minutes of data loss (RPO).

Architecture:

  • Strategy: Warm standby. Scaled-down but fully functional environment in us-west-2.
  • Aurora global database replicates with typical lag under 1 second.
  • Application servers at reduced capacity in us-west-2.
  • Route 53 failover routing with health checks on the primary endpoint.
  • On failover: promote Aurora secondary (<1 min), scale ASG, Route 53 shifts traffic.

Why not pilot light? Pilot light requires provisioning app servers during recovery, adding time. Warm standby is faster for the 30-minute target.

Exam clue: “RTO 30 min, RPO 5 min, Regional DR” → warm standby + continuous replication.

Scenario C — Minimize Recovery Time

Business requirement: A financial application has near-zero RTO. Any downtime causes regulatory failures.

Architecture:

  • Strategy: Multi-site active/active. Both Regions serve traffic simultaneously.
  • Route 53 latency-based routing or Global Accelerator distributes traffic.
  • DynamoDB global tables for multi-Region read/write.
  • If one Region fails, the other absorbs all traffic — no failover delay.

Trade-off: Highest cost, most complex data model, requires write-conflict handling.

Exam clue: “Near-zero RTO, cannot tolerate any downtime” → multi-site active/active.

Scenario D — Minimize Disaster Recovery Cost

Business requirement: An analytics platform can tolerate 8 hours of downtime (RTO) and 4 hours of data loss (RPO). Cheapest DR approach needed.

Architecture:

  • Strategy: Backup and restore.
  • RDS snapshots every 4 hours, copied to DR Region via AWS Backup.
  • S3 cross-Region replication for data files.
  • CloudFormation templates ready in DR Region.
  • On disaster: deploy stack, restore RDS, update DNS.

Critical: Test the restore procedure regularly. An untested backup is not a recovery plan.

Exam clue: “Lowest cost DR, hours of downtime acceptable” → backup and restore.

Scenario E — Global Low-Latency Application

Business requirement: Users across three continents need sub-100ms responses. The app must survive a Regional failure.

Architecture:

  • Multi-Region active/active in us-east-1, eu-west-1, ap-northeast-1.
  • Route 53 latency-based routing sends users to the nearest Region.
  • DynamoDB global tables replicate across all three Regions.
  • CloudFront for static content caching at edge locations.

Data consistency: DynamoDB global tables use eventual consistency across Regions. The application must tolerate brief inconsistency windows.

Exam clue: “Global users, low latency, multi-Region” → active/active with latency-based routing.

Scenario F — Application Database Has Replication Lag

Business requirement: After failing over to a cross-Region replica, users report missing recent orders.

Root cause: The cross-Region read replica uses asynchronous replication. At failover, the replica was 45 seconds behind. Those 45 seconds of transactions were lost.

Lessons:

  • Asynchronous replication always has a lag window. RPO = replication lag at time of failure.
  • Monitor ReplicaLag in CloudWatch continuously.
  • Aurora global database typically replicates under 1 second.
  • Point-in-time backups protect against data corruption that replication would propagate.

Exam clue: “Recent data missing after failover” → asynchronous replication lag.

Scenario G — Active/Active Design With Conflicting Writes

Business requirement: Both us-east-1 and eu-west-1 must accept user profile updates simultaneously.

Options:

  • DynamoDB global tables: Last-writer-wins. Simple but may silently discard a concurrent update.
  • Aurora global database (write global): All writes to one Region. No conflicts but adds write latency for remote users.
  • Write partitioned: Each user writes to their “home” Region. Eliminates same-record conflicts but requires routing logic.

Key lesson: Multi-Region infrastructure does not solve data consistency. The data model and conflict resolution strategy must be designed explicitly.

Exam clue: “Active/active writes” → address conflict resolution strategy.

Scenario H — Failover Does Not Restore the Application

Business requirement: DNS failover to DR Region succeeds, but the application returns errors.

Root causes found:

  • Database replica not promoted — app could not write.
  • Secrets not replicated to DR Region — app could not authenticate.
  • IAM roles had stale policies.
  • Service quotas at default limits — ASG could not scale.
  • External API had only primary Region IP whitelisted.

Key lesson: DNS failover is just traffic redirection. The entire stack — database, secrets, permissions, quotas, networking, external dependencies — must be ready and tested.

Exam clue: “Failover succeeds but app still fails” → check all dependencies, not just DNS.

Multi-AZ vs Multi-Region Architecture

Left: A multi-AZ architecture distributes resources across AZs within one Region for high availability. The load balancer, application, database, and cache all span AZs with automatic failover. This handles most production failures but does not protect against a complete Regional outage. Right: A multi-Region architecture adds a recovery Region with replicated data and a standby (or active) environment. Route 53 failover or Global Accelerator shifts traffic during a Regional disaster. Actual recovery time depends on the DR strategy chosen, data replication lag, and full-stack readiness. Bottom: The four DR strategies form a spectrum — greater readiness and lower RTO/RPO come with increased cost and complexity.

20 Exam Gotchas

  1. An AZ failure is not a Regional failure — an AZ disruption affects one data center cluster. A Regional failure affects all AZs in that Region. Multi-AZ protects against the first; multi-Region protects against the second. The exam tests whether you know which scope the scenario describes.
  2. Multi-AZ alone does not protect against a complete Regional outage — if all AZs in a Region are disrupted, multi-AZ resources in that Region are all affected. Regional disaster recovery requires infrastructure in a second Region.
  3. Multi-Region does not automatically mean zero downtime — a second Region must be ready: data replicated, app servers running, secrets and permissions in place, DNS switched. The actual RTO depends on the DR strategy and implementation, not just having a second Region.
  4. RTO and RPO are different measurements — RTO is how fast you recover (time to restore service). RPO is how much data you can lose (time since last good data point). Confusing them changes the correct architecture. The exam uses specific RTO/RPO numbers to guide the answer.
  5. A backup is not a replica — backups are point-in-time snapshots used to restore to a specific moment. Replicas continuously mirror the primary (including unwanted changes). Backups protect against data corruption; replicas provide fast failover. Both are needed.
  6. Pilot light is not warm standby — pilot light keeps only the data tier running; application servers are off and must be provisioned during recovery. Warm standby keeps all tiers running at reduced capacity. Warm standby recovers faster but costs more.
  7. Warm standby is not active/active — warm standby is a scaled-down passive environment that does not serve production traffic. Active/active serves traffic from multiple Regions simultaneously. The exam may describe warm standby as “reduced capacity in standby Region.”
  8. Active/active does not eliminate data consistency challenges — concurrent writes from multiple Regions require conflict resolution (last-writer-wins, write-global, write-partitioned). Active/active infrastructure without a data consistency strategy leads to data conflicts.
  9. Asynchronous replication means potential data loss — if the primary fails before a replica catches up, transactions committed during the lag window are lost. RPO for async replication = the replication lag at the moment of failure, not zero.
  10. Application servers in separate AZs do not guarantee resilience — if the database is in a single AZ, or session state is lost, or health checks are missing, distributing servers across AZs only partially addresses availability. The entire stack must be resilient.
  11. Stateful dependencies must be handled during failover — user sessions, caches, uploaded files, message queues, and configuration all need replication or recovery strategies. Failing over compute without state leaves users with errors.
  12. DNS failover is not instant for every client — clients cache DNS responses based on TTL. After Route 53 changes a record, clients with cached responses continue using the old IP until TTL expires. Lower TTL enables faster switching but increases query volume.
  13. Health checks do not prove the entire application is ready — a health check may confirm that a load balancer responds on port 443. It does not verify that the database is promoted, secrets are loaded, downstream APIs are reachable, or service quotas allow scaling.
  14. A multi-Region app does not automatically replicate every resource — databases may be replicated, but secrets, IAM policies, VPC configurations, service quotas, certificate deployments, and external API whitelists are often separate. DR planning must cover all dependencies.
  15. Secrets, permissions, quotas, and networking must be pre-staged — the DR Region needs Secrets Manager entries, IAM roles, VPC/subnet configuration, security groups, and sufficient service quotas before a disaster occurs. Provisioning these during a crisis adds to RTO.
  16. The lowest-cost DR strategy cannot satisfy the strictest RTO/RPO — backup and restore is cheapest but has hours of RTO. If the business requires minutes of RTO, warm standby or active/active is needed. The exam maps RTO/RPO requirements to the appropriate strategy.
  17. A secondary Region is useless without tested recovery procedures — infrastructure that has never been tested for DR may have configuration drift, stale credentials, or missing dependencies. Regular DR drills are essential. The exam values “tested recovery.”
  18. High availability, fault tolerance, and disaster recovery are different — HA keeps the system running during small failures (multi-AZ). Fault tolerance continues without interruption despite a failure (zero-downtime design). DR restores service after a major disruption. The exam uses precise language to distinguish them.
  19. Route 53 alone is not a complete DR solution — Route 53 failover routing redirects DNS traffic. It does not provision infrastructure, promote databases, replicate secrets, or verify application readiness. It is one component of a DR plan, not the entire plan.
  20. More copies of infrastructure do not always mean better resilience — deploying in 5 Regions does not help if data replication, failover automation, and recovery testing are not in place. Resilience comes from design, not just duplication.

Quick-Fire Practice

Q1. A company runs a web application on EC2 instances behind an Application Load Balancer. The application must remain available if one Availability Zone experiences a disruption. The database is Amazon RDS MySQL in a single AZ. Which change provides the MOST resilient architecture?

  • A. Add more EC2 instances in the same AZ and increase the instance size for higher throughput.
  • B. Deploy EC2 instances across two AZs, configure the ALB to span both AZs, and enable RDS Multi-AZ for the database.
  • C. Create a cross-Region read replica of the RDS database and configure Route 53 failover routing.
  • D. Move all resources to a larger instance type in a single AZ and enable enhanced monitoring.

Correct Answer: B

Multi-AZ deployment distributes application instances and provides automatic database failover. The ALB routes traffic to healthy targets across AZs, and RDS Multi-AZ maintains a synchronous standby that promotes automatically during an AZ disruption. A adds capacity but not AZ resilience. C addresses Regional DR (overkill for AZ-level HA) and does not fix the single-AZ application tier. D increases capacity but remains a single point of failure.

Memory rule: “Survive AZ failure” = multi-AZ deployment for both compute and database.

Q2. A company requires a disaster recovery solution for a critical application. The business defines an RTO of 30 minutes and an RPO of 5 minutes. The recovery site must be in a different AWS Region. Which disaster recovery strategy BEST meets these requirements at the lowest cost?

  • A. Backup and restore: copy daily RDS snapshots to the DR Region and redeploy infrastructure from CloudFormation during a disaster.
  • B. Pilot light: continuously replicate the database to the DR Region, but keep application servers off until needed.
  • C. Warm standby: run a scaled-down but fully functional environment in the DR Region with continuous database replication.
  • D. Multi-site active/active: run full production environments in both Regions with DynamoDB global tables.

Correct Answer: C

With an RTO of 30 minutes and RPO of 5 minutes, backup and restore (A) is too slow — daily snapshots give RPO of up to 24 hours, and restoring infrastructure takes hours. Pilot light (B) could meet the RPO with continuous replication but provisioning application servers from scratch may push past 30 minutes for complex applications. Warm standby (C) meets both targets: continuous replication achieves near-zero RPO, and all tiers are already running so scaling up takes minutes. Active/active (D) meets the targets but is far more expensive than necessary.

Memory rule: Match the DR strategy to the RTO/RPO. Warm standby = minutes RTO, near-zero RPO. Don’t over-spend on active/active when warm standby suffices.

Q3. A company uses an Aurora global database with a primary cluster in us-east-1 and a secondary cluster in eu-west-1. During a Regional failover drill, the secondary cluster is promoted successfully and Route 53 redirects traffic. However, the application in eu-west-1 returns authentication errors. What is the MOST likely cause?

  • A. Route 53 failover routing does not work with Aurora global database endpoints.
  • B. Aurora global database does not support cross-Region failover and the secondary cluster cannot accept writes.
  • C. The application’s database connection strings are hardcoded to the us-east-1 endpoint and cannot reach the promoted cluster.
  • D. The application depends on secrets stored in AWS Secrets Manager in us-east-1 that were not replicated to eu-west-1.

Correct Answer: D

Aurora global database fully supports cross-Region promotion (B is wrong). Route 53 works with any endpoint (A is wrong). If the application successfully reaches the DR Region and the database is promoted, authentication errors point to missing credentials. Secrets Manager secrets are Regional — if database passwords, API keys, or certificates were not replicated to eu-west-1, the application cannot authenticate. C is plausible but the scenario states DNS was redirected successfully, implying the application is reaching the correct Region. The authentication error specifically points to missing secrets.

Memory rule: DR is more than database + DNS. Secrets, IAM, quotas, and external dependencies must all be pre-staged in the recovery Region.

Elastic Load Balancing & Auto Scaling

How architects distribute traffic, scale compute capacity, and build self-healing applications that respond to demand.

Learn from Zero

Part 1A — Load Balancing Fundamentals

Load balancing means distributing incoming network traffic across multiple servers so that no single server carries all the load. Without a load balancer, one EC2 instance handles every request — creating both a performance bottleneck and a single point of failure. If that instance crashes, the application is down.

Why a single EC2 instance is a problem. One server has a fixed amount of CPU, memory, and network bandwidth. When requests exceed its capacity, response times degrade and requests start failing. Worse, any hardware, software, or AZ-level failure takes down the entire application. Load balancing eliminates both problems by spreading traffic across a fleet of instances.

Example: Online Shopping Application

An online store receives thousands of requests per second during a sale. With a single EC2 instance, the server runs out of CPU during peak traffic and starts returning errors. With a load balancer in front of four instances across two AZs:

  • The load balancer receives every request and forwards it to one of the four servers.
  • Each server handles roughly a quarter of the traffic.
  • If one server crashes, the load balancer detects the failure via health checks and routes traffic to the remaining three.
  • If an entire AZ goes down, the instances in the surviving AZ continue serving traffic.

Key components of load balancing:

ConceptDefinitionExample
TargetA destination that can receive traffic — an EC2 instance, container, IP address, or Lambda functionAn EC2 instance running your web server on port 443
Target groupA logical collection of targets that the load balancer routes requests to. Each target group has its own health-check configurationA target group containing four EC2 instances running the API service
ListenerA process that checks for connection requests on a configured protocol and portAn HTTPS listener on port 443 that accepts incoming requests
Listener ruleA condition that determines which target group receives a request. Rules can match host headers, URL paths, HTTP headers, and other request attributesA rule that sends /api/* requests to the API target group

Health checks are essential. Without health checks, a load balancer would send traffic to crashed or unresponsive servers, causing user-visible failures. The load balancer periodically sends a request (the health check) to each target. If a target fails to respond correctly for a configured number of consecutive checks, it is marked unhealthy and the load balancer stops routing new requests to it.

A load balancer does not automatically make the entire application highly available. The load balancer distributes traffic, but availability depends on the full stack:

  • Backend capacity — enough healthy targets must exist to handle the load.
  • Data availability — if the database is single-AZ and it fails, every target returns errors even though the load balancer is healthy.
  • Network routing — subnets, security groups, and NACLs must allow traffic to reach the targets.
  • Health check accuracy — a superficial health check (ping) may not detect application-level failures.
  • Application design — if one target holds session state locally and fails, that user’s session is lost.

Connection draining (deregistration delay). When a target is removed from a target group (during deployment, scale-in, or failure), active requests may still be in progress. Connection draining gives those in-flight requests time to complete before the load balancer fully removes the target. Without it, ongoing requests are abruptly terminated. The default deregistration delay is 300 seconds. This is critical during rolling deployments and scale-in events.

Connection to Topic 9. Load balancing is the traffic-distribution layer in the multi-AZ architecture discussed in Topic 9. A load balancer that spans two AZs, combined with targets distributed across both AZs, enables the application to survive an AZ failure. But the load balancer alone does not provide multi-AZ resilience — the targets, database, and all other dependencies must also be distributed.

Part 1B — Elastic Load Balancing Types

AWS offers four load balancer types. Each operates at a different network layer and serves different architectural purposes.

Application Load Balancer (ALB)

The ALB operates at Layer 7 (application layer) and understands HTTP and HTTPS traffic. It can inspect request content — URLs, headers, cookies, query strings — and make intelligent routing decisions.

How ALB routes traffic:

  • A listener accepts traffic on a port (typically 80 or 443).
  • Listener rules evaluate request attributes and route to the matching target group.
  • Host-based routing — route based on the Host header (e.g., api.example.com → API targets, www.example.com → frontend targets).
  • Path-based routing — route based on the URL path (e.g., /api/*, /images/*).
  • Header and query-string routing — route based on HTTP headers or query parameters.
  • A default action handles requests that match no explicit rule.

Example: One ALB, Three Backend Services

A company runs a web application with three components. A single ALB handles all traffic:

  • /api/* → API target group (EC2 instances running the REST API)
  • /images/* → Image service target group (EC2 instances optimized for media processing)
  • Everything else → Frontend target group (EC2 instances serving the React application)

Each target group has its own health check, scaling, and instance configuration. The ALB replaces what would otherwise require three separate load balancers.

ALB capabilities:

  • Target types: EC2 instances, IP addresses, Lambda functions, containers (ECS/EKS).
  • TLS termination: HTTPS listeners decrypt TLS using certificates managed by AWS Certificate Manager (ACM), forwarding decrypted HTTP to backend targets.
  • Sticky sessions: Route a user’s requests to the same target using application-based or duration-based cookies.
  • WebSocket support.
  • HTTP/2 support.
  • Authentication integration with OIDC and Amazon Cognito.

Why ALB is the default for web applications. If your traffic is HTTP/HTTPS and you need routing based on URL path, hostname, headers, or query strings, ALB is typically the right choice. An NLB cannot inspect HTTP content and cannot perform path-based or host-based routing.

Network Load Balancer (NLB)

The NLB operates at Layer 4 (transport layer) and handles TCP, UDP, and TLS traffic. It does not inspect HTTP content — it distributes network connections to targets based on protocol and port.

NLB characteristics:

  • High performance and low latency — designed for millions of requests per second with ultra-low latencies.
  • Static IP addresses — each NLB node in an AZ gets a static IP. You can also assign an Elastic IP to each AZ. This is critical when clients or firewalls must whitelist specific IP addresses.
  • Preserves source IP — targets see the client’s original IP address (for TCP and TLS).
  • TLS termination — NLB can terminate TLS and forward decrypted traffic, or pass TLS traffic through to targets.
  • Target types: EC2 instances, IP addresses, ALBs (NLB in front of ALB pattern).
  • Zonal behavior — by default, each NLB node routes to targets only in its own AZ. Cross-zone load balancing distributes across all AZs but must be explicitly enabled.

When to choose NLB over ALB:

  • Non-HTTP protocols (TCP, UDP, gaming, IoT, financial protocols).
  • The client requires a static IP address or Elastic IP for firewall allowlisting.
  • Extreme performance requirements (millions of concurrent connections).
  • You need to preserve the client’s source IP without proxy protocol workarounds.

NLB is not a better version of ALB. It cannot route by URL path, hostname, or HTTP headers. If you need application-layer routing, NLB is the wrong choice.

Gateway Load Balancer (GWLB)

The GWLB operates at Layer 3 (network layer) and is designed for deploying, scaling, and managing fleets of third-party network virtual appliances — firewalls, intrusion detection systems, deep packet inspection tools.

How it works:

  • Traffic is routed to GWLB via Gateway Load Balancer endpoints (GWLBE) in your VPC.
  • GWLB distributes traffic across a fleet of appliance instances for inspection.
  • After inspection, traffic is returned to the original path.
  • Uses the GENEVE protocol to encapsulate traffic.

When to choose GWLB: Centralized traffic inspection, a fleet of third-party security appliances, or architectures where all traffic must pass through a network appliance before reaching the application. GWLB is not a substitute for ALB or NLB — it solves a different architectural problem.

For SAA-C03, know what GWLB does (appliance fleet scaling and inspection) and when it is used (network security and traffic inspection), not deep implementation details.

Classic Load Balancer (CLB)

The CLB is the original AWS load balancer, predating ALB, NLB, and GWLB. It operates at both Layer 4 and Layer 7 but with a simpler, less flexible feature model.

  • Does not support target groups, listener rules, host-based routing, or path-based routing.
  • Targets are registered directly to the CLB rather than organized into target groups.
  • Does not support WebSocket, HTTP/2 natively, or Lambda targets.
  • Considered legacy — AWS recommends migrating to ALB or NLB for new deployments.

Why it still appears: Existing legacy applications may still use CLBs. The exam may mention CLB to test whether you recognize it as a previous-generation service or to compare it with modern options.

Part 1C — Target Groups, Listeners, Health Checks, and TLS

Listeners

  • A listener is a process that checks for connection requests using a configured protocol and port (e.g., HTTPS on port 443).
  • Each load balancer has at least one listener.
  • ALB listeners support rules that inspect HTTP request attributes and route to different target groups. Each rule has a priority, conditions, and an action (forward to a target group, redirect, return fixed response).
  • NLB listeners route based on protocol and port only — no request inspection.
  • A default action handles requests that match no other rule.

Target groups

  • Targets are grouped so the load balancer can route different types of requests to different backend services.
  • Each target group defines: target type (instance, IP, Lambda), protocol, port, health-check settings, and deregistration delay.
  • New targets are registered with the group (manually or by an Auto Scaling group).
  • Separate target groups let you run distinct services behind one load balancer: the API on one group, the frontend on another, each with independent scaling and health checks.

Health checks

  • The load balancer periodically sends a request to each target to verify it can handle traffic.
  • Configurable parameters: protocol, port, path (e.g., /health), expected response codes, check interval, timeout, healthy threshold, unhealthy threshold.
  • If a target fails the unhealthy threshold (e.g., three consecutive failed checks), the load balancer marks it unhealthy and stops routing new requests to it.
  • A target marked unhealthy can become healthy again if it passes the healthy threshold.
  • A health check is not proof that the entire application works. A /health endpoint that returns 200 does not prove the database is reachable, caches are populated, or downstream APIs are available. Design health-check endpoints to verify meaningful application readiness.

Load-balancer health checks vs. Auto Scaling health checks. The load balancer decides whether to route traffic to a target. An Auto Scaling group decides whether to replace an instance. These are separate decisions:

ResponsibilityELB health checkASG health check
PurposeRoute or stop routing trafficTerminate and replace unhealthy instances
Default typeHTTP/TCP check on targetEC2 status check (system & instance status)
Optional—Can be configured to also use ELB health-check status
Consequence of failureTarget removed from rotationInstance terminated and replaced

If an ASG uses only EC2 status checks, an instance could fail its ELB health check (application not responding) but the ASG would not replace it because the EC2 status check still passes. Configure the ASG to use ELB health checks when instances are registered with a load balancer.

TLS

  • HTTPS listeners on ALB and TLS listeners on NLB can terminate TLS — decrypt incoming encrypted traffic using a certificate.
  • Certificates are managed through AWS Certificate Manager (ACM), which provides free public certificates and handles renewal automatically.
  • Client → Load Balancer: Encrypted with TLS (HTTPS or TLS listener).
  • Load Balancer → Target: Can be HTTP (unencrypted) or HTTPS (re-encrypted). The security of the backend connection is a separate architectural decision.
  • For compliance, some organizations require end-to-end encryption (TLS to the load balancer, then TLS again to the target).
  • NLB can alternatively pass TLS through without terminating — the target handles decryption directly.

Part 1D — Cross-Zone Load Balancing and Availability

What cross-zone load balancing means. A load balancer has nodes in each AZ where it is configured. Without cross-zone load balancing, each node distributes traffic only to targets in its own AZ. With cross-zone enabled, each node distributes across all registered targets in all AZs.

Why it matters. If targets are unevenly distributed (e.g., 4 instances in AZ-A, 2 in AZ-B), without cross-zone balancing each AZ node gets 50% of traffic. This means AZ-B’s 2 instances each handle 25% of total traffic, while AZ-A’s 4 instances each handle 12.5%. This creates an uneven load.

Worked Example: Uneven Target Distribution

AZ-A (4 instances)AZ-B (2 instances)
Cross-zone OFFEach instance gets 12.5% of trafficEach instance gets 25% of traffic
Cross-zone ONEach instance gets ~16.7% of trafficEach instance gets ~16.7% of traffic

With cross-zone on, traffic is evenly distributed regardless of which AZ has more targets. This prevents overloading AZ-B’s smaller fleet.

Defaults by load balancer type:

  • ALB: Cross-zone load balancing is enabled by default (can be disabled at the target-group level).
  • NLB: Cross-zone load balancing is disabled by default. Must be explicitly enabled. Cross-zone traffic incurs data transfer charges.
  • GWLB: Disabled by default.
  • CLB: Disabled by default.

AZ failure scenario. If AZ-A fails and all targets there become unhealthy, the load balancer routes all traffic to AZ-B’s targets. Those remaining targets must have enough capacity to absorb the full load. Multi-AZ distribution is only useful if each surviving AZ can handle 100% of the traffic during a failure.

What the load balancer cannot do. The load balancer distributes traffic, but it cannot fix an unavailable database, a full disk, an expired certificate, or an application-wide bug. If every target is unhealthy due to a shared dependency failure, the load balancer has nowhere to route traffic.

Part 1E — Amazon EC2 Auto Scaling Fundamentals

Amazon EC2 Auto Scaling automatically adjusts the number of EC2 instances in your fleet based on demand, health, and configuration. It provides both elasticity (scaling to match demand) and resilience (replacing failed instances).

Vertical vs. horizontal scaling:

TypeHow it worksLimitation
Vertical (scale up/down)Change the instance type to one with more or fewer resourcesRequires downtime; hard upper limit on instance size; single point of failure remains
Horizontal (scale out/in)Add or remove instances from the fleetApplication must support multiple instances (stateless design preferred); slightly more complex

Horizontal scaling is the standard approach for resilient web architectures because it adds both capacity and redundancy without an upper bound tied to instance size.

Auto Scaling group (ASG). An ASG is a collection of EC2 instances managed as a logical unit. The ASG maintains a specified number of instances and can scale the count based on demand.

Capacity settings:

SettingMeaningConstraint
Minimum capacityThe floor — the ASG never reduces below this countSet to the minimum number of instances needed for availability (e.g., 2 for multi-AZ)
Desired capacityThe current target — the ASG tries to maintain exactly this many healthy instancesMust be ≥ minimum and ≤ maximum
Maximum capacityThe ceiling — the ASG never exceeds this count, even under heavy loadProtects against runaway scaling and unexpected costs

Example: Capacity Settings

Min: 2  |  Desired: 4  |  Max: 10

  • The ASG launches 4 instances at creation.
  • If one instance fails, the ASG terminates it and launches a replacement to maintain 4.
  • A scaling policy detects high CPU and increases desired to 7 — 3 new instances are launched.
  • Traffic drops — the policy reduces desired to 3. The ASG terminates 4 instances.
  • The ASG never goes below 2 (minimum) or above 10 (maximum), regardless of the scaling signal.

Critical: Maximum = 10 does not mean the ASG will automatically reach 10 instances. Scaling to 10 only happens if a scaling policy or manual action requests it. Without a trigger, the ASG stays at its desired capacity.

AZ distribution. An ASG distributes instances across the AZs in its configured subnets. If configured for two AZs, the ASG tries to balance instances evenly. This means an AZ failure only loses roughly half the fleet, and the ASG launches replacements in the healthy AZ.

Launch templates. A launch template defines everything needed to create an instance: AMI ID, instance type, key pair, security groups, IAM instance profile, storage configuration, user data (startup script), and network settings. The ASG uses the launch template to create identical instances. This is why instances launched by an ASG should be reproducibly configured — each new instance must start the application correctly without manual intervention.

ASG and load balancer integration. An ASG can be configured to automatically register new instances with a target group. When the ASG launches an instance, the instance is registered; when it terminates one, the instance is deregistered. This creates a self-healing loop: the load balancer routes traffic, the ASG maintains capacity, and health checks connect both systems.

Part 1F — EC2 Auto Scaling Policies

Scaling policies tell the ASG when and how much to change capacity.

Dynamic Scaling

Dynamic scaling adjusts capacity in response to real-time changes in demand, using CloudWatch metrics.

Target tracking scaling

  • You specify a target value for a metric (e.g., “keep average CPU utilization at 50%”).
  • The ASG automatically adjusts the number of instances to maintain that target, similar to a thermostat.
  • Scales out when the metric exceeds the target; scales in when it drops below.
  • Typically the best starting point for most workloads due to its simplicity.
  • Common metrics: ASGAverageCPUUtilization, ALBRequestCountPerTarget, custom CloudWatch metrics.

Step scaling

  • Uses CloudWatch alarms with multiple thresholds that trigger different capacity adjustments.
  • Example: CPU > 60% → add 1 instance; CPU > 80% → add 3 instances.
  • More control than target tracking but requires more configuration.
  • Useful when you need different responses at different alarm levels.

Simple scaling

  • A single CloudWatch alarm triggers a single scaling adjustment.
  • After scaling, a cooldown period prevents additional scaling actions until the system stabilizes.
  • Less responsive than step scaling because it waits during cooldown.
  • Generally superseded by target tracking and step scaling.

Choosing the right metric. CPU utilization is a common default, but it is not always the best signal. A web server might have low CPU but be overloaded by concurrent connections. A data processing service might have high CPU that is normal, not a sign of overload. The best scaling metric reflects what actually constrains your application’s ability to serve users — requests per target, queue depth, or a custom application metric.

Scheduled Scaling

  • Changes capacity at specific times based on a known schedule.
  • Example: increase minimum to 8 instances every weekday at 8 AM, reduce to 2 at 8 PM.
  • Ideal for predictable recurring patterns: business hours, marketing campaigns, batch processing windows.
  • Scheduled scaling alone does not respond to unexpected spikes. Combine it with dynamic scaling for complete coverage.

Predictive Scaling

  • Uses machine learning to analyze historical traffic patterns and forecast future demand.
  • Pre-provisions capacity before the predicted demand arrives, reducing the lag of reactive scaling.
  • Works best with recurring, cyclical workloads where historical data is a reliable guide.
  • Does not replace dynamic scaling — it complements it. Unpredictable bursts still need reactive policies.
  • Effectiveness depends on how well historical patterns predict future demand. A new application with no history has nothing to learn from.

Part 1G — Auto Scaling Configuration and Lifecycle

Launch templates and ASGs. A launch template is the blueprint; the ASG is the manager. When the ASG decides to scale out, it uses the launch template to create a new instance with the correct configuration. Updating the launch template (e.g., new AMI) creates a new version — the ASG can be updated to use the new version for future launches.

Instance warm-up. A newly launched instance needs time to start the application, load caches, and reach steady state. During warm-up, the instance’s metrics are not yet representative. If the ASG uses the new instance’s initially low CPU for scaling decisions, it might launch even more instances unnecessarily. Warm-up periods tell the ASG to exclude new instances from scaling metric calculations until they are ready.

Health-check grace period. When an instance launches, the application may take minutes to initialize. If the ASG checks health immediately, it might terminate a perfectly good instance that simply has not finished starting. The health-check grace period gives the application time to pass health checks before the ASG starts evaluating its health. A common mistake: setting the grace period too short, causing a cycle of launch → terminate → launch.

Lifecycle hooks. Hooks pause an instance during launch or termination to allow custom actions:

  • Launch hook: Instance enters Pending:Wait. Use it to install software, pull configuration, register with external systems, run integration tests, then signal completion.
  • Termination hook: Instance enters Terminating:Wait. Use it to push logs, deregister from services, drain connections, then signal completion.

Instance refresh. When you update a launch template (new AMI, configuration change), existing instances still run the old version. Instance refresh replaces instances in a rolling fashion: terminate a batch, launch replacements with the new template, wait for health checks, then proceed to the next batch. This is how you deploy new application versions across an ASG without downtime.

Deregistration delay and connection draining. When an instance is being terminated or deregistered from a target group:

  1. The load balancer stops sending new requests to the instance.
  2. Existing in-flight requests continue for the deregistration delay period (default 300 seconds).
  3. After the delay expires, remaining connections are closed.

This is the load balancer’s responsibility. The ASG does not manage connection draining — it tells the load balancer to deregister the instance, and the load balancer handles the graceful removal.

Termination policies. When the ASG needs to scale in (reduce capacity), it chooses which instances to terminate. The default policy prioritizes the AZ with the most instances (to maintain balance), then selects the instance with the oldest launch configuration or template. Other policies include: oldest instance, newest instance, or closest to the next billing hour.

Launching does not mean ready. An instance can be “running” in EC2 terms but not yet serving application traffic. The application must start, pass health checks, warm up, and be registered with the target group before it absorbs real load. This initialization time affects how quickly Auto Scaling can respond to a spike.

Part 1H — Auto Scaling and High Availability

ELB and EC2 Auto Scaling are complementary services that together create self-healing, demand-responsive applications. Neither is sufficient alone.

How they work together:

Internet users → Load Balancer → ASG instances in multiple AZs → Database / Backend services

  • ELB distributes traffic to healthy targets across AZs.
  • ELB health checks detect unhealthy targets and remove them from routing.
  • The ASG maintains capacity by launching instances to match the desired count.
  • The ASG replaces unhealthy instances when configured to use ELB health checks.
  • Scaling policies adjust capacity based on demand metrics.

AZ failure scenario:

  1. AZ-A fails. All instances in AZ-A become unhealthy.
  2. The load balancer stops routing traffic to AZ-A targets.
  3. AZ-B targets receive all traffic — they must have enough capacity.
  4. The ASG detects the unhealthy instances and launches replacements in AZ-B.
  5. Scaling policies may trigger additional instances if load increases beyond AZ-B’s current capacity.

Critical: If AZ-B had exactly enough capacity for half the traffic, it cannot absorb the full load. Always provision enough headroom in the surviving AZ, or ensure scaling policies can respond quickly enough.

High availability vs. elasticity. These are different properties:

PropertyMeaningAchieved by
High availabilitySystem remains operational during component failuresMulti-AZ distribution, health checks, automatic replacement
ElasticitySystem adjusts capacity to match demandScaling policies, metric-driven capacity changes

An application can be highly available without scaling (fixed fleet across AZs) or elastic without being highly available (scaling within a single AZ). Best practice combines both.

Stateless vs. stateful. Horizontal scaling works best when instances are stateless — any instance can handle any request because session data is stored externally (ElastiCache, DynamoDB, or cookies). Stateful instances (local session storage) create problems: if the instance terminates, the user’s session is lost. Sticky sessions can partially mitigate this but re-introduce a single-point-of-failure problem for the stuck sessions.

What Auto Scaling does NOT do:

  • It does not scale the database. If the database is the bottleneck, more EC2 instances will not help.
  • It does not route traffic. That is the load balancer’s job.
  • It does not guarantee instant capacity. Instances take time to launch and initialize.
  • It does not replace networking, security, or data-tier resilience. The ASG manages compute capacity only.

When Real Architects Actually Use This

Scenario A — HTTP Application With Multiple Backend Services

Business requirement: A company runs a website at www.example.com and an API at www.example.com/api/*. Frontend and API are separate services deployed on different EC2 fleets. The team wants one load balancer.

Architecture:

  • One ALB with an HTTPS listener on port 443.
  • Listener rule 1: path /api/* → API target group (4 EC2 instances).
  • Listener rule 2: path /images/* → image service target group (2 instances).
  • Default action → frontend target group (4 instances).
  • Each target group has its own health check (e.g., /api/health, /images/health, /).

Why ALB: Only ALB can route by URL path and host header. NLB operates at Layer 4 and cannot inspect HTTP content. Using three separate load balancers would triple cost and DNS complexity.

Exam clue: “Path-based routing,” “route /api and / to different targets,” “single load balancer for multiple services” → ALB with listener rules.

Scenario B — Low-Latency TCP Service With Static IP Requirements

Business requirement: A financial services company exposes a TCP-based trading protocol on port 9000. Partner firms must whitelist specific IP addresses in their firewalls. The service needs ultra-low latency.

Architecture:

  • One NLB with a TCP listener on port 9000.
  • Elastic IP addresses assigned to the NLB in each AZ — partners whitelist these IPs.
  • Target group with EC2 instances running the trading service.
  • Cross-zone load balancing enabled to distribute evenly across AZs.

Why NLB: NLB provides static IPs and Elastic IP support per AZ. ALB uses dynamically changing IP addresses behind a DNS name — unsuitable for firewall whitelisting. NLB also preserves the client source IP and provides lower latency than ALB for non-HTTP protocols.

Exam clue: “Static IP,” “Elastic IP,” “firewall whitelist,” “TCP protocol,” “low latency” → NLB.

Scenario C — Automatically Replace Unhealthy Instances

Business requirement: An application runs 6 EC2 instances behind an ALB across two AZs. If an instance stops responding, it should be removed from traffic immediately and replaced with a new, healthy instance automatically.

Architecture:

  • ALB performs HTTP health checks on each target every 30 seconds.
  • If a target fails 3 consecutive checks, the ALB marks it unhealthy and stops routing traffic to it.
  • The ASG is configured with ELB health checks (not just EC2 status checks).
  • The ASG detects the ELB-unhealthy instance, terminates it, and launches a replacement from the launch template.
  • The new instance is registered with the ALB target group and begins receiving traffic after passing health checks.

Why ELB health checks on the ASG matter: Without this configuration, the ASG uses only EC2 status checks. An instance could have a crashed application (failing ALB health checks) but a healthy EC2 status check — the ASG would never replace it.

Exam clue: “Automatically replace unhealthy instances,” “self-healing” → ASG with ELB health checks enabled.

Scenario D — Traffic Spikes During Business Hours

Business requirement: A SaaS application sees heavy usage from 8 AM to 6 PM on weekdays, with occasional unpredictable spikes during product launches.

Architecture:

  • Scheduled scaling: Increase minimum capacity to 8 instances at 7:30 AM weekdays; decrease to 3 at 7 PM.
  • Target tracking scaling: Maintain ALBRequestCountPerTarget at 1000 requests per target. If requests per target exceed the target, the ASG scales out; if they drop, it scales in.
  • Minimum: 3  |  Desired: varies  |  Maximum: 20.

Why both: Scheduled scaling ensures capacity is ready before the morning rush (no cold-start delay). Target tracking handles unpredictable spikes during the day. Neither alone covers both patterns.

Exam clue: “Predictable daily pattern + unexpected spikes” → scheduled scaling + dynamic scaling combined.

Scenario E — Protect an Application During an AZ Disruption

Business requirement: An application must remain available if one of two AZs fails. Current deployment: 4 instances (2 per AZ) behind an ALB.

Architecture:

  • ALB spans both AZs with cross-zone load balancing.
  • ASG configured across both AZs with minimum: 4, desired: 4, maximum: 8.
  • Target tracking scaling on CPU utilization at 60%.

The problem: If AZ-A fails, only 2 instances remain in AZ-B. Those 2 instances now handle 100% of traffic. If each instance was already at 50% capacity, they are now at 100% — overloaded.

Solution options:

  • Increase minimum to 6 (3 per AZ) so the surviving AZ can absorb full load.
  • Set maximum high enough that the ASG can scale out quickly in AZ-B.
  • Use a scaling metric that triggers before instances become saturated.

Key lesson: Multi-AZ is not resilient if the surviving AZ lacks headroom. The minimum capacity must account for AZ failure scenarios.

Exam clue: “Remain available during AZ failure” with specific instance counts → calculate whether the surviving AZ has enough capacity.

Scenario F — Safely Deploy a New Application Version

Business requirement: A company needs to deploy a new AMI to all instances in an ASG without causing user-visible errors.

Architecture:

  • Create a new launch template version with the updated AMI.
  • Update the ASG to use the new template version.
  • Start an instance refresh with a minimum healthy percentage of 90% and a warm-up period of 120 seconds.
  • The ASG terminates a batch of instances, deregistering them from the ALB with a deregistration delay to drain in-flight requests.
  • New instances launch with the new AMI, pass health checks, and enter the target group.
  • The process repeats until all instances run the new version.

Why this works: The minimum healthy percentage ensures the application retains enough capacity during the rollout. Deregistration delay protects in-flight requests. The warm-up period prevents premature scaling decisions based on new instances.

Exam clue: “Update instances without downtime,” “rolling deployment” → launch template update + instance refresh.

Scenario G — Handle Unpredictable Application Demand

Business requirement: A social media application experiences viral-driven traffic spikes that are impossible to predict. The application must scale to handle 10x normal load within minutes.

Architecture:

  • ASG with target tracking on ALBRequestCountPerTarget — more responsive than CPU for request-driven workloads.
  • Minimum: 4  |  Maximum: 40.
  • Launch template uses a pre-baked AMI with the application already installed (reduces initialization time).
  • Warm-up period set to match actual application startup time.

Limitations to acknowledge:

  • EC2 instances take 2–5 minutes to launch and initialize. Extremely sudden spikes may hit before new capacity arrives.
  • Service quotas (instance limits) must be pre-increased to support 40 instances.
  • The database must also handle the increased connection count — 10x compute without database scaling creates a new bottleneck.

Exam clue: “Unpredictable demand,” “react to traffic spikes” → dynamic scaling with appropriate metric and sufficient maximum capacity.

Scenario I — Gracefully Scale In an Application

Business requirement: Traffic drops at night. The team wants to reduce capacity from 8 to 3 instances without interrupting active user requests.

Architecture:

  • The ASG’s scaling policy reduces desired capacity to 3.
  • The ASG selects 5 instances for termination using the configured termination policy (default: AZ balance, then oldest launch template).
  • Before termination, each instance is deregistered from the ALB target group.
  • The ALB stops sending new requests but allows in-flight requests to complete during the deregistration delay (default 300 seconds).
  • After the delay, connections are closed and the ASG terminates the instance.
  • If lifecycle hooks are configured, the instance enters Terminating:Wait for additional cleanup (push logs, deregister from service discovery).

Key lesson: Deregistration delay is the load balancer’s mechanism. Lifecycle hooks are the ASG’s mechanism. Both contribute to graceful scale-in, but they serve different purposes.

Exam clue: “Scale in without interrupting active requests,” “graceful shutdown” → deregistration delay + lifecycle hooks.

ELB & Auto Scaling Architecture

Key takeaway: The load balancer and Auto Scaling group have separate responsibilities. The ELB distributes traffic and removes unhealthy targets from rotation. The ASG maintains instance count, replaces failed instances, and adjusts capacity based on scaling signals from CloudWatch. Neither service does the other’s job.

22 Exam Gotchas

  1. ALB is not NLB — ALB operates at Layer 7 (HTTP/HTTPS) and can route by path, host, and headers. NLB operates at Layer 4 (TCP/UDP) and routes by port and protocol only. If the scenario mentions “path-based routing” or “host-based routing,” the answer is ALB, not NLB.
  2. NLB is required for static IP and Elastic IP — ALB does not provide static IP addresses. If clients or firewalls must whitelist specific IP addresses, or the scenario mentions “Elastic IP on the load balancer,” the answer is NLB. ALB has dynamically changing IPs behind a DNS name.
  3. ALB is required for HTTP routing — NLB cannot inspect HTTP headers, paths, or host headers. If the scenario requires routing /api to one service and /web to another, NLB cannot do it.
  4. GWLB is not an application load balancer — GWLB is for network appliance fleets (firewalls, IDS/IPS). If the scenario mentions “traffic inspection,” “network appliance,” or “third-party security appliance,” the answer involves GWLB. It does not serve application traffic directly.
  5. ELB does not launch EC2 instances — the load balancer distributes traffic and checks health. It does not create, terminate, or replace instances. That is the Auto Scaling group’s responsibility. An ELB with no healthy targets serves errors; it does not provision replacements.
  6. ASG does not route traffic — the Auto Scaling group manages instance count. It does not receive incoming requests or distribute them. Without a load balancer (or DNS-based routing), clients have no way to reach ASG instances evenly.
  7. ELB health checks ≠ ASG health checks — ELB health checks determine whether to route traffic to a target. ASG health checks determine whether to replace an instance. By default the ASG uses EC2 status checks only. You must explicitly configure the ASG to use ELB health checks so that application-level failures trigger instance replacement.
  8. ASG subnets must span AZs — if the ASG is configured with subnets in only one AZ, all instances launch in that AZ. An AZ failure takes down the entire fleet. Always configure ASG subnets across at least two AZs for production workloads.
  9. Multiple instances across AZs does not guarantee sufficient capacity — if you have 4 instances (2 per AZ) and each runs at 50% capacity, an AZ failure leaves 2 instances at 100%. They cannot absorb additional traffic. The minimum capacity must account for the loss of an AZ.
  10. Minimum ≠ desired ≠ maximum — minimum is the floor, desired is the current target, maximum is the ceiling. Scaling policies change desired. The ASG never goes below minimum or above maximum. Setting all three equal creates a fixed fleet with no scaling.
  11. Maximum capacity is not automatically reached — the ASG only scales to maximum if a scaling policy or manual action requests it. Maximum = 20 does not mean 20 instances are running. Without a trigger, the ASG stays at desired capacity.
  12. CPU is not always the right scaling metric — a web server might have low CPU but be bottlenecked on connections. A data processing service might have high CPU that is normal. The best metric reflects what actually constrains the application: requests per target, queue depth, or a custom metric. The exam sometimes specifies the workload to test metric selection.
  13. Target tracking ≠ step ≠ scheduled ≠ predictive — target tracking maintains a metric target (thermostat). Step scaling uses multiple alarm thresholds. Scheduled scaling changes capacity at set times. Predictive scaling uses ML forecasts. The exam tests whether you match the strategy to the demand pattern.
  14. Scheduled scaling does not handle unexpected traffic — scheduled scaling pre-provisions capacity for known patterns. If an unexpected spike occurs outside the schedule, scheduled scaling alone does nothing. Combine it with dynamic scaling for complete coverage.
  15. Predictive scaling cannot perfectly forecast demand — predictive scaling works best with recurring, cyclical patterns where historical data is reliable. A new application or an unprecedented event has no useful history. The exam may test whether you rely solely on predictive scaling for unpredictable workloads (incorrect).
  16. New instances are not immediately ready — launching an EC2 instance takes minutes. The application then needs to start, load configuration, warm caches, and pass health checks. The time from “scale-out decision” to “instance serving production traffic” is measured in minutes, not seconds. Extremely sudden spikes may hit before new capacity arrives.
  17. Health-check grace period and warm-up matter — without a grace period, the ASG may terminate an instance that simply has not finished starting. Without warm-up, the ASG may make scaling decisions based on a new instance’s unrepresentative metrics. Setting these too short causes launch-terminate cycles. Setting them too long delays failure detection.
  18. Deregistration delay is not the same as termination — deregistration delay is the load balancer’s grace period for in-flight requests (default 300s). The instance is still running during this period. After the delay, the ASG proceeds with termination. Confusing these causes answers that skip connection draining.
  19. Sticky sessions do not solve all state problems — sticky sessions route a user to the same target, but if that target fails, the session is lost. Sticky sessions also create uneven load distribution. Externalizing state (ElastiCache, DynamoDB) is the resilient approach. The exam may offer sticky sessions as a distractor.
  20. Cross-zone load balancing defaults differ by ELB type — ALB enables it by default. NLB, GWLB, and CLB disable it by default. If targets are unevenly distributed across AZs and cross-zone is off, some targets get disproportionate traffic. The exam tests awareness of these defaults, especially for NLB.
  21. Scaling EC2 does not scale the database — adding more application instances increases connections to the database. If the database is the bottleneck, more EC2 instances make it worse. Database scaling (read replicas, caching, connection pooling) must be addressed separately. The exam tests whether you identify the real bottleneck.
  22. Service quotas and capacity limits exist — an ASG cannot launch instances beyond your account’s EC2 service quota. If the maximum is 50 but the account limit is 20, scaling stops at 20. Insufficient capacity in an AZ may also prevent launches. The exam rarely tests specific quota numbers but may present scenarios where scaling fails due to account limits.

Q1. A company serves a web application and a REST API from the same domain. The web application is at / and the API is at /api/*. Each runs on a separate fleet of EC2 instances. The company wants one load balancer to route requests to the correct backend. Which solution meets this requirement?

  • A. Deploy a Network Load Balancer with two target groups. Configure TCP listeners to route /api/* requests to the API target group and all other requests to the web target group.
  • B. Deploy an Application Load Balancer with two target groups. Create a listener rule that routes requests with path /api/* to the API target group. Set the default action to forward to the web target group.
  • C. Deploy a Network Load Balancer and an Application Load Balancer. Use the NLB for the API and the ALB for the web application.
  • D. Deploy two Classic Load Balancers, one for each fleet, and use Route 53 weighted routing to split traffic between them.

Correct Answer: B

ALB operates at Layer 7 and can inspect HTTP request paths. A listener rule matching /api/* forwards API traffic to the API target group, while the default action handles everything else. A (NLB) cannot inspect HTTP paths — it operates at Layer 4 and routes by protocol and port only. C uses two load balancers, which adds cost and DNS complexity when one ALB can handle both. D uses legacy CLBs, which do not support path-based routing or target groups.

Memory rule: Path-based routing = ALB. NLB cannot see URL paths.

Q2. A company runs a web application on EC2 instances behind an Application Load Balancer across two Availability Zones. Instances occasionally stop responding to HTTP requests due to application crashes, but the Auto Scaling group does not replace them. The instances pass EC2 status checks. What should a solutions architect do to ensure unhealthy instances are automatically replaced?

  • A. Increase the number of instances in the Auto Scaling group to compensate for unhealthy instances.
  • B. Configure the Application Load Balancer to terminate and relaunch unhealthy instances directly.
  • C. Configure the Auto Scaling group to use Elastic Load Balancing health checks instead of EC2 status checks only.
  • D. Create a CloudWatch alarm on the UnHealthyHostCount metric and trigger a Lambda function to terminate unhealthy instances.

Correct Answer: C

By default, an ASG uses only EC2 status checks, which verify hardware and system-level health. An application crash that fails the ALB health check does not fail the EC2 status check, so the ASG does not replace the instance. Enabling ELB health checks on the ASG lets it detect instances that fail application-level health checks and replace them automatically. A adds instances but does not fix the unhealthy ones. B is incorrect — ALBs do not launch or terminate instances. D works but is unnecessarily complex when the ASG has a built-in option for this.

Memory rule: ASG default = EC2 status checks only. Enable ELB health checks on the ASG to replace application-level failures.

Q3. A media company experiences a predictable traffic surge every weekday at 9 AM when subscribers check the morning news. The company also sees occasional unpredictable spikes when breaking news events occur. The Auto Scaling group must have capacity ready before the 9 AM surge and react to unexpected spikes. Which scaling configuration meets both requirements?

  • A. Use predictive scaling as the only scaling policy. It will learn the 9 AM pattern and react to breaking news events based on historical data.
  • B. Use scheduled scaling to increase capacity at 8:30 AM on weekdays. Add a target tracking scaling policy on ALBRequestCountPerTarget to handle unexpected demand.
  • C. Use target tracking scaling on CPU utilization as the only scaling policy. Set the target to 40% to leave headroom for spikes.
  • D. Set the Auto Scaling group minimum capacity to the peak level for the entire day so instances are always ready.

Correct Answer: B

Scheduled scaling ensures capacity is pre-provisioned before the predictable 9 AM rush, eliminating the delay of reactive scaling. Target tracking on ALBRequestCountPerTarget handles unpredictable breaking-news spikes by adjusting capacity based on actual request load. A relies solely on predictive scaling, which cannot anticipate unprecedented breaking news events — it forecasts from history, not from real-time signals. C uses only reactive scaling, which means the 9 AM surge hits before capacity scales out. D wastes resources by running peak capacity 24/7 instead of scaling to match demand.

Memory rule: Known pattern = scheduled scaling. Unknown spikes = dynamic scaling. Best practice combines both.

Amazon RDS Multi-AZ & Read Replicas

How architects design database layers for high availability, read scaling, and disaster recovery using Amazon RDS.

Learn from Zero

Part 1A — Relational Database Fundamentals

What is a database? A database is an organized system for storing, retrieving, and managing data. Applications need databases because they cannot hold everything in memory — data must survive restarts, be shared among application servers, and support complex queries.

What is a relational database? A relational database organizes data into tables. Each table has columns (fields) and rows (records). A primary key uniquely identifies each row. Relationships between tables use foreign keys. You interact with the data using SQL (Structured Query Language).

Example: Online Shopping Application

An online store uses three tables:

  • Customers — customer_id (primary key), name, email.
  • Orders — order_id (primary key), customer_id (foreign key), total, status.
  • Payments — payment_id (primary key), order_id (foreign key), amount, method.

When a customer places an order, the application writes to Orders and Payments. When the customer views order history, the application reads from Orders. The database must remain available for both operations. If the database goes down, customers cannot place orders or check their status.

This store serves 80% reads (browsing products, checking orders) and 20% writes (placing orders, processing payments). This read-heavy pattern is common and influences database architecture decisions.

A database instance is a running copy of the database software on a server, with allocated CPU, memory, storage, and network. A database engine (MySQL, PostgreSQL, Oracle, SQL Server, MariaDB) is the software that manages data; a database instance is that engine running on specific hardware.

Why databases become bottlenecks. Application servers can scale horizontally (add more EC2 instances behind a load balancer), but the database often cannot be duplicated as easily. All application instances write to the same primary database. If the database runs out of CPU, connections, or storage, every application instance is affected — even if the application tier has plenty of capacity.

Protecting a database involves more than launching a second server:

  • Connections — each application instance opens database connections; too many connections exhaust database resources.
  • Storage — the database needs reliable, durable storage that does not lose data.
  • Backups — a copy of the data at a point in time, for recovery after corruption or accidental deletion.
  • Replication — copying data to another database instance for availability or read scaling.
  • Failover — switching to a backup instance when the primary fails.

Part 1B — Amazon RDS Fundamentals

Amazon Relational Database Service (RDS) is a managed service that makes it easier to set up, operate, and scale relational databases in the cloud. RDS handles hardware provisioning, database setup, patching, backups, and infrastructure management.

Supported engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Amazon Aurora (a cloud-native engine compatible with MySQL and PostgreSQL).

What AWS manages vs. what you manage:

AWS managesYou manage
Hardware provisioning and maintenanceDatabase schema and queries
Database engine installation and patchingApplication connection logic and retry behavior
Automated backupsSecurity configuration (security groups, IAM, encryption)
Storage management and scalingPerformance tuning and indexing

RDS vs. database on EC2. Running a database on EC2 gives you full OS-level access but requires you to manage everything: installation, patching, backups, replication, failover, and monitoring. RDS trades some control for significantly less operational burden. Most production workloads on the SAA-C03 exam use RDS or Aurora.

Key RDS concepts:

  • DB instance — the database environment running in the cloud (compute + memory + storage).
  • DB endpoint — a DNS address that applications use to connect. This endpoint does not change during failover, allowing applications to reconnect to the new primary.
  • DB subnet group — a collection of subnets (typically across multiple AZs) where RDS can place DB instances. Spanning AZs enables Multi-AZ deployments.
  • Security groups — control network access to the DB instance. Only allow connections from authorized sources (application servers, specific CIDR blocks).
  • Automated backups — RDS automatically takes daily snapshots and captures transaction logs, enabling point-in-time recovery within the retention period (up to 35 days).
  • DB snapshots — manual, user-initiated backups that persist until explicitly deleted.

A database should generally not be publicly accessible. Placing an RDS instance in a private subnet with no public IP and restricting security groups to only your application servers is standard practice. Public accessibility exposes the database to the internet and should only be used when the requirements explicitly justify it.

Applications must handle connection interruptions. Even with RDS managing failover, active TCP connections are dropped during a failover event. Applications need connection-retry logic, connection pooling with health checks, and error handling for transient database unavailability.

Part 1C — High Availability and RDS Multi-AZ

Why a single database instance is a risk. If the database instance runs in one AZ and that AZ experiences a disruption, the database is unavailable until the AZ recovers or you manually restore from a backup. For production applications, this downtime is unacceptable.

RDS Multi-AZ solves this by maintaining a copy of the database in another AZ. If the primary fails, RDS automatically fails over to the copy. The application connects through a stable DB endpoint (a DNS name) that points to whichever instance is currently the primary. After failover, the DNS record updates, and applications reconnect to the new primary.

How automatic failover works (conceptually):

  1. RDS detects that the primary DB instance is unhealthy (AZ failure, instance failure, storage failure).
  2. RDS promotes the standby to primary.
  3. The DB endpoint’s DNS record is updated to point to the new primary.
  4. Applications using the endpoint reconnect to the new primary.

Why failover still interrupts connections. Active database connections to the old primary are dropped. The DNS update takes a short time to propagate. Applications must detect the closed connection, resolve the endpoint again, and reconnect. Without proper retry logic, users may see brief errors.

Multi-AZ improves availability within a Region but:

  • It does not protect against a Region-wide disaster (all AZs in a Region affected).
  • It does not automatically scale read throughput (in the traditional DB instance deployment).
  • It does not protect against accidental data deletion — a DELETE command replicates to the standby too.

Part 1D — RDS Multi-AZ DB Instance vs Multi-AZ DB Cluster

This distinction is a frequent source of exam confusion. AWS offers two different Multi-AZ deployment models for RDS, and they have different architectures and capabilities.

Multi-AZ DB Instance Deployment (Traditional)

This is the original, widely available Multi-AZ architecture:

  • One primary DB instance handles all reads and writes.
  • One standby DB instance in a different AZ receives synchronous replication from the primary.
  • The standby does not serve read traffic — it exists solely for failover.
  • Applications connect through a single DB instance endpoint.
  • If the primary fails, RDS promotes the standby to primary and updates the endpoint. Typical failover takes 60–120 seconds.
  • Supported by all RDS engines (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server).

Key point: The traditional standby is not a read replica. It cannot be queried. It only becomes active when the primary fails.

Multi-AZ DB Cluster Deployment

This is a newer architecture with a different topology:

  • One writer DB instance handles all write operations.
  • Two reader DB instances in two other AZs — three instances across three AZs total.
  • The reader instances can serve read traffic via a reader endpoint, providing both HA and some read scaling.
  • Uses semisynchronous replication — a write is acknowledged after at least one reader confirms receipt, providing a balance of durability and performance.
  • Three endpoints: cluster endpoint (writes → writer), reader endpoint (reads → readers), and individual instance endpoints.
  • Faster failover — typically around 35 seconds.
  • Currently supported for MySQL 8.0.28+ and PostgreSQL 13.4+ (not all engines or all Regions).

Part 1E — RDS Read Replicas

What is a read replica? A read replica is a separate, read-only copy of the primary database. The primary streams changes to the replica using asynchronous replication. Applications can direct read queries to the replica to reduce load on the primary.

Why use read replicas?

  • Offload read-heavy workloads (reports, dashboards, search) from the primary.
  • Allow the primary to focus on write operations.
  • Scale read throughput by adding multiple replicas.

How it works:

  1. The primary database processes writes and streams changes to replicas asynchronously.
  2. Each replica has its own endpoint. Applications direct suitable read queries to replica endpoints.
  3. Writes always go to the primary — replicas are read-only.

Replication lag. Because replication is asynchronous, the replica may be seconds or more behind the primary. A query on the replica immediately after a write to the primary may return stale data. This is called replication lag, and it means replicas provide eventual consistency, not immediate consistency.

Read replicas are not Multi-AZ standby instances. These are fundamentally different mechanisms:

Read replica promotion. A read replica can be promoted to a standalone primary database. This is a manual operation (not automatic failover) and breaks the replication link. After promotion, the replica becomes an independent read-write database. Promotion is sometimes used in disaster recovery but requires application reconfiguration to point to the new endpoint.

Replica limits: Up to 5 read replicas per primary for standard RDS engines (MySQL, PostgreSQL, MariaDB). Aurora supports up to 15 replicas with integrated reader endpoints and automatic failover.

Part 1F — Cross-Region Read Replicas and Disaster Recovery

A cross-Region read replica is a read replica in a different AWS Region than the primary. It serves two purposes: read scaling in the remote Region and a potential recovery target if the primary Region becomes unavailable.

How cross-Region replication works:

  • The primary streams changes to the remote replica asynchronously.
  • Cross-Region network latency means replication lag is typically higher than same-Region replicas.
  • The actual RPO equals the replication lag at the moment of failure — any data committed but not yet replicated is lost.

Promotion for disaster recovery:

  1. The primary Region becomes unavailable.
  2. An operator promotes the cross-Region read replica to a standalone primary.
  3. Applications must be reconfigured (or DNS must be updated) to point to the promoted database in the new Region.
  4. The promoted database is now independent — it has no replication link back to the original.

Why a cross-Region replica is not a complete DR solution by itself:

  • Promotion is manual, not automatic — an operator must initiate it.
  • Applications in the DR Region need to be running and configured (compute, secrets, networking, permissions).
  • DNS or traffic routing must redirect clients to the new Region.
  • Replication lag means some recent data may be lost.
  • The full application stack (not just the database) must be recoverable.

Part 1G — Replication Lag and Read/Write Patterns

Not all reads are the same. The decision to route a query to a replica depends on whether the application can tolerate stale data.

Read-after-write consistency. When an application writes data and immediately reads it back, it needs read-after-write consistency. This means the read must return the data that was just written. Asynchronous replicas cannot guarantee this. The safe pattern is: write to the primary, read critical confirmations from the primary, route everything else to replicas.

Monitoring replication lag. CloudWatch provides the ReplicaLag metric. If lag increases, it may indicate that the primary is generating changes faster than the replica can apply them, or that network throughput is limited. Persistent high lag means the replica’s data is increasingly stale.

More replicas do not always improve performance. If the bottleneck is storage I/O, query design, connection limits, or the primary’s write capacity, adding read replicas will not help. Each replica adds replication overhead to the primary. Diagnose the actual bottleneck before adding replicas.

When Real Architects Actually Use This

Scenario A — Production Database Must Survive an AZ Failure

Business requirement: An order-processing application uses an RDS MySQL database. If the primary’s AZ fails, the database must fail over automatically with minimal data loss.

Architecture:

  • Enable RDS Multi-AZ DB instance deployment.
  • RDS creates a synchronous standby in a second AZ.
  • The application connects through the DB instance endpoint.
  • If the primary’s AZ fails, RDS promotes the standby in 60–120 seconds and updates the endpoint’s DNS.
  • The application detects the dropped connection, re-resolves the endpoint, and reconnects to the new primary.

Why Multi-AZ: Synchronous replication means the standby is always current — near-zero data loss. Failover is automatic with no operator intervention. Read replicas use asynchronous replication and require manual promotion, making them unsuitable as the primary HA mechanism.

Application responsibility: The application must implement connection retry logic. Active transactions are interrupted during failover. Without retry handling, users see errors even though the database recovers quickly.

Exam clue: “Automatic failover,” “survive AZ failure,” “high availability for the database” → RDS Multi-AZ.

Scenario B — Read-Heavy Reporting Workload

Business requirement: A business intelligence team runs daily reports against the production MySQL database. Report queries are slow, complex aggregations that consume significant CPU and I/O, degrading the experience for customers using the application.

Architecture:

  • Create one or more RDS read replicas.
  • Configure the reporting application to connect to the replica endpoint.
  • The primary handles all writes and real-time application reads.
  • Reports can tolerate data that is seconds old — asynchronous lag is acceptable.

Why read replicas: Offloads expensive read queries from the primary. The primary’s CPU and I/O remain available for the customer-facing application. A Multi-AZ standby cannot serve read traffic (traditional deployment), so it does not solve this problem.

Watch for: Monitor ReplicaLag in CloudWatch. If lag grows, the replica may be undersized or the primary is generating changes faster than the replica can apply.

Exam clue: “Offload read traffic,” “reporting workload impacts production,” “read scaling” → RDS read replicas.

Scenario C — Strong Read-After-Write Requirement

Business requirement: After a customer places an order, the application immediately displays the order confirmation with its status. The customer must see the order they just placed.

Architecture:

  • Write the order to the primary database.
  • Read the order confirmation from the primary database (not a replica).
  • Route other reads (product browsing, order history) to read replicas where lag is acceptable.

Why not use a replica for this read? Asynchronous replication means the replica may be seconds behind the primary. If the application reads from the replica immediately after writing, the order may not exist yet on the replica. The customer sees “no order found” — a confusing and incorrect experience.

Design principle: Route critical, consistency-sensitive reads to the primary. Route everything else to replicas. The application must know which reads require consistency.

Exam clue: “Must see the data just written,” “read-after-write consistency” → read from primary, not replica.

Scenario D — Regional Disaster Recovery

Business requirement: A company needs to recover its production database in another Region if the primary Region becomes completely unavailable. RTO: 1 hour. RPO: 5 minutes.

Architecture:

  • Create a cross-Region read replica in the DR Region.
  • The replica continuously receives asynchronous updates from the primary.
  • If the primary Region fails, promote the cross-Region replica to a standalone primary (manual action).
  • Update DNS (Route 53) to point the application to the DR Region’s database endpoint.
  • Ensure application servers, secrets, and networking are pre-staged in the DR Region (Topic 9 warm standby).
  • Also maintain automated backups with cross-Region replication for point-in-time recovery if the replica itself has data corruption.

RPO consideration: The actual RPO = replication lag at the time of failure. If the replica is typically <1 second behind, RPO is well within 5 minutes. But network issues could increase lag, so monitor ReplicaLag continuously.

Why not Multi-AZ alone? Multi-AZ protects within a Region only. A Regional outage affects all AZs, including the standby.

Exam clue: “Recover in another Region,” “Regional disaster recovery,” “RPO of minutes” → cross-Region read replica + backup strategy.

Scenario E — Read Workload Needs Additional Capacity

Business requirement: A product search feature generates thousands of read queries per second. The primary database’s CPU is at 85% and response times are increasing.

Architecture:

  • Create 2–3 read replicas and route product search queries to them.
  • Writes (new products, inventory updates) continue to the primary.
  • Product data changes infrequently — seconds of replica lag is invisible to shoppers.

Why not just scale up the primary? Scaling up (larger instance) has an upper limit and requires a restart. Read replicas allow horizontal read scaling without affecting the primary’s availability.

Important caveat: Adding replicas does not help if the bottleneck is write throughput, storage I/O, or poor query design. If all queries do full table scans, more replicas just do more full table scans. Fix the query and indexing first.

Exam clue: “Read-heavy,” “high CPU on primary due to read queries,” “offload reads” → read replicas.

Scenario F — Automatic Database Failover and Stale Connections

Business requirement: After an RDS Multi-AZ failover, the application returns database connection errors for several minutes even though the database is operational again.

Root cause:

  • During failover, all existing TCP connections to the old primary are dropped.
  • The DB endpoint’s DNS record updates to point to the new primary.
  • The application’s connection pool holds stale connections to the old IP address.
  • DNS caching in the application, JVM, or OS delays resolution of the new IP.

Solution:

  • Use connection pooling with health checks that validate connections before use.
  • Set the JVM’s TTL for DNS entries to a short value (e.g., 60 seconds or less).
  • Implement connection retry logic with backoff in the application.
  • Test failover behavior in a staging environment before production.

Key lesson: A stable endpoint does not mean connections survive failover. The endpoint’s DNS updates, but existing connections are broken. The application must detect and recover.

Exam clue: “Connection errors after failover,” “application not reconnecting” → connection handling, DNS caching, retry logic.

Business requirement: A company runs PostgreSQL 15 on RDS. It needs automatic failover and wants the standby to handle some read queries to reduce primary load.

Scenario H — Accidental Data Deletion or Corruption

Business requirement: A developer accidentally runs DELETE FROM orders WHERE status = 'pending' in production, deleting thousands of valid orders. The database has Multi-AZ enabled.

Why Multi-AZ does not help: The DELETE statement is a valid write operation. It replicates synchronously to the standby. Both the primary and standby now have the deleted data. Multi-AZ protects against infrastructure failure, not logical data corruption.

Recovery:

  • Use point-in-time recovery (PITR) to restore the database to a moment just before the accidental DELETE was executed.
  • PITR creates a new DB instance with data as of the chosen timestamp.
  • The application must be reconfigured to use the restored instance (or data migrated back).
  • Automated backups must be enabled with sufficient retention (up to 35 days).

Why read replicas also do not help: The DELETE replicates to read replicas too (they are asynchronous but still replicate all changes). The only difference is timing — if you catch the error within seconds, the replica might not have applied it yet, but this is not a reliable recovery strategy.

Key lesson: Replication (Multi-AZ and replicas) protects against infrastructure failure. Backups and PITR protect against data corruption and human error. Both are needed.

Exam clue: “Accidental deletion,” “data corruption,” “recover to a specific time” → automated backups + point-in-time recovery.

Key takeaway: The traditional Multi-AZ DB instance deployment (top left) provides high availability with a non-readable standby. Read replicas (top right) provide read scaling with asynchronous replication and possible lag. The Multi-AZ DB cluster (bottom) combines both: HA failover with readable standby instances across three AZs, but is limited to MySQL 8.0+ and PostgreSQL 13.4+. 20 Exam Gotchas

  1. A traditional Multi-AZ standby is not a read replica — the standby in a Multi-AZ DB instance deployment exists solely for failover. It does not serve read traffic. If the scenario needs read scaling, Multi-AZ alone is the wrong answer.
  2. A traditional Multi-AZ standby cannot serve read queries — even if you want to offload reads, the standby is not accessible for queries. You need read replicas (or a Multi-AZ DB cluster with readable standby instances) for read scaling.
  3. A read replica does not auto-failover like Multi-AZ — read replicas use asynchronous replication and require manual promotion. If the exam asks for “automatic failover,” the answer is Multi-AZ, not read replicas.
  4. Not all Multi-AZ deployments have two instances — the Multi-AZ DB cluster has 1 writer + 2 readers = 3 instances across 3 AZs. The traditional deployment has 1 primary + 1 standby = 2 instances. Read the scenario carefully to determine which architecture is described.
  5. Multi-AZ DB instance ≠ Multi-AZ DB cluster — the DB instance deployment has a non-readable standby. The DB cluster has readable standby instances and faster failover (~35s vs. 60–120s). These are different architectures with different capabilities.
  6. Multi-AZ DB cluster readers ARE readable — unlike the traditional standby, the two reader instances in a DB cluster can serve read queries via the reader endpoint. If the scenario mentions “readable standby in a Multi-AZ deployment,” it describes the DB cluster model.
  7. Not all engines support the Multi-AZ DB cluster — as of current documentation, only MySQL 8.0+ and PostgreSQL 13.4+ support the DB cluster deployment. Oracle, SQL Server, and MariaDB do not. Always check engine compatibility.
  8. Read replicas have replication lag — asynchronous replication means the replica may be seconds or more behind the primary. The exam uses lag to distinguish when replicas are suitable (analytics) versus when they are not (read-after-write for checkout).
  9. Reading immediately after writing may return stale data from a replica — if the application writes an order and immediately reads from a replica, the order may not exist on the replica yet. Read-after-write consistency requires reading from the primary.
  10. Read replicas do not replace Multi-AZ for HA — if the requirement is “automatic failover when the primary fails,” read replicas are wrong. They require manual promotion. Multi-AZ provides automatic failover.
  11. Multi-AZ alone does not solve read-throughput problems — the standby is not readable (traditional deployment). If the primary is overloaded with read queries, adding Multi-AZ does nothing for performance. Add read replicas instead.
  12. RDS failover drops active connections — during a Multi-AZ failover, existing TCP connections to the old primary are terminated. Applications must detect the drop, resolve the endpoint DNS again, and reconnect. Without retry logic, users see errors even after the database is available.
  13. A stable DB endpoint does not preserve connections — the endpoint DNS updates to point to the new primary, but existing TCP connections are broken. The endpoint provides a stable address for reconnection, not connection continuity.
  14. Cross-Region replication is not the same as same-Region Multi-AZ — Multi-AZ protects within one Region (AZ-level failure). Cross-Region read replicas address Regional DR. A Regional outage affects all AZs in that Region, including the Multi-AZ standby.
  15. A cross-Region read replica is not a complete DR solution — the replica handles database replication, but the application also needs compute, secrets, networking, and DNS changes in the DR Region. Promoting the replica does not automatically restore the full application.
  16. Backups, Multi-AZ standby, and read replicas are not interchangeable — Multi-AZ = automatic HA failover. Read replicas = read scaling. Backups = recovery from corruption/deletion. Using one when you need another is the most common exam trap in this topic.
  17. Replication does not protect against accidental deletion — a DELETE or DROP TABLE replicates to both the standby and all read replicas. Multi-AZ and read replicas both contain the corrupted data. Point-in-time recovery (from backups) is the correct recovery mechanism.
  18. Replication lag affects RPO during disaster recovery — if a cross-Region replica is 30 seconds behind and the primary Region fails, those 30 seconds of transactions are lost. RPO = replication lag at the time of failure, not zero.
  19. More replicas do not always improve performance — if the bottleneck is write throughput, storage I/O, query design, or connection limits, adding read replicas will not help. Each replica also adds replication overhead to the primary.
  20. The application must route reads and writes correctly — adding read replicas does nothing if the application sends all queries to the primary. The application must be modified to direct appropriate reads to replica endpoints and writes to the primary endpoint.

Q1. A company runs a critical order-processing application backed by an Amazon RDS MySQL database in a single Availability Zone. If the database becomes unavailable due to an AZ failure, orders cannot be processed. The company needs automatic database failover with minimal data loss. Which solution meets this requirement?

  • A. Create a read replica in another AZ. If the primary fails, promote the read replica to a standalone primary.

Correct Answer: B

C (snapshots) restores to a new instance, which takes significant time and loses data since the last snapshot. D requires custom application logic for failover, which is error-prone and not managed by AWS.

Memory rule: “Automatic failover + minimal data loss” = Multi-AZ. Read replicas are for read scaling, not automatic HA.

Q2. A company’s RDS PostgreSQL database handles both customer-facing transactions and reporting queries.   • D. Create a cross-Region read replica and direct reporting queries to the remote Region.

A read replica offloads reporting queries from the primary. Asynchronous replication means the replica may lag by seconds, which the reporting team can tolerate. 1A — DynamoDB Fundamentals

Amazon DynamoDB is a fully managed NoSQL database service provided by AWS. Unlike traditional relational databases (such as MySQL or PostgreSQL) that store data in tables with fixed columns and rows, DynamoDB is a key-value and document-oriented database. It stores data as items (similar to rows) composed of attributes (similar to columns), but each item can have a different set of attributes.

Core Concepts

  • Table — A collection of items. Every DynamoDB table has a name and a primary key.
  • Item — A single record in a table. Think of it like a JSON object.
  • Attribute — A named data element within an item. Items in the same table can have completely different attributes (except for the primary key, which every item must include).

Example: E-Commerce Application

In a relational database, a customer order might require a JOIN across Customers, Orders, and Products tables. In DynamoDB, you design the table around how your application accesses data. A single table could store both customer information and their orders by using a well-designed primary key.

Key principle: In DynamoDB, you design your data model around the access patterns your application needs — the queries it will run. This is the opposite of relational design, where you model the data first and write queries later. You cannot efficiently scan every attribute the way a relational database can with SQL.

Low-latency access means DynamoDB can return data in single-digit milliseconds because it uses the primary key to locate items directly, without scanning the entire dataset. This is essential for applications that need fast, predictable performance at scale.

1B — Primary Keys, Partition Keys & Sort Keys

Every DynamoDB table must have a primary key that uniquely identifies each item. DynamoDB offers two primary-key types:

Partition Key (Simple Primary Key)

A partition key (also called a hash key) is a single attribute whose value DynamoDB uses to determine which internal partition stores the item. When a table uses only a partition key, each partition-key value must be unique — it alone identifies the item.

DynamoDB hashes the partition-key value to determine which physical partition stores the data. This is why key distribution matters: if too many requests target the same partition-key value, that partition becomes a hot partition (or hot key), causing throttling or reduced performance.

Hot key example: If you use Country as a partition key and 80% of users are in “US”, that single partition handles 80% of all traffic — a classic hot-key problem. Choose keys with high cardinality and even traffic distribution, such as CustomerId or OrderId.

Composite Primary Key (Partition Key + Sort Key)

A composite primary key consists of a partition key plus a sort key (also called a range key). Multiple items can share the same partition key as long as their sort keys differ. The combination of partition key + sort key must be unique.

Items with the same partition key form an item collection and are stored together. The sort key determines their order, enabling range-based queries and efficient retrieval of related items.

Sort Key Access Patterns

Sort keys support:

  • Exact match — SK = "ORDER#2026-001"
  • Range queries — SK BETWEEN "ORDER#2026-001" AND "ORDER#2026-012"
  • Begins-with — SK begins_with("ORDER#2026") to get all 2026 orders

1C — Access Patterns & Query Design

DynamoDB provides three main ways to read data:

OperationWhat It DoesCapacity Impact
GetItemRetrieves a single item by its full primary keyMinimal — reads exactly one item
QueryRetrieves items sharing a partition key, with optional sort-key conditionsReads only the matching items in the partition
ScanReads every item in the table (or index), optionally filtering resultsReads the entire table — expensive for large datasets

Key Conditions vs Filters

A key condition restricts which items DynamoDB reads from storage — it targets a specific partition and optionally a sort-key range. A filter expression removes items from the results after they have already been read. Filters do not reduce the read capacity consumed.

Exam trap: A filter on a Scan does not make it efficient. DynamoDB still reads the entire table; the filter just hides items from the response. The read capacity is consumed for every item evaluated, not just the items returned.

When Is a Scan Acceptable?

Scans are not inherently wrong. They may be appropriate for:

  • Small reference tables (hundreds of items)
  • Administrative or batch operations during off-peak hours
  • One-time data exports or migrations

For large production tables serving customer-facing traffic, scans should be avoided in favor of key-based Queries.

Modeling Relationships

Denormalization — Instead of JOINing separate tables, DynamoDB encourages storing related data together. A composite sort key like ORDER#2026-001 alongside PROFILE# lets one Query retrieve a customer’s profile and orders from the same partition.

Single-table design stores multiple entity types (customers, orders, products) in one table using generic key names (PK, SK). This can reduce the number of requests but adds complexity. Separate tables may be simpler when entities have completely independent access patterns.

Access-pattern example: “Find all orders for Customer #123” uses a Query on PK = CUSTOMER#123. But “Find all orders with status = Shipped” cannot use the table’s primary key if Status is not part of it. This is where secondary indexes come in.

1D — Secondary Index Fundamentals

A secondary index is an additional data structure that DynamoDB maintains alongside your base table. It allows you to query data using a different key than the table’s primary key.

Why Indexes?

If your table’s primary key is CustomerId + OrderId, you can efficiently query by customer. But if you also need to query by OrderStatus, the primary key cannot help. A secondary index with OrderStatus as its key enables that query.

Projected Attributes

When creating an index, you choose which attributes to project (copy) into it:

ProjectionWhat’s CopiedTrade-off
KEYS_ONLYOnly the index key and table key attributesSmallest storage; must fetch other attributes from the base table
INCLUDEKey attributes plus specified additional attributesBalanced; covers common query fields
ALLAll attributes from the base tableLargest storage; no need to fetch from base table
Indexes are not free. Every index consumes additional storage and write capacity — when you write to the base table, DynamoDB also updates every affected index. A secondary index is not a universal replacement for good primary-key design.

DynamoDB provides two types of secondary indexes:

  1. Global Secondary Index (GSI) — Can use a completely different partition key and sort key.
  2. Local Secondary Index (LSI) — Shares the base table’s partition key but uses a different sort key.

1E — Global Secondary Index (GSI)

A Global Secondary Index creates a separate view of your data with a different partition key (and optionally a different sort key) than the base table. “Global” means the index spans the entire table, not just a single partition.

Key Properties

  • Different partition key — The GSI partition key can be any table attribute, enabling query patterns the base table cannot support.
  • Eventually consistent only — GSI data is replicated asynchronously from the base table. GSI queries never support strongly consistent reads.
  • Can be added after table creation — Unlike LSIs, you can create GSIs on existing tables (subject to account limits).
  • Separate capacity — In provisioned mode, each GSI has its own read and write capacity settings. In on-demand mode, the GSI capacity scales with usage.
  • Default limit: 20 GSIs per table.

GSI Example

Base table primary key: CustomerId (PK) + OrderId (SK)

Access pattern needed: “Find all orders with status = Shipped”

GSI design:

  • GSI partition key: OrderStatus
  • GSI sort key: OrderDate
  • Projection: INCLUDE (OrderTotal, CustomerId)

Now you can query: OrderStatus = "Shipped" with OrderDate range conditions.

GSI hot-key risk: If your GSI partition key is OrderStatus and 90% of orders are “Completed”, that status value becomes a hot key on the GSI. The same distribution principles that apply to the base table also apply to every GSI.

GSI Backfill

When you create a GSI on an existing table, DynamoDB backfills the index with existing data. This consumes write capacity and can take time for large tables. Plan index creation during low-traffic periods.

1F — Local Secondary Index (LSI)

A Local Secondary Index provides an alternative sort key for the same partition key as the base table. “Local” means the index is scoped to items sharing a partition-key value.

Key Properties

  • Same partition key as the base table — You cannot use a different partition key.
  • Different sort key — Enables alternative ordering or range queries within a partition.
  • Must be defined at table creation — You cannot add an LSI to an existing table.
  • Supports strongly consistent reads — Unlike GSIs, LSI queries can be strongly consistent.
  • 10 GB item collection limit — All items sharing a partition key (including base table and LSI data) must fit within 10 GB.
  • Default limit: 5 LSIs per table.

LSI Example

Base table: CustomerId (PK) + OrderDate (SK)

LSI: Same PK (CustomerId) + Alternative SK (OrderTotal)

Now you can query a customer’s orders sorted by total amount instead of date — but only within that customer’s partition.

10 GB limit: If a customer accumulates enough orders that the item collection exceeds 10 GB, writes to that partition will be rejected. Monitor item collection sizes for tables with LSIs, especially if data grows unboundedly.

1H — Read/Write Capacity Modes

DynamoDB offers two capacity modes that control how you pay for and manage read/write throughput:

Provisioned Capacity Mode

You specify the number of reads and writes per second your table needs:

  • Read Capacity Unit (RCU) — One RCU provides one strongly consistent read per second (or two eventually consistent reads) for an item up to 4 KB.
  • Write Capacity Unit (WCU) — One WCU provides one write per second for an item up to 1 KB.

Provisioned Capacity Example

Assuming items are ≤ 4 KB and using strongly consistent reads:

  • 100 reads/second → 100 RCUs
  • 100 eventually consistent reads/second → 50 RCUs (half the cost)

Note: Larger items, transactional reads/writes, and batch operations have different capacity calculations. These examples assume the simplest case.

Auto Scaling adjusts provisioned capacity automatically based on actual usage, within minimum and maximum bounds you define. It reacts to traffic changes but may not respond instantly to sudden spikes.

Throttling occurs when requests exceed provisioned capacity. Throttled requests receive an error and must be retried. In provisioned mode, each GSI also has its own capacity — a GSI can be throttled independently of the base table.

On-Demand Capacity Mode

DynamoDB automatically handles capacity scaling. You pay per request instead of provisioning throughput in advance.

  • No need to estimate or manage RCUs/WCUs.
  • Scales to accommodate workload changes automatically.
  • Charges are based on actual read and write request units consumed.
  • Well-suited for new applications, unpredictable traffic, or workloads with large usage spikes.
On-demand is not unlimited. DynamoDB on-demand tables still have account and table-level throughput quotas. If traffic increases beyond what the table has recently handled, DynamoDB may need time to scale (it doubles the previous peak traffic automatically). Extremely sudden spikes from zero can still encounter throttling. Switching between modes is allowed but limited to once every 24 hours.

Critical exam fact: GSI queries are always eventually consistent. If a scenario requires strongly consistent reads through an index, the only option is an LSI (which shares the base table’s partition key). If neither the base table nor an LSI fits, you must read directly from the base table.

Hot Keys and Throttling

A hot partition key means a disproportionate share of requests targets a small number of partition-key values. This overloads specific partitions while others sit idle.

Adaptive capacity — DynamoDB can automatically redistribute some capacity to hot partitions, helping absorb short bursts. However, adaptive capacity is not a fix for fundamentally poor key design. If one key value receives sustained heavy traffic, the solution is to redesign the key for better distribution.

Diagnosis checklist when throttling occurs:

  1. Check if the table or GSI has sufficient provisioned capacity (or is on on-demand mode).
  2. Check partition-key distribution — are a few keys receiving most traffic?
  3. Check if a GSI is the bottleneck (GSI throttling can back-pressure writes to the base table).
  4. Check if the access pattern causes full-table scans instead of targeted queries.
  5. Simply switching from provisioned to on-demand does not fix a hot-key problem — the hot partition is still hot.

Data Modeling Principles

  • Choose partition keys with high cardinality — UserId, OrderId, DeviceId; avoid low-cardinality keys like Status or Country.
  • Use composite sort keys to model one-to-many relationships (e.g., ORDER#date).
  • Select the right index — GSI for new partition-key patterns; LSI for alternative sort orders.
  • Manage index overhead — Every write to the base table also writes to affected indexes.
  • Prefer Query over Scan for production workloads — design keys so your critical queries use targeted lookups.

When Real Architects Actually Use This

Scenario A — Retrieve a Customer’s Orders

Requirement: An e-commerce company stores orders in DynamoDB. The application must retrieve all orders belonging to a customer, sorted by order date.

Design: Use a composite primary key with CustomerId as the partition key and OrderDate as the sort key. A Query on PK = CUSTOMER#123 returns all orders for that customer, already sorted by date.

Why this works: Items sharing a partition key are stored together and sorted by the sort key. The Query operation reads only that customer’s item collection — no scan required.

Trade-offs: This key design cannot directly support queries like “all orders with status = Shipped” without a secondary index. The design optimizes for the primary access pattern.

Exam clue: “Retrieve all related items for one entity, sorted by date/time” → composite primary key with the entity as PK and timestamp-based SK.

Scenario B — Query Orders by Status

Requirement: The same company needs to find all orders with a particular status (e.g., “Pending”) across all customers.

Design: Create a GSI with OrderStatus as the partition key and OrderDate as the sort key. Project CustomerId and OrderTotal using INCLUDE projection.

Why this works: The GSI provides a completely different partition key, enabling cross-customer queries by status. The base table’s primary key (CustomerId + OrderDate) cannot support this pattern.

Trade-offs: GSI queries are eventually consistent. If OrderStatus has low cardinality (few distinct values) and one status dominates traffic, the GSI can develop hot partitions. The GSI consumes additional storage and write capacity.

Why not LSI: An LSI cannot change the partition key — it would still query within one customer’s partition, not across all customers.

Exam clue: “Query by a different attribute across all items” + “different partition key needed” → GSI.

Scenario C — Alternative Sort Order Within a Customer

Requirement: A company wants to retrieve a customer’s orders sorted by total amount rather than order date, with strongly consistent reads.

Design: Define an LSI at table creation with the same partition key (CustomerId) and OrderTotal as the alternative sort key.

Why this works: The LSI provides alternative ordering within the same partition. Because it shares the base table’s partition key, it supports strongly consistent reads.

Trade-offs: The LSI must be defined at table creation. The 10 GB item collection size limit applies. If the customer accumulates too many orders, writes to that partition will fail.

Why not GSI: A GSI could technically achieve this, but it would not support strongly consistent reads. If strong consistency is required and the partition key stays the same, the LSI is the better choice.

Exam clue: “Same partition key” + “different sort order” + “strongly consistent” → LSI.

Scenario D — Unpredictable Request Volume

Requirement: A startup launches a new social media app. Traffic patterns are completely unknown and could spike unpredictably during viral events.

Design: Use on-demand capacity mode. The table scales automatically without requiring throughput estimation.

Why this works: On-demand mode absorbs unpredictable traffic without manual intervention. There is no risk of under-provisioning during unexpected spikes.

Trade-offs: On-demand costs more per request than well-tuned provisioned capacity. On-demand is not unlimited — tables have throughput quotas (default 40,000 read/write request units per table), and extremely sudden traffic from near-zero can still experience brief throttling as DynamoDB scales. The team should still monitor usage and table quotas.

Exam clue: “Unpredictable traffic” + “minimize operational overhead” + “new application” → on-demand mode.

Scenario E — Predictable High-Volume Workload

Requirement: A mature logistics company processes 50,000 consistent reads per second during business hours and 5,000 during off-hours. The pattern has been stable for months.

Design: Use provisioned capacity with auto scaling. Set the minimum to 5,000 RCUs, maximum to 50,000 RCUs, and target utilization at 70%.

Why this works: Provisioned mode with auto scaling handles the predictable daily pattern at a lower per-request cost than on-demand. Auto scaling adjusts capacity as traffic ramps up and down.

Trade-offs: Auto scaling reacts to trends over minutes, not seconds. Very sudden spikes within the pattern could briefly throttle before scaling kicks in. If traffic patterns change significantly, the auto scaling configuration may need updating.

Exam clue: “Predictable traffic” + “cost optimization” + “stable workload” → provisioned + auto scaling.

Scenario F — A Hot Partition Key

Requirement: An IoT company uses DeviceType as the partition key. Three popular device types generate 95% of all traffic, causing throttling even though overall capacity seems sufficient.

Design: Redesign the partition key for better distribution. Use DeviceId (high cardinality) instead of DeviceType (low cardinality). If queries by device type are still needed, create a GSI.

Why this works: Redistributing traffic across many partition-key values prevents any single partition from being overwhelmed. DynamoDB’s adaptive capacity helps with temporary imbalances, but sustained hot keys require a key redesign.

Why common alternatives fail:

  • Adding a GSI does not fix a hot base-table partition — the base table still receives the writes.
  • Switching to on-demand does not resolve a hot key — the partition is still overloaded regardless of capacity mode.
  • Increasing provisioned capacity helps only if the bottleneck is overall table capacity, not a single partition.

Exam clue: “Throttling despite sufficient overall capacity” + “few partition key values” → hot partition problem → redesign the key.

Scenario G — LSI Requirement Discovered After Table Creation

Requirement: A company realizes six months after launch that it needs an alternative sort key within the same partition, and the table was created without any LSIs.

Design: You cannot add an LSI to an existing table. Options include:

  1. Create a GSI that mimics the access pattern (but sacrifices strongly consistent reads).
  2. Create a new table with the required LSI and migrate data.
  3. Redesign the sort key on a new table if the application can tolerate a migration.

Why this matters: LSI design is a one-time decision at table creation. This is why understanding all access patterns before creating the table is critical.

Exam clue: “Alternative sort key” + “existing table” + “cannot add LSI” → use a GSI (if eventual consistency is acceptable) or migrate to a new table.

Scenario H — Strong Consistency Requirement

Requirement: A financial application reads account balances that must always reflect the latest write. The application also needs to query balances by branch office.

Design: For the primary access (by AccountId), read directly from the base table with strongly consistent reads. For the branch-office query, if strong consistency is required, define an LSI at table creation with AccountId as PK and BranchId as the alternative SK. If eventual consistency is acceptable for the branch query, a GSI works.

Why this works: Base table reads and LSI reads support strongly consistent mode. A GSI cannot provide it.

Trade-offs: The LSI requires foresight at table creation and imposes the 10 GB item collection limit. If the branch query does not need strong consistency, a GSI is simpler and more flexible.

Exam clue: “Must have strongly consistent reads” + “indexed query” → only LSI or base table (never GSI).

Scenario I — Table Is Being Throttled

Requirement: An application’s DynamoDB requests start returning ProvisionedThroughputExceededException after a traffic increase.

Diagnosis approach:

  1. Check capacity mode — Is the table provisioned or on-demand? If provisioned, are RCUs/WCUs sufficient for current demand?
  2. Check partition-key distribution — Use CloudWatch ConsumedReadCapacityUnits and ConsumedWriteCapacityUnits per partition. Are a few keys receiving most traffic?
  3. Check GSI capacity — In provisioned mode, each GSI has its own throughput. A throttled GSI can back-pressure writes to the base table.
  4. Check access patterns — Are scans consuming excessive capacity? Should they be replaced with targeted queries?
  5. Evaluate solutions — Increase capacity, enable auto scaling, switch to on-demand (if the issue is overall capacity), or redesign keys (if the issue is hot partitions).

Exam clue: “Throttling” questions require identifying whether the root cause is insufficient capacity, poor key distribution, GSI bottleneck, or inefficient access patterns before choosing a solution.

Exam Gotchas

1. Confusing partition key with sort key

Wrong: Thinking the sort key determines data distribution across partitions.

Right: The partition key determines which partition stores the data. The sort key determines ordering within a partition. Both serve different roles.

Memory rule: Partition key = where data lives. Sort key = how data is ordered within that location.

2. Assuming duplicate partition keys in a simple primary key

Wrong: Two items can share the same partition key in a table with only a partition key.

Right: In a simple primary key (partition key only), each partition-key value must be unique. Duplicates are only possible in a composite primary key where different sort keys distinguish the items.

Memory rule: Simple PK = unique values only. Composite PK = PK+SK combination must be unique.

3. Forgetting that composite keys use both attributes

Wrong: Thinking the partition key alone identifies an item in a table with a composite key.

Right: The partition key + sort key combination uniquely identifies each item. Multiple items can share a partition key if their sort keys differ.

Memory rule: Composite key identity = PK + SK together, not PK alone.

4. Assuming sort key enables cross-partition queries

Wrong: A sort key lets you query across all partitions automatically.

Right: A sort key only supports range queries within a single partition key value. To query across partitions, you need a GSI or a Scan.

Memory rule: Sort key = within partition. Cross-partition = GSI.

5. Confusing GSI with LSI

Wrong: GSI and LSI are interchangeable index types.

Right: A GSI can have a completely different partition key. An LSI must share the base table’s partition key and only provides a different sort key.

Memory rule: GSI = new partition key possible. LSI = same partition key, different sort key only.

6. Assuming GSI must share the base table’s partition key

Wrong: A GSI always uses the same partition key as the base table.

Right: The whole point of a GSI is that its partition key can differ from the base table. That’s what makes it “global.”

Memory rule: “Global” = different key possible. “Local” = same partition key required.

7. Assuming LSI can use a different partition key

Wrong: An LSI can change both the partition key and sort key.

Right: An LSI must use the base table’s partition key. Only the sort key can differ. If you need a different partition key, use a GSI.

Memory rule: LSI changes the sort key only. Different partition key = GSI.

8. Assuming LSI can be added after table creation

Wrong: You can add an LSI to an existing table like you add a GSI.

Right: LSIs must be defined at table creation. Once the table exists, you cannot add or remove LSIs. GSIs can be added anytime.

Memory rule: LSI = birth only. GSI = anytime.

9. Forgetting GSI queries are eventually consistent only

Wrong: You can set ConsistentRead = true on a GSI query.

Right: GSI queries never support strongly consistent reads. Data is replicated asynchronously to the GSI. If strong consistency is required, read from the base table or an LSI.

Memory rule: GSI = eventually consistent always. Strong consistency = base table or LSI.

10. Assuming identical consistency for all indexes

Wrong: All secondary indexes behave the same way for consistency.

Right: LSIs support both eventually and strongly consistent reads. GSIs support only eventually consistent reads. This is a key architectural difference.

Memory rule: Consistency varies by index type. LSI = both. GSI = eventual only.

11. Assuming indexes have no overhead

Wrong: Creating indexes is free and has no impact on writes or storage.

Right: Every index consumes additional storage and write capacity. When you write to the base table, every affected index is also updated. In provisioned mode, GSIs have separate throughput settings.

Memory rule: Each index = more storage + more write cost + more to manage.

12. Assuming GSI makes every query efficient

Wrong: A GSI automatically makes any query fast.

Right: A GSI is only efficient if its key design matches the query pattern and the partition key distributes traffic evenly. A GSI with a hot partition key is just as problematic as a hot base-table key.

Memory rule: GSI efficiency depends on its key design, not just its existence.

13. Confusing Query with Scan

Wrong: Query and Scan are the same operation.

Right: Query targets a specific partition key (efficient). Scan reads the entire table (expensive). For production workloads on large tables, prefer Query with appropriate key design.

Memory rule: Query = targeted by key. Scan = reads everything.

14. Assuming filters reduce read capacity

Wrong: Adding a filter expression to a Scan makes it use less read capacity.

Right: Filter expressions remove items from the results but DynamoDB still reads and charges for every item evaluated. Only key conditions reduce what is actually read from storage.

Memory rule: Filters hide results; key conditions prevent reads. Capacity is consumed for items read, not items returned.

15. Choosing on-demand because it is always cheaper

Wrong: On-demand mode is always the most cost-effective choice.

Right: On-demand has a higher per-request cost. For predictable, sustained workloads, provisioned capacity with auto scaling is typically more cost-effective.

Memory rule: Unpredictable = on-demand. Predictable + cost-sensitive = provisioned.

16. Choosing provisioned without accounting for variability

Wrong: Setting static provisioned capacity works for all traffic patterns.

Right: Without auto scaling, provisioned capacity cannot adapt to traffic changes. Under-provisioning causes throttling; over-provisioning wastes money.

Memory rule: Provisioned without auto scaling = fragile. Always pair with auto scaling or use on-demand.

17. Assuming on-demand means no throttling ever

Wrong: On-demand mode guarantees unlimited throughput with zero throttling.

Right: On-demand tables still have throughput quotas (default 40,000 read/write request units per table). Extremely sudden traffic spikes from near-zero can briefly throttle while DynamoDB scales.

Memory rule: On-demand scales automatically but has quotas. Not unlimited.

18. Treating adaptive capacity as a universal fix

Wrong: Adaptive capacity solves all hot-key problems automatically.

Right: Adaptive capacity helps with temporary imbalances. Sustained hot keys from poor partition-key design require a key redesign, not reliance on adaptive capacity.

Memory rule: Adaptive capacity = temporary relief. Key redesign = permanent fix.

19. Ignoring GSI bottlenecks when diagnosing throttling

Wrong: If the base table has enough capacity, throttling cannot occur.

Right: In provisioned mode, each GSI has separate throughput. A throttled GSI can back-pressure writes to the base table, causing write rejections even when the base table has capacity.

Memory rule: Check GSI capacity when base table writes throttle. GSI is a separate capacity consumer.

20. Assuming flexible attributes eliminate design needs

Wrong: Because DynamoDB items can have any attributes, no upfront design is needed.

Right: Flexible item structure does not eliminate the need to design access patterns, keys, and indexes. Poor key design leads to hot partitions, expensive scans, and inability to support required queries.

Memory rule: Flexible schema ≠ no design needed. Access patterns must drive key and index choices.

21. Forgetting to verify index behavior for the workload

Wrong: An index works correctly regardless of how the workload uses it.

Right: Indexes consume capacity and have their own key distribution. A GSI can become a bottleneck. An LSI has a 10 GB item collection limit. Always evaluate index behavior against the actual workload.

Memory rule: Indexes need capacity and design planning too — not just the base table.

22. Assuming more read capacity fixes poor key design

Wrong: Increasing RCUs always resolves read throttling.

Right: If the problem is a hot partition key, increasing overall capacity does not help because the extra capacity is distributed across all partitions, not concentrated on the hot one. The fix is better key distribution.

Memory rule: Throttling from hot keys ≠ insufficient capacity. Fix the key design, not the capacity number.

Practice Questions

Q1. A company stores customer orders in a DynamoDB table with CustomerId as the partition key and OrderId as the sort key. The marketing team needs to query all orders across all customers that have a status of “Returned.” The query must support filtering by return date. Which solution enables this access pattern with the LEAST operational effort?

  • A. Create a Local Secondary Index with OrderStatus as the sort key.
  • B. Scan the entire table and filter results where OrderStatus = "Returned".
  • C. Create a Global Secondary Index with OrderStatus as the partition key and ReturnDate as the sort key.
  • D. Create a new table with OrderStatus as the partition key and replicate data using DynamoDB Streams.

Correct Answer: C

A GSI with OrderStatus as the partition key enables querying orders by status across all customers — a different partition key than the base table. Adding ReturnDate as the sort key supports date-range filtering efficiently. A is wrong — an LSI cannot change the partition key, so it would only query within one customer’s partition, not across all customers. B is wrong — scanning the entire table is expensive and does not scale. D is wrong — maintaining a separate table adds significant operational overhead compared to a GSI.

Memory rule: “Query by a different attribute across all items” = GSI. An LSI cannot provide a different partition key.

Q2. A startup is launching a new mobile game. Player activity is expected to vary dramatically — from near-zero during development to potentially millions of requests during launch events. The team wants to minimize time spent on capacity planning and avoid throttling during unpredictable traffic spikes. Which DynamoDB capacity configuration BEST meets these requirements?

  • A. Use provisioned capacity mode with high initial RCU and WCU values to handle the expected peak.
  • B. Use on-demand capacity mode so the table scales automatically with actual traffic without requiring throughput estimation.
  • C. Use provisioned capacity mode with auto scaling configured for a wide range of minimum to maximum values.
  • D. Use provisioned capacity mode and manually increase capacity before each launch event.

Correct Answer: B

On-demand mode eliminates capacity planning entirely — DynamoDB handles scaling automatically. This is ideal for unpredictable, highly variable workloads. A is wrong — over-provisioning wastes money during low-traffic periods and may still under-provision during unexpected spikes. C is wrong — auto scaling reacts to trends over minutes, which may not respond fast enough for sudden massive spikes, and still requires configuring capacity ranges. D is wrong — manual scaling before events requires operational effort and accurate prediction, which the team wants to avoid.

Memory rule: “Unpredictable traffic” + “minimize operational overhead” = on-demand mode.

Q3. A financial services company has a DynamoDB table with AccountId as the partition key and TransactionDate as the sort key. The compliance team needs to query an account’s transactions sorted by amount instead of date, and the results must reflect the most recent writes (strongly consistent reads). Which solution meets these requirements?

  • A. Create a Global Secondary Index with AccountId as the partition key and TransactionAmount as the sort key, and use strongly consistent reads on the GSI.
  • B. Scan the table with a filter expression on TransactionAmount using strongly consistent reads.
  • C. Create a new table with TransactionAmount as the sort key and replicate data.
  • D. Define a Local Secondary Index at table creation with AccountId as the partition key and TransactionAmount as the sort key, and use strongly consistent reads.

Correct Answer: D

An LSI shares the base table’s partition key (AccountId) and provides an alternative sort key (TransactionAmount). LSI queries support strongly consistent reads. A is wrong — GSI queries are always eventually consistent; you cannot use ConsistentRead = true on a GSI. B is wrong — scanning the entire table is expensive and does not provide sorting by amount. C is wrong — creating a separate table and replicating data adds unnecessary complexity.

Memory rule: “Same partition key” + “different sort key” + “strongly consistent” = LSI. GSI can never provide strongly consistent reads.

Amazon S3 — Storage Classes, Versioning & Replication

Learn from Zero

1A — Amazon S3 Fundamentals

Amazon Simple Storage Service (S3) is a fully managed object storage service. Unlike block storage (EBS) that provides raw disk volumes or file storage (EFS) that provides a shared file system, S3 stores data as discrete objects in buckets.

Core Concepts

  • Bucket — A container for objects. Bucket names are globally unique across all AWS accounts. Each bucket is created in a specific AWS Region.
  • Object — A file stored in a bucket. Each object consists of data, metadata (key-value pairs), and a unique key.
  • Object key — The full path that uniquely identifies an object within a bucket (e.g., reports/2026/quarterly-summary.pdf).
  • Metadata — System-defined and user-defined key-value pairs attached to each object (content type, encryption, custom tags).

Durability and Availability

Durability is the probability that a stored object will not be lost. Most S3 storage classes provide 99.999999999% (11 nines) durability by storing data redundantly.

Availability is the percentage of time the service is accessible. Different storage classes offer different availability SLAs (e.g., S3 Standard targets 99.99% availability).

Durable does not mean available. An object can be safely stored (durable) but temporarily inaccessible due to a service disruption. And highly durable storage does not make your application highly available — you still need redundant compute, networking, and recovery plans.

S3 is commonly used for: website assets, application data, backup and restore, log storage, data lakes and analytics, media hosting, disaster recovery copies, and compliance archives. Storage class selection should be based on access frequency, retrieval latency needs, retention duration, availability requirements, and cost.

1B — S3 Storage Classes

S3 Standard

General-purpose storage for frequently accessed data. Stores objects redundantly across a minimum of three Availability Zones. Provides 99.99% availability and 11 nines durability. No retrieval charges, no minimum storage duration charge. Best for active content such as website assets, application data, and content distribution.

S3 Intelligent-Tiering

Designed for data with unknown or changing access patterns. Automatically moves objects between access tiers based on usage:

  • Frequent Access tier — Default tier for new objects.
  • Infrequent Access tier — Objects not accessed for 30 days move here automatically.
  • Archive Instant Access tier — Objects not accessed for 90 days move here automatically.
  • Archive Access tier — Optional; must be enabled. Objects not accessed for 90+ days (configurable).
  • Deep Archive Access tier — Optional; must be enabled. Objects not accessed for 180+ days (configurable).

A small monthly monitoring and automation charge per object applies. No retrieval charges when accessing objects in the Frequent or Infrequent Access tiers. Objects in the optional archive tiers require a restore before access. Objects smaller than 128 KB are always stored in the Frequent Access tier and not monitored for tiering.

When to use: Intelligent-Tiering is ideal when you cannot predict which objects will become cold. It avoids the manual effort of lifecycle policies for unpredictable access patterns.

S3 Standard-Infrequent Access (Standard-IA)

For data accessed less frequently but requiring rapid access when needed. Lower storage cost than Standard, but with per-GB retrieval charges. Stored across multiple AZs (11 nines durability, 99.9% availability). Minimum storage duration: 30 days (deleting earlier still incurs the 30-day charge). Minimum billable object size: 128 KB.

Best for: disaster recovery copies, infrequently accessed reports, long-lived data that is occasionally read.

S3 One Zone-Infrequent Access (One Zone-IA)

Similar to Standard-IA but stores data in a single Availability Zone. Lower cost than Standard-IA, but data is lost if that AZ is destroyed. 99.5% availability. Same 30-day minimum duration and 128 KB minimum size.

Best for: recreatable data, secondary backup copies, data that can be restored from another source.

One Zone-IA does NOT provide the same resilience as Standard-IA. If the exam requires “resilience across Availability Zones,” One Zone-IA is the wrong answer.

S3 Glacier Instant Retrieval

For rarely accessed archival data that still needs millisecond retrieval. Lower storage cost than Standard-IA, but higher retrieval charges. Minimum storage duration: 90 days. Data is available immediately when requested — no restore process required.

Best for: medical images, news media archives, user-generated content accessed once a quarter.

S3 Glacier Flexible Retrieval

For archive data that can tolerate a restore process before access. Objects are not immediately readable — you must initiate a restore, which copies the data to Standard temporarily.

Retrieval options:

  • Expedited — typically 1–5 minutes.
  • Standard — typically 3–5 hours.
  • Bulk — typically 5–12 hours (lowest cost).

Minimum storage duration: 90 days. Best for: backup archives, regulatory records, disaster recovery data where multi-hour retrieval is acceptable.

S3 Glacier Deep Archive

The lowest-cost S3 storage class. For data retained for years and very rarely accessed.

Retrieval options:

  • Standard — within 12 hours.
  • Bulk — within 48 hours.

Minimum storage duration: 180 days. Best for: long-term compliance archives, financial records retained for 7+ years, data that may never be accessed again but must be preserved.

Deep Archive is unsuitable for data that must be retrieved quickly. If the scenario requires fast access, use Glacier Instant Retrieval or a higher-tier class.

S3 Express One Zone

A high-performance, single-AZ storage class for latency-sensitive workloads requiring single-digit-millisecond access. Uses a directory-bucket model rather than general-purpose buckets. Designed for specific compute-intensive use cases like ML training and analytics. Not a general replacement for S3 Standard.

1D — S3 Lifecycle Policies

A lifecycle configuration is a set of rules that automate transitions between storage classes and/or expire (delete) objects based on their age or other criteria.

Transition Actions

Move objects to a lower-cost storage class after a defined period. Example transitions:

  • Standard → Standard-IA after 30 days
  • Standard-IA → Glacier Flexible Retrieval after 90 days
  • Glacier Flexible Retrieval → Glacier Deep Archive after 365 days
Transition constraints: Objects must remain in a class for the minimum storage duration before transition (e.g., 30 days in Standard-IA before moving to Glacier). Not all transitions are allowed — you generally cannot transition from an archival class back to a more frequently accessed class via lifecycle rules. Objects smaller than 128 KB are not transitioned to Standard-IA or One Zone-IA.

Expiration Actions

Automatically delete objects after a specified period. Common uses:

  • Delete temporary log files after 90 days.
  • Remove incomplete multipart uploads after 7 days.
  • Expire noncurrent object versions after a defined retention period.

Scope and Versioning Interaction

Lifecycle rules can target specific prefixes (e.g., logs/) or objects with specific tags. In versioned buckets, rules can apply separately to current versions and noncurrent versions. This enables policies like: “Keep the current version in Standard, transition noncurrent versions to Glacier after 30 days, expire noncurrent versions after 365 days.”

Always test lifecycle policies against actual retention and access requirements before deploying. Once an object transitions to an archival class, retrieval behavior changes.

1E — S3 Versioning

S3 Versioning preserves every version of every object in a bucket. When you overwrite or delete an object, S3 keeps the previous versions instead of replacing them.

How It Works

  • Each version gets a unique version ID.
  • Overwriting an object creates a new version; the old version remains accessible by its version ID.
  • Deleting an object (without specifying a version ID) creates a delete marker — a placeholder that hides the current version from normal listings and GET requests.
  • Permanent deletion requires specifying the exact version ID. This removes that specific version irreversibly.

Worked Example

StepActionResult
1Upload report.pdfVersion v1 created
2Upload corrected report.pdfVersion v2 created; v1 still exists
3Delete report.pdf (no version ID)Delete marker added; v1 and v2 still exist
4GET report.pdfReturns 404 (delete marker hides the object)
5Remove the delete markerv2 becomes current again; object is accessible
6GET report.pdf?versionId=v1Returns the original version
Delete marker ≠ permanent deletion. A delete marker hides the object but does not destroy any version. Removing the delete marker restores access. Permanently deleting a version (by specifying its version ID) is irreversible.

Versioning States

  • Unversioned (default) — No versions maintained.
  • Enabled — All new objects get version IDs; old versions are preserved.
  • Suspended — New objects get a null version ID; existing versions remain but no new versions are created.

Versioning increases storage costs because every version consumes space. Use lifecycle policies on noncurrent versions to control costs. Versioning alone is not a complete backup strategy — it does not protect against bucket deletion, account compromise, or Region-wide outages.

1F — S3 Replication — CRR and SRR

S3 Replication automatically copies objects from a source bucket to one or more destination buckets.

Two Types

DestinationDifferent AWS RegionSame AWS Region
Primary useDisaster recovery, data locality, complianceLog aggregation, data separation, compliance copies
LatencyHigher (cross-Region transfer)Lower (same Region)
Data transfer costCross-Region transfer charges applyNo cross-Region charges

Prerequisites

  • Versioning must be enabled on both source and destination buckets.
  • An IAM role must grant S3 permission to replicate objects to the destination.
  • The destination bucket must have appropriate bucket policy permissions.
  • If objects are encrypted with KMS, the replication role needs KMS permissions for both source and destination keys.

Important Behaviors

  • Replication is asynchronous — there is a delay (replication lag) between the source write and the replica appearing.
  • S3 Replication Time Control (RTC) provides an SLA that 99.99% of objects replicate within 15 minutes, for an additional cost.
  • By default, replication applies only to new objects written after the rule is created.
  • S3 Batch Replication can replicate existing objects that were written before the rule was configured.
  • Replication copies eligible objects according to the configured rules — it does not replicate the entire application infrastructure.
Replication is not an instant mirror. There is always some lag. And a replicated bucket does not automatically make your application recoverable — you still need compute, DNS failover, and application configuration in the destination Region.

1G — Replication Delete Behavior & Details

Delete Marker Replication

By default, delete markers are NOT replicated. If a user deletes an object in the source bucket, the delete marker is not copied to the destination — the replica remains visible. You can enable delete marker replication in the replication rule if you want deletions to propagate.

Permanent Version Deletion

When a user permanently deletes a specific object version (by version ID), that deletion is never replicated. This protects replicas from malicious or accidental permanent deletions at the source.

Replication Scope

  • Rules can be scoped by prefix (e.g., documents/) or object tags.
  • Each object has a replication status: PENDING, COMPLETED, FAILED, or REPLICA.
  • Replica objects have their own version IDs and ownership settings.

Lifecycle and Replication Interaction

Lifecycle rules operate independently on source and destination buckets. A transition or expiration in the source bucket does not trigger the same action in the destination. Plan lifecycle rules for both buckets based on their respective retention requirements.

1H — Object Lock, Encryption & Data Protection

S3 Object Lock

Object Lock provides WORM (Write Once Read Many) protection for S3 objects. Once locked, an object version cannot be deleted or overwritten for the specified retention period.

FeatureGovernance ModeCompliance Mode
ProtectionMost users cannot delete/overwriteNo one can delete/overwrite, including root
OverrideUsers with special permissions can overrideCannot be overridden by anyone during retention
Retention changeCan be shortened with permissionsCan only be extended, never shortened
Use caseSoft protection; testing retention policiesRegulatory compliance (SEC, HIPAA, FINRA)

Legal Hold — Independently prevents deletion of an object version until explicitly removed. No retention period — stays active until removed by an authorized user. Can be applied alongside retention modes.

Object Lock ≠ Versioning. Versioning preserves old versions but does not prevent their deletion. Object Lock prevents deletion of specific versions during the retention period. Object Lock requires versioning to be enabled, but adds enforcement that versioning alone does not provide.

Encryption at Rest

S3 supports server-side encryption (SSE-S3, SSE-KMS, SSE-C) and client-side encryption. When replicating encrypted objects, the replication IAM role must have permissions for the source and destination KMS keys. The destination bucket may use a different encryption key.

Additional Protections

  • Least-privilege bucket policies — Restrict who can read, write, or delete.
  • MFA Delete — Requires MFA to permanently delete object versions or change versioning state.
  • Access logging and CloudTrail — Audit all S3 operations.
  • Separate recovery copies — CRR to another Region provides geographic separation.
  • Backup testing — Regularly verify that recovery procedures work.

When Real Architects Actually Use This

Scenario A — Frequently Accessed Website Assets

Requirement: A retail company stores product images and CSS/JS bundles that customers request thousands of times per day.

Design: Store in S3 Standard. No retrieval charges, highest availability (99.99%), data redundant across ≥ 3 AZs.

Why this works: Frequent-access data benefits from Standard’s zero retrieval cost and highest availability. Moving active assets to IA classes would add retrieval charges that offset storage savings.

Trade-offs: Standard has the highest per-GB storage rate. If some assets become inactive, a lifecycle policy or Intelligent-Tiering could optimize cost over time.

Exam clue: “Frequently accessed” + “highest availability” → S3 Standard.

Scenario B — Unknown Access Patterns

Requirement: A media company stores millions of articles and images. Some remain popular for weeks; others are never read again after publication.

Design: Use S3 Intelligent-Tiering. Objects automatically move between access tiers based on actual usage. No retrieval charges for the Frequent and Infrequent Access tiers.

Why this works: The company cannot predict which objects will stay hot. Intelligent-Tiering handles the optimization automatically, avoiding manual lifecycle rules for each object.

Trade-offs: A small monthly monitoring charge per object (≥ 128 KB) applies. Objects under 128 KB stay in the Frequent Access tier and are not monitored. The optional archive tiers require a restore before access.

Exam clue: “Unknown access patterns” + “automated cost optimization” → Intelligent-Tiering.

Scenario C — Long-Term Compliance Archives

Requirement: A financial institution must retain transaction records for 7 years. Records are almost never retrieved, but when they are, a 12-hour wait is acceptable.

Design: Use S3 Glacier Deep Archive. Lowest storage cost. Standard retrieval within 12 hours, bulk within 48 hours. 180-day minimum storage duration aligns well with multi-year retention.

Why this works: Extremely low access frequency and tolerance for long restore times make Deep Archive the most cost-effective choice.

Why not Glacier Flexible Retrieval: Glacier Flexible Retrieval costs more per GB stored. It makes sense only if the company occasionally needs faster (1–5 minute expedited) retrieval, which this scenario does not require.

Exam clue: “Years of retention” + “rarely accessed” + “hours of retrieval acceptable” → Glacier Deep Archive.

Scenario D — Accidental Object Deletion

Requirement: A developer accidentally deletes a critical configuration file from S3. The company needs to restore the previous version.

Design: Enable S3 Versioning on the bucket. The delete created a delete marker, not a permanent deletion. Remove the delete marker to restore the latest version, or retrieve a specific version by its version ID.

Why this works: Versioning preserves every previous version. An ordinary delete only hides the object behind a delete marker — all versions remain intact.

Trade-offs: Versioning increases storage costs (all versions consume space). Use lifecycle rules to expire noncurrent versions after a suitable retention period. For stronger protection, add MFA Delete to require multi-factor authentication for permanent version deletions.

Exam clue: “Recover previous version” + “accidental delete” → S3 Versioning + remove delete marker.

Scenario E — Cross-Region Disaster Recovery

Requirement: A healthcare company stores patient records in us-east-1 and needs a separate copy in eu-west-1 for disaster recovery.

Design: Enable CRR (Cross-Region Replication) with versioning on both buckets. Configure an IAM role granting S3 replication permissions. If KMS-encrypted, grant the role access to both source and destination KMS keys.

Why this works: CRR asynchronously copies new objects to the destination Region. If us-east-1 becomes unavailable, the eu-west-1 copy is accessible.

Trade-offs: Replication is asynchronous — there is always some lag. CRR incurs cross-Region data transfer charges. Replication copies objects, not the application — compute, DNS, and networking must also be planned. For a 15-minute SLA, enable Replication Time Control (RTC).

Exam clue: “Copy objects to another Region” + “disaster recovery” → CRR with versioning.

Scenario F — Same-Region Copies for Data Separation

Requirement: A company needs to replicate production data to a separate analytics bucket in the same Region, owned by a different team, for compliance and audit separation.

Design: Use SRR (Same-Region Replication). Both buckets must have versioning enabled. Configure appropriate destination bucket policies.

Why this works: SRR copies eligible objects within the same Region without cross-Region transfer costs. The analytics team gets their own copy without impacting production.

Trade-offs: SRR is still asynchronous. Lifecycle rules on the destination bucket operate independently. SRR does not aggregate from multiple sources automatically — configure separate rules if needed.

Exam clue: “Same-Region copy” + “separate bucket for compliance/analytics” → SRR.

Scenario G — Reduce Storage From Old Versions

Requirement: A versioned bucket stores application logs. Developers overwrite objects frequently, accumulating hundreds of noncurrent versions and inflating storage costs.

Design: Create a lifecycle rule for noncurrent versions: transition noncurrent versions to Standard-IA after 30 days, then to Glacier Flexible Retrieval after 90 days, and expire them after 365 days.

Why this works: Noncurrent versions rarely need fast access. Transitioning them to cheaper classes and eventually expiring them keeps costs under control while preserving recovery capability for a defined period.

Trade-offs: Expiring noncurrent versions too early reduces recovery options. The policy should match the company’s retention requirements.

Exam clue: “Versioned bucket” + “growing storage costs” + “old versions” → lifecycle policy on noncurrent versions.

Scenario H — Immutable Compliance Records

Requirement: A brokerage firm must store trading records that cannot be deleted or modified by anyone, including administrators, for a minimum of 5 years. This is a regulatory requirement.

Design: Enable S3 Object Lock in compliance mode with a 5-year retention period. Enable versioning (required). Compliance mode prevents anyone — including the root user — from deleting or overwriting protected object versions until retention expires.

Why not governance mode: Governance mode allows users with special permissions to override the lock. For regulatory requirements where no exceptions are allowed, compliance mode is mandatory.

Trade-offs: Object Lock must be enabled at bucket creation. Compliance mode retention cannot be shortened once set. Plan carefully — mistakes in retention periods cannot be corrected downward.

Exam clue: “Cannot be deleted by anyone” + “regulatory retention” → Object Lock compliance mode.

Scenario I — Replicate Existing Objects

Requirement: A company enables CRR on an existing bucket with millions of objects, but discovers that only newly uploaded objects appear in the destination.

Design: Use S3 Batch Replication to copy existing objects that were uploaded before the replication rule was created.

Why this works: Standard replication (CRR/SRR) only applies to new objects written after the rule is configured. Batch Replication is an on-demand job that processes existing objects and can also retry previously failed replications.

Trade-offs: Batch Replication is not covered by the RTC SLA. It runs as a batch job through S3 Batch Operations and incurs per-object and per-GB charges.

Exam clue: “Existing objects not replicated” + “replication rule already active” → S3 Batch Replication.

Scenario J — Balance Retrieval Speed and Cost

Requirement: A hospital stores medical imaging archives. Radiology images accessed within the first year need millisecond retrieval. Images older than one year can tolerate a 3–5 hour restore. Images older than 5 years need only long-term retention.

Design: Use a lifecycle policy:

  1. Store in S3 Standard for the first 90 days (frequent access during initial review).
  2. Transition to Glacier Instant Retrieval after 90 days (rare but instant access for the first year).
  3. Transition to Glacier Flexible Retrieval after 365 days (standard 3–5 hour restore acceptable).
  4. Transition to Glacier Deep Archive after 1,825 days / 5 years (long-term retention).

Why this works: Each stage matches the retrieval requirement to the lowest-cost class that can satisfy it. The lifecycle policy automates the transitions.

Exam clue: “Different retrieval needs at different ages” → lifecycle policy transitioning through progressively cheaper classes.

Exam Gotchas

1. Choosing an archival class when immediate retrieval is required

Wrong: Picking Glacier Flexible Retrieval or Deep Archive for data that must be accessed instantly.

Right: Glacier Flexible and Deep Archive require a restore process (minutes to hours). If millisecond retrieval is needed, use Glacier Instant Retrieval, Standard-IA, or Standard.

Memory rule: “Immediate access” = Glacier Instant or higher. “Can wait hours” = Glacier Flexible/Deep Archive.

2. Confusing Standard-IA with One Zone-IA

Wrong: Treating them as identical except for price.

Right: Standard-IA stores across ≥ 3 AZs (99.9% availability). One Zone-IA stores in a single AZ (99.5% availability). Data is lost if that AZ is destroyed.

Memory rule: “AZ resilience required” = Standard-IA. “Recreatable data” = One Zone-IA.

3. Assuming lower storage rate = lower total cost

Wrong: Choosing the cheapest per-GB class for all data.

Right: IA and Glacier classes add retrieval charges, minimum duration charges, and restore fees. Frequently accessed data in an IA class may cost more than Standard.

Memory rule: Total cost = storage + retrieval + requests + minimum-duration penalty. Evaluate all components.

4. Forgetting retrieval charges and minimum storage duration

Wrong: Storing short-lived data in Glacier Deep Archive (180-day minimum) and deleting after 30 days.

Right: Early deletion still incurs the full minimum-duration charge. Standard-IA: 30 days. Glacier Instant: 90 days. Deep Archive: 180 days.

Memory rule: Short-lived data in archival classes = wasted money. Match retention to minimum duration.

5. Assuming Intelligent-Tiering has no costs or limitations

Wrong: Intelligent-Tiering is free and works for all objects.

Right: A monthly monitoring charge per object applies. Objects < 128 KB are not monitored. Optional archive tiers require a restore before access.

Memory rule: Intelligent-Tiering = great for unpredictable access, but has monitoring fees and size thresholds.

6. Assuming all Glacier classes have the same retrieval

Wrong: Glacier Instant, Flexible, and Deep Archive all take hours.

Right: Glacier Instant = milliseconds. Glacier Flexible = 1 min to 12 hours (depending on tier). Deep Archive = 12–48 hours. No expedited option for Deep Archive.

Memory rule: Instant = ms. Flexible = min-to-hours. Deep = half-day to two days.

7. Confusing lifecycle transition with lifecycle expiration

Wrong: Thinking transition and expiration are the same.

Right: Transition moves objects to a different storage class. Expiration deletes objects (or noncurrent versions). Both are lifecycle actions but do completely different things.

Memory rule: Transition = move to cheaper class. Expiration = delete.

8. Assuming any object can transition to any class at any time

Wrong: Objects can freely move between any storage classes via lifecycle.

Right: Lifecycle transitions follow a one-way waterfall. You cannot transition from Glacier back to Standard via lifecycle. Objects < 128 KB don’t transition to IA classes. Minimum duration constraints must be respected.

Memory rule: Lifecycle = downhill only. Check minimum durations and size limits.

9. Forgetting noncurrent versions in versioned buckets

Wrong: Ignoring version storage when versioning is enabled.

Right: Every overwritten version accumulates storage costs. Use lifecycle rules on noncurrent versions to transition or expire them.

Memory rule: Versioned bucket + no noncurrent lifecycle = unbounded storage growth.

10. Assuming versioning protects against everything

Wrong: Versioning is a complete backup solution.

Right: Versioning protects against accidental overwrites and simple deletes. It does not protect against bucket deletion, account compromise, or Region-wide failures. Combine with CRR, Object Lock, and MFA Delete.

Memory rule: Versioning = one layer of protection, not the entire strategy.

11. Confusing delete marker with permanent deletion

Wrong: A delete marker removes all versions of an object.

Right: A delete marker hides the current version but all versions remain. Permanent deletion requires specifying the version ID and is irreversible.

Memory rule: DELETE without version ID = delete marker (recoverable). DELETE with version ID = permanent.

12. Assuming an ordinary delete permanently removes every version

Wrong: Running aws s3 rm on a versioned object destroys it.

Right: It creates a delete marker. All prior versions survive. To permanently remove, delete each version by its version ID.

Memory rule: Simple delete = hide. Version-specific delete = destroy.

13. Assuming CRR and SRR have identical purposes

Wrong: CRR and SRR are the same thing in different locations.

Right: CRR copies to another Region (DR, data locality, compliance). SRR copies within the same Region (log aggregation, test/prod separation). CRR incurs cross-Region transfer charges.

Memory rule: CRR = cross-Region DR. SRR = same-Region separation.

14. Forgetting versioning is required for replication

Wrong: Replication works without versioning.

Right: Versioning must be enabled on both source and destination buckets. This is a hard prerequisite.

Memory rule: Replication = versioning on both buckets. No exceptions.

15. Assuming new replication rules copy existing objects

Wrong: Enabling CRR retroactively copies all existing objects.

Right: Replication applies only to new objects written after the rule is created. Use S3 Batch Replication for existing objects.

Memory rule: New rule = new objects only. Existing objects = Batch Replication.

16. Confusing async replication with synchronous consistency

Wrong: CRR provides an instant synchronized copy.

Right: Replication is asynchronous. There is always a lag. RTC provides a 15-minute SLA for 99.99% of objects, but it is not instant either.

Memory rule: Replication = async with lag. RTC = 15-min SLA (not instant).

17. Assuming replicated objects = full DR

Wrong: CRR alone makes the application recoverable in another Region.

Right: CRR copies objects. A full DR plan also needs compute, networking, DNS failover, and application configuration in the destination Region.

Memory rule: Replicated data ≠ replicated application. Plan the whole stack.

18. Assuming source deletion always deletes the replica

Wrong: Deleting an object in the source bucket always removes the replica.

Right: Delete markers are not replicated by default. Permanent version deletions are never replicated. Enable delete marker replication explicitly if you want deletions to propagate.

Memory rule: Delete at source ≠ delete at destination (by default). A safety feature.

19. Forgetting replication permissions and encryption

Wrong: Replication just needs a rule — permissions handle themselves.

Right: Replication requires an IAM role, destination bucket policy, and (for KMS-encrypted objects) KMS key permissions on both source and destination.

Memory rule: Replication = rule + IAM role + bucket policy + KMS perms.

20. Confusing Object Lock with versioning

Wrong: Versioning and Object Lock are the same thing.

Right: Versioning preserves versions but does not prevent their deletion. Object Lock prevents deletion of specific versions during the retention period. Object Lock requires versioning but adds enforcement.

Memory rule: Versioning = keep versions. Object Lock = prevent deletion of versions.

21. Confusing governance mode with compliance mode

Wrong: Both Object Lock modes provide the same protection.

Right: Governance mode can be overridden by users with special permissions. Compliance mode cannot be overridden by anyone, including root, until retention expires.

Memory rule: Governance = soft lock (overridable). Compliance = hard lock (absolute).

22. Ignoring lifecycle and replication interactions

Wrong: Lifecycle and replication configurations work independently with no side effects.

Right: Lifecycle rules run independently on each bucket. A transition or expiration in the source does not trigger the same action in the destination. Plan both.

Memory rule: Source lifecycle ≠ destination lifecycle. Configure each bucket’s rules separately.

23. Forgetting lifecycle rules must match retention requirements

Wrong: Any lifecycle transition or expiration is safe.

Right: Expiring noncurrent versions too early loses recovery data. Transitioning to archival classes changes retrieval behavior. Lifecycle rules must align with actual retention and access needs.

Memory rule: Lifecycle saves money but can lose data. Test rules against business requirements.

24. Assuming storage class changes S3 authorization

Wrong: Moving objects to a different storage class changes who can access them.

Right: Storage class affects cost, retrieval behavior, and availability. IAM policies, bucket policies, and ACLs control access regardless of storage class.

Memory rule: Storage class = cost/performance. Access control = IAM/policy. They are independent.

Messaging & Event-Driven Architecture Fundamentals

What is a distributed application? A modern application is rarely a single program running on one server. Instead, it is split into multiple components (microservices, serverless functions, worker processes) that run independently and communicate over a network. These components need a reliable way to talk to each other.

Synchronous vs. asynchronous communication. In synchronous communication, one component calls another and waits for a response before continuing — like a phone call. In asynchronous communication, the sender fires off a message and continues its own work without waiting for the receiver to finish — like sending a text message. Asynchronous designs improve responsiveness because the sender is not blocked by slow downstream processing.

Messages, events, and commands.

  • Command: An instruction to do something — “Process this order.”
  • Message: A unit of data sent between components — it could carry a command, a request, or any payload.
  • Event: A notification that something happened — “OrderPlaced” or “PaymentFailed.” Events describe facts; they do not tell the receiver what to do.

Producers and consumers. A producer (or publisher) creates and sends messages. A consumer (or subscriber) receives and processes them. Decoupling producers from consumers means that each side can scale, fail, and recover independently.

Three fundamental patterns:

  • Message queue: A durable buffer between a producer and one or more competing consumers. Each message is processed by one consumer. Think of a line at a bank — one teller handles each customer.
  • Pub/sub (publish–subscribe): A publisher sends a message to a topic, and the topic delivers a copy to every subscriber. Think of a radio broadcast — every tuned-in listener hears the same news.
  • Event bus: A central router that receives events, evaluates rules based on event content, and routes matching events to the appropriate targets.

Why decoupling matters. If the order-submission API directly calls inventory, payment, and notification services synchronously, any failure or slowdown in one service stalls the entire request. Decoupled designs use messaging so each downstream component processes work at its own pace. This improves resilience (one slow service does not block others), flexibility (you can add consumers without changing the producer), and scalability (you can scale consumers independently).

E-commerce example: A customer places an order. The system must (1) record the order, (2) process payment, (3) update inventory, and (4) send a confirmation email. These tasks have different latencies (payment is slow, recording is fast), different reliability needs (payment must not be lost), and different delivery needs (the email is not critical to the transaction). Doing them all synchronously in one API call makes the system fragile. Instead, the order API can publish a message or event, and each downstream system processes its part independently and asynchronously.

Important nuances of asynchronous processing:

  • Retries: A consumer may fail and need to reprocess a message.
  • Ordering: Messages may arrive in a different order than sent (depending on the service).
  • Duplication: A message may be delivered more than once.
  • Eventual consistency: Downstream state may take time to reflect the original action.
  • Success ≠ completion: Successfully publishing a message does not mean every consumer has finished its work. The producer knows the message was accepted, not that inventory was updated or the email was sent.

Before diving into each AWS service, remember: a message queue (SQS) buffers work, a notification service (SNS) broadcasts to subscribers, and an event bus (EventBridge) routes events by content. They solve different problems and are often combined.

Amazon Simple Queue Service (SQS)

What is SQS? Amazon SQS is a fully managed message queue service. It acts as a durable buffer between producers and consumers. A producer sends a message to the queue, and a consumer retrieves (polls) and processes it later. The queue decouples the two: the producer does not need to know who or what will process the message, and the consumer does not need to be available when the message is sent.

How it works:

  1. A producer sends a message to an SQS queue.
  2. The message stays in the queue until a consumer polls the queue and receives it.
  3. While the consumer is processing the message, SQS hides it from other consumers for a period called the visibility timeout.
  4. After successful processing, the consumer deletes the message from the queue.
  5. If the consumer fails (crashes, times out), the visibility timeout expires, and the message becomes visible again for another consumer to retry.

Why consumers poll (pull model). SQS does not push messages to consumers the way SNS does. Consumers must actively poll the queue. This means consumers control their own processing rate — they fetch messages when they are ready, not when the queue decides. This is fundamental to how SQS provides backpressure and buffering.

Key SQS concepts:

Message retention: How long SQS keeps an unprocessed message before automatically deleting it. Default: 4 days. Maximum: 14 days. If no consumer processes the message within this window, it is gone.

Visibility timeout: When a consumer receives a message, SQS hides it from other consumers for this duration (default: 30 seconds, max: 12 hours). This prevents two consumers from processing the same message simultaneously. If the consumer finishes and deletes the message, great. If the consumer fails, the timeout expires and the message reappears for retry. Visibility timeout is not the same as message retention — retention is how long the message exists; visibility timeout is how long it is hidden during processing.

Dead-letter queue (DLQ): A separate SQS queue where messages are sent after a configured number of failed processing attempts (the maxReceiveCount in the redrive policy). DLQs isolate “poison messages” so they do not block the main queue. DLQs are not automatic — you must configure a redrive policy. Messages in a DLQ still have a retention period and must be monitored.

Long polling vs. short polling: Short polling returns immediately (possibly empty). Long polling waits up to 20 seconds for a message to arrive, reducing empty responses and unnecessary API calls. Long polling is almost always preferred — it saves cost and reduces latency.

Delay queues: You can configure a queue-level delay (0–900 seconds) so that new messages are invisible for a set period before consumers can receive them. Message timers can set per-message delays on Standard queues.

Why consumers must delete messages. SQS does not auto-delete messages after delivery. If a consumer receives a message, processes it, but forgets to delete it, the message reappears after the visibility timeout and gets processed again — causing duplicate work.

Planning together: Retention, visibility timeout, and DLQ redrive configuration must be coordinated. If your visibility timeout is too short, messages reappear before workers finish. If retention is too short, messages expire before being processed. If the DLQ maxReceiveCount is too low, messages get sent to the DLQ before the application has enough retry chances.

Worked example — absorbing traffic spikes: An online store runs a flash sale and receives 5,000 order-processing messages in 10 minutes. The order-processing workers can handle 500 messages per minute. Without a queue, the system drops 80% of orders. With SQS, all 5,000 messages sit safely in the queue, and workers process them at a sustainable 500/minute pace. The queue absorbs the burst. However, SQS does not magically make workers faster — if the backlog grows too large relative to consumer capacity, you need to scale out more workers. And those workers must respect downstream limits (database connections, payment API rate limits). The queue provides buffering, not infinite scalability.

Amazon Simple Notification Service (SNS)

What is SNS? Amazon SNS is a fully managed pub/sub (publish–subscribe) messaging service. Instead of buffering messages for one consumer like SQS, SNS fans out a published message to all of its subscribers.

The pub/sub model:

  1. You create an SNS topic — a named channel for messages.
  2. Publishers send messages to the topic.
  3. The topic delivers a copy of each message to every subscriber that is subscribed to it.
  4. Subscribers can be SQS queues, Lambda functions, HTTP/S endpoints, email addresses, SMS, or mobile push notifications.

SNS pushes; SQS pulls. This is a critical distinction. When a publisher sends a message to an SNS topic, SNS immediately pushes that message to all subscribers. There is no polling. With SQS, consumers must actively poll. This difference drives when you choose each service.

Why fanout matters. Suppose an order is placed and three systems need to react: shipping, analytics, and customer notification. Without fanout, the order service would need to call each system individually (tight coupling). With SNS, the order service publishes one message to a topic, and SNS delivers it to all three subscribers. Adding a fourth subscriber later requires zero changes to the order service.

Subscription filters. By default, every subscriber gets every message. Message filtering lets subscribers set filter policies so they only receive messages that match specific attributes. For example, a shipping subscriber can filter for {"order_type": ["physical"]} and ignore digital orders. This reduces unnecessary processing and keeps subscriber logic clean.

SNS is not a durable work queue. SNS delivers messages to subscribers, but if a subscriber is temporarily unavailable, the message may be lost (depending on configuration and the subscription type). SNS supports delivery retries and DLQs for certain subscription types (like SQS and Lambda), but it does not buffer messages the way SQS does. If you need durable, independently processed backlogs for each consumer, use SNS + SQS fanout: publish to an SNS topic, and subscribe separate SQS queues for each consumer. Each queue then acts as an independent, durable buffer.

Retries and DLQs. SNS has its own retry policies for delivery failures. For SQS and Lambda subscriptions, you can configure a DLQ (on the subscription side) to capture messages that SNS failed to deliver. Note that an SNS delivery failure (SNS could not deliver to the subscriber) is different from an SQS processing failure (a consumer could not process a message from a queue).

Permissions matter. The publisher needs permission to publish to the topic. The topic needs permission to deliver to each subscriber. And the subscriber (e.g., an SQS queue) needs a resource policy allowing SNS to send messages to it. A successful publish does not guarantee every subscriber completed its business operation — it means SNS accepted the message and will attempt delivery.

Practical example — order notifications: When an order is placed, the order service publishes to an SNS topic called OrderEvents. Three SQS queues are subscribed: ShippingQueue, AnalyticsQueue, and NotificationQueue. Each queue gets its own copy of the message. The shipping team’s workers poll ShippingQueue, analytics workers poll AnalyticsQueue, and email workers poll NotificationQueue. If the analytics system falls behind, its queue accumulates messages without affecting shipping or email processing. Each consumer has its own backlog, retry behavior, and DLQ.

Amazon EventBridge

What is EventBridge? Amazon EventBridge is a serverless event bus service that receives events and routes them to targets based on rules you define. It is the AWS hub for event-driven architecture — connecting AWS services, SaaS applications, and your own code through structured events.

Core concepts:

  • Event bus: A channel that receives events. Every AWS account has a default event bus that receives events from AWS services. You can also create custom event buses for your applications and partner event buses for SaaS integrations.
  • Event source: What generates the event — an AWS service (e.g., EC2 state change, S3 object creation), a SaaS partner (e.g., Zendesk, Datadog), or your application (custom events).
  • Rule: A filter that matches incoming events against an event pattern. A rule specifies: “when an event with these fields arrives, send it to these targets.”
  • Target: The destination that receives matching events — Lambda functions, SQS queues, SNS topics, Step Functions, ECS tasks, Kinesis streams, and more. A single rule can have multiple targets.

How it works:

  1. An event arrives on the event bus (from AWS, a partner, or your app).
  2. EventBridge evaluates the event against all active rules on that bus.
  3. For every rule whose pattern matches, EventBridge delivers the event to that rule’s configured targets.
  4. Multiple rules can match the same event, sending it to different targets.

Event bus vs. SQS queue. An SQS queue is a durable buffer where consumers poll for work. An EventBridge event bus is a router — it evaluates event content and pushes matching events to targets in near-real-time. EventBridge does not buffer messages for later consumption the way SQS does. If a target is unavailable, EventBridge has its own retry policy and can send failed events to a DLQ, but it is not a persistent work queue.

Event patterns. EventBridge rules use JSON-based event patterns to match on specific fields. For example, you can match all OrderPlaced events where the region is us-east-1 and the amount is greater than 100. This content-based filtering is far more powerful than simple topic-level filtering — you can route events by any combination of fields in the event payload.

AWS service events. Over 90 AWS services automatically emit events to the default event bus. For example, EC2 sends instance state-change events, S3 sends object-creation events, and CodePipeline sends deployment status events. This makes EventBridge the natural choice for reacting to infrastructure changes.

EventBridge vs. EventBridge Scheduler. These are related but distinct. EventBridge event buses route events that happen or are published. EventBridge Scheduler is designed for invoking targets at a scheduled time (one-time or recurring) — like a cron job. Scheduler does not process events from a bus; it triggers actions on a schedule. Do not confuse “schedule a Lambda every 5 minutes” (Scheduler) with “route an OrderPlaced event to Lambda” (event bus).

Retries and DLQs. When EventBridge cannot deliver an event to a target, it retries for up to 24 hours (configurable). If all retries fail, you can configure a DLQ (an SQS queue) to capture undeliverable events. However, EventBridge routing an event to a target does not mean the target completed its operation successfully — a Lambda function might receive the event but fail internally.

Schema registry and discovery. EventBridge can discover and store schemas for events flowing through your bus. This helps developers understand event structures without reading source code. Useful but not a core SAA-C03 topic.

Practical example — event routing: A company’s application publishes structured events to a custom EventBridge bus. Three rules are configured:

  • Rule 1: Event type = OrderPlaced → triggers an order-processing Step Functions workflow.
  • Rule 2: Event type = PaymentFailed → sends an alert to an operations SNS topic.
  • Rule 3: Event type = DeliveryCompleted → invokes a Lambda that sends a customer satisfaction survey.

Each rule independently evaluates every event. If a new event type RefundRequested is added later, a new rule handles it without modifying the existing rules or the publishing application. This is the power of loosely coupled, event-driven design.

Delivery Semantics, Ordering, Retries & Failure Handling

Delivery guarantee terminology:

  • At-most-once: A message is delivered zero or one time. If delivery fails, no retry. Simple but risks data loss.
  • At-least-once: A message is delivered one or more times. Retries ensure delivery, but duplicates are possible. This is what SQS Standard, SNS Standard, and EventBridge provide.
  • Exactly-once: Each message is delivered and processed exactly one time. SQS FIFO provides exactly-once within SQS, but your downstream business operations can still run twice if the delete call fails and the message is redelivered.

Why idempotency is essential. Because at-least-once delivery means duplicates are possible, any consumer that performs a non-reversible operation (charging a credit card, creating a database record) should be idempotent — processing the same message twice must produce the same result. Common techniques: use a unique message/event ID as a deduplication key in your database, or use conditional writes that check whether the operation has already been performed.

Concrete example — duplicate payment protection: A payment service receives an OrderPlaced message from SQS. It charges the customer’s card and writes a record to the database with the order ID. Due to a network hiccup, the consumer fails to delete the message, and SQS redelivers it. Without idempotency, the customer is charged twice. With idempotency, the consumer checks: “Does a payment record for order-12345 already exist?” If yes, it skips the charge and deletes the message. The order ID acts as a deduplication key.

SQS failure handling flow:

  1. Consumer receives a message. Visibility timeout starts.
  2. Consumer fails to process it before the timeout expires.
  3. Message becomes visible again. Another consumer (or the same one) picks it up.
  4. This repeats up to maxReceiveCount times (configured in the redrive policy).
  5. After maxReceiveCount failures, the message is moved to the dead-letter queue (DLQ).
  6. An alarm on DLQ depth alerts the operations team.
  7. After diagnosing and fixing the issue, the team can redrive messages from the DLQ back to the source queue.

DLQ is not automatic recovery. Moving a message to a DLQ isolates the problem but does not fix it. Redriving messages without understanding the original failure can cause the same error again. Replaying from a DLQ also requires idempotency — the consumer may have partially processed the message before it failed.

SNS delivery failures vs. SQS processing failures. An SNS delivery failure means SNS could not push the message to a subscriber (e.g., the SQS queue policy denied it, the HTTP endpoint was down). An SQS processing failure means a consumer received the message but could not complete its work. These are different failure modes with different solutions: fix the subscription configuration for SNS failures; fix the consumer code or downstream dependency for SQS failures.

EventBridge target delivery. EventBridge retries failed target deliveries for up to 24 hours with exponential backoff (configurable). If retries are exhausted, events go to a configured DLQ. But EventBridge does not know whether the target’s internal processing succeeded — it only knows whether it delivered the event to the target. A Lambda function that receives the event but throws an error is a different problem from EventBridge failing to invoke the Lambda.

Message delivery ≠ business completion. Across all three services, successfully sending a message does not mean the business operation finished. The producer knows the message was accepted; it does not know the consumer completed its task. Monitoring (queue depth, error rates, DLQ size, consumer logs) bridges this gap.

One failed consumer should not block unrelated consumers. In an SNS-to-SQS fanout, if the analytics consumer fails, its queue fills up — but the shipping and email consumers continue processing from their own queues. This isolation is a key benefit of the fanout-to-separate-queues pattern.

Filtering, Fanout & Routing Patterns

Pattern 1: Work Queue (SQS)

A producer sends messages to a queue, and competing consumers share the work. Each message is processed by exactly one consumer (under normal delivery). Multiple consumers poll the same queue, and SQS distributes messages among them — like multiple bank tellers serving one line of customers.

  • Good for: background job processing, order fulfillment, image resizing.
  • Retry handling: visibility timeout + DLQ isolate failures.
  • Scaling: add more consumers to process faster, but respect downstream limits.
  • Key distinction: competing consumers is not the same as fanout. Each message goes to one worker, not all workers.

Pattern 2: Pub/Sub Fanout (SNS or SNS + SQS)

A publisher sends a message to an SNS topic, and every subscriber receives a copy. This is broadcast, not competition. If three systems need to react to the same event, each gets its own copy.

  • Good for: notifying multiple independent systems, event broadcasting.
  • SNS-to-SQS fanout: Subscribe separate SQS queues to one SNS topic. Each consumer gets its own durable buffer with independent backlogs, retry behavior, and DLQ. This is the recommended pattern when consumers process at different speeds or have different failure modes.
  • Subscribing fast-changing consumers directly to SNS (e.g., HTTP endpoints) is simpler but does not provide the same durable buffering that separate SQS queues offer.
  • Each consumer’s backlog is isolated — a slow analytics consumer does not block shipping.

Pattern 3: Event Routing (EventBridge)

Events are published to an event bus, and rules evaluate each event’s content to determine which targets receive it. Different downstream actions trigger based on different event fields — this is content-based routing, not just topic-level filtering.

  • Good for: reacting to AWS service events, routing different event types to different workflows, SaaS integration.
  • Rule filtering prevents targets from receiving irrelevant events.
  • Multiple rules can match the same event, sending it to different targets.
  • Targets still need monitoring and failure handling — EventBridge delivering an event does not mean the target completed its job.
  • Event routing creates loosely coupled workflows — add new rules without changing publishers or existing rules.

Security, Scalability & Operational Considerations

IAM and resource-based policies. All three services use IAM for access control. Producers need permission to send messages (e.g., sqs:SendMessage, sns:Publish, events:PutEvents). Consumers need permission to receive and process (e.g., sqs:ReceiveMessage, sqs:DeleteMessage). SQS queues and SNS topics also support resource-based policies that grant cross-account or cross-service access — for example, allowing an SNS topic to send messages to an SQS queue. Always apply least-privilege: a consumer should only access the queues it needs.

Encryption. All three services support encryption at rest using AWS KMS and in-transit encryption via TLS. When using KMS, ensure that producers, consumers, and the services themselves have the required key permissions. A common gotcha: an SNS topic encrypted with a KMS key cannot deliver to an SQS queue unless the queue’s key policy allows SNS to use the key.

Monitoring signals:

  • Queue depth (ApproximateNumberOfMessagesVisible): growing backlog means consumers cannot keep up.
  • Message age (ApproximateAgeOfOldestMessage): old messages indicate stalled processing.
  • DLQ depth: messages in the DLQ indicate repeated processing failures.
  • Error rates: SNS delivery failures and EventBridge failed invocations need their own alarms.

Scaling considerations. Queue-based buffering absorbs spikes, but consumers still have limits. Scaling workers based on queue depth helps, but you must respect downstream constraints: database connection limits, API rate limits, and memory/CPU capacity. Scaling to 1,000 workers that all hit the same database can create worse problems than a growing queue.

Reprocessing and idempotency. When messages are reprocessed (from retries, DLQ redrive, or duplicate delivery), duplicate side effects can occur unless consumers are idempotent. This is an operational requirement, not just a design principle.

Diagnosing problems. A growing queue might be a messaging problem (messages not arriving correctly) or an application problem (consumer code crashing). Check consumer error logs, DLQ contents, and downstream service health before blaming the messaging layer.

When Real Architects Actually Use This

Scenario A: Buffering Order Processing

Business requirement: An e-commerce platform receives bursts of 10,000 orders during flash sales, but order-processing workers can only handle 1,000 per minute.

Recommended service: Amazon SQS (Standard queue)

How it flows: The order API sends each order as a message to an SQS queue. Workers poll the queue, process orders at a sustainable rate, and delete messages after successful processing. A DLQ captures any orders that fail repeatedly.

Why SQS: It provides durable message buffering — no orders are lost during the burst. Workers control their own pace. If a worker crashes, the message reappears after the visibility timeout for another worker to retry.

Failure handling: Visibility timeout must be longer than the longest expected processing time. DLQ maxReceiveCount should allow enough retries (e.g., 3–5) before isolating failures. Monitor queue depth and message age to trigger scaling.

Trade-off: SQS buffers but does not speed up processing. If the burst is sustained, you must scale consumers. Workers must be idempotent because Standard queues can deliver duplicates.

Why not SNS: SNS does not buffer — it pushes immediately and does not provide a durable backlog for workers.

Exam clue: “Decouple producers from consumers” + “handle traffic spikes” + “process asynchronously” = SQS.

Scenario B: Notify Multiple Independent Systems

Business requirement: When a customer places an order, shipping, analytics, and customer communications must all react independently.

Recommended service: SNS topic → three SQS queues

How it flows: The order service publishes to an SNS topic. Three SQS queues subscribe to the topic. Each queue feeds its own set of workers: shipping processes fulfillment, analytics records metrics, and notification sends a confirmation email.

Why SNS + SQS: SNS provides fanout (one message reaches all subscribers). Separate SQS queues give each consumer its own durable backlog, independent retry behavior, and isolated failure handling. If analytics falls behind, shipping and email continue unaffected.

Failure handling: Each queue has its own DLQ. A shipping failure does not affect the analytics queue. SNS subscription filter policies can reduce unnecessary processing if some consumers only care about certain order types.

Trade-off: More queues to manage. Each subscriber receives a copy of every message (unless filtered), so storage and processing costs scale with subscriber count.

Why not SQS alone: A single SQS queue delivers each message to one consumer, not all three. You would need custom fan-out logic.

Exam clue: “Multiple systems need to receive the same message” + “independent processing” = SNS fanout to SQS queues.

Scenario C: Route Different Event Types

Business requirement: A company publishes structured application events (order placed, payment failed, delivery completed) and needs different workflows triggered based on event type and content.

Recommended service: Amazon EventBridge

How it flows: The application publishes events to a custom EventBridge bus. Three rules are configured: OrderPlaced events trigger a Step Functions workflow, PaymentFailed events send an alert via SNS, and DeliveryCompleted events invoke a Lambda for customer surveys.

Why EventBridge: Rules match on event content (type, fields, values) — each rule independently evaluates every event and routes matches to the right target. No consumer receives irrelevant events. Adding a new event type only requires a new rule.

Failure handling: EventBridge retries target delivery with exponential backoff. Configure a DLQ for each rule target to capture undeliverable events.

Trade-off: ~500ms latency (vs. <30ms for SNS). No persistent message buffering — if you need durable work queues, route to SQS as a target.

Why not SQS: SQS has no content-based filtering — every consumer receives every message and must filter in application code.

Exam clue: “Route events based on content/type” + “different actions for different events” = EventBridge.

Scenario D: Preserve Message Ordering

Business requirement: A financial processing application requires that all transactions for the same account are processed in the exact order they occurred.

Recommended service: SQS FIFO queue with account ID as the message group ID.

How it flows: The transaction service sends messages to a FIFO queue with the account ID as the message group ID. All transactions for account-12345 are processed in order. Transactions for account-67890 are processed in parallel (different group).

Why SQS FIFO: Strict ordering within message groups ensures that deposit-then-withdrawal for the same account happens in the correct sequence. Deduplication prevents double-processing of the same transaction within a 5-minute window.

Failure handling: If a message fails, no subsequent messages in that message group are delivered until the failed message is successfully processed or moved to the DLQ. Consumers must still be idempotent — FIFO deduplication protects against duplicate enqueueing, but downstream operations (database writes) need their own protection.

Trade-off: Lower throughput than Standard queues (up to 70K TPS with high-throughput mode). Blocking within a message group on failure means a poison message can stall all messages for that group until resolved.

Exam clue: “Process in order” + “per entity” = SQS FIFO with entity ID as message group ID.

Scenario E: Isolate a Slow Consumer

Business requirement: A notification system has a fast operational consumer (responds in milliseconds) and a slow reporting consumer (batch processing, takes minutes). The slow consumer must not delay the fast one.

Recommended service: SNS topic → two separate SQS queues

How it flows: Events publish to an SNS topic. The fast consumer’s SQS queue is processed immediately. The slow consumer’s SQS queue accumulates messages and processes them in batches without affecting the fast queue.

Why separate queues: Each queue provides an independent backlog. The slow consumer’s growing queue does not block, slow, or affect the fast consumer’s queue. Each has its own visibility timeout, DLQ, and scaling behavior.

Trade-off: Two queues to manage instead of one. Both receive copies of all messages, so storage costs are higher.

Exam clue: “One slow consumer should not affect another” = separate SQS queues via SNS fanout.

Scenario F: Handle Poison Messages

Business requirement: A worker repeatedly fails to process a specific malformed message, causing it to cycle through the queue and delay other messages.

Recommended service: SQS + DLQ with redrive policy

How it flows: The redrive policy sets maxReceiveCount to 3. After three failed processing attempts, SQS automatically moves the message to the DLQ. A CloudWatch alarm on DLQ depth alerts the team. After fixing the consumer or the data, the team redrives messages from the DLQ back to the source queue.

Why DLQ: Without a DLQ, the poison message cycles indefinitely through the queue, consuming worker capacity and blocking processing of healthy messages (especially in FIFO queues). The DLQ isolates the problem while healthy messages continue processing.

Failure handling: DLQ messages still have a retention period — they expire too if not addressed. Redriving requires that the root cause is fixed and that consumers are idempotent (the message may have been partially processed before each failure).

Trade-off: A DLQ does not fix the problem — it only quarantines it. Without monitoring and alerting, messages can silently expire in the DLQ.

Exam clue: “Messages fail repeatedly” + “isolate problem messages” = SQS DLQ with redrive policy.

Scenario G: Respond to AWS Service Events

Business requirement: A company wants to automatically remediate when an EC2 instance changes to a “stopped” state in production, and log all security group changes for auditing.

Recommended service: Amazon EventBridge

How it flows: AWS services emit events to the default EventBridge bus. Rule 1 matches EC2 instance state-change events where the state is “stopped” and the tag “env” = “production” → invokes a remediation Lambda. Rule 2 matches AWS CloudTrail events for security group changes → sends to an audit SQS queue.

Why EventBridge: AWS service events are natively available on the default bus. Rules provide content-based filtering without any custom plumbing. Each rule operates independently.

Trade-off: Event patterns must match the exact structure of AWS service events — test patterns carefully.

Exam clue: “React to AWS service state changes” + “automate response” = EventBridge.

Scenario H: Schedule a Future Task

Business requirement: A company needs to invoke a Lambda function every day at 2 AM to generate reports, and also send a one-time reminder email 48 hours after a customer signs up.

Recommended service: EventBridge Scheduler

How it flows: A recurring schedule invokes the report Lambda daily at 2 AM UTC. For each new customer, the application creates a one-time schedule set for 48 hours in the future, targeting a Lambda that sends the reminder.

Why Scheduler: Scheduler is purpose-built for time-based invocations (cron and one-time). It supports millions of schedules with at-least-once invocation. It is not an event bus — it triggers actions at a specific time, not in response to published events.

Trade-off: Scheduler invocations are at-least-once, so the target must handle duplicates. No content-based routing — use event buses for that.

Why not an event bus: An event bus routes events that happen; it does not watch the clock and fire at a scheduled time.

Exam clue: “At a scheduled time” or “recurring daily/weekly” = EventBridge Scheduler, not an event bus.

Scenario I: Scale Consumers Safely

Business requirement: A company’s SQS queue backlog is growing. The team wants to increase processing capacity by adding more consumer instances.

Recommended approach: Auto Scaling group with a scaling policy based on the ApproximateNumberOfMessagesVisible CloudWatch metric.

How it flows: When queue depth exceeds a threshold, Auto Scaling launches additional consumer instances. As the backlog drains, instances scale back down.

Why metric-based scaling: Queue depth is a direct signal of workload demand. Scaling in response to it matches consumer capacity to actual message volume.

Failure handling: More consumers does not always help. If the bottleneck is downstream (database connections, API rate limits), adding consumers can create new failures (connection pool exhaustion, throttling). Scale the downstream resource too, or throttle consumers.

Trade-off: Auto Scaling adds and removes instances with some delay. During sudden spikes, there is a lag before new capacity comes online. Over-aggressive scaling can overwhelm downstream systems.

Exam clue: “Queue backlog growing” + “scale processing” = scale consumers based on SQS queue metrics, but consider downstream limits.

Scenario J: Prevent Duplicate Payment Effects

Business requirement: A payment processing consumer may receive the same order message more than once (at-least-once delivery). Charging a customer twice is unacceptable.

Recommended approach: Application-level idempotency using the order ID as a deduplication key.

How it flows: The consumer receives a message with order ID ord-98765. Before charging, it checks a database: “Has ord-98765 already been charged?” If yes, skip and delete the message. If no, process the payment, record it, then delete the message. The database check and insert should use a conditional write or unique constraint to prevent race conditions.

Why idempotency: No messaging service can guarantee that your downstream business operations execute exactly once across retries, network failures, and distributed systems. SQS FIFO deduplication prevents duplicate enqueueing within a 5-minute window, but it does not protect against a consumer processing a message, failing to delete it, and receiving it again. Only the application can prevent duplicate business effects.

Trade-off: Idempotency adds complexity (deduplication table, conditional writes, key management) but is essential for any operation where duplicates cause real harm.

Exam clue: “Prevent duplicate processing” + “at-least-once delivery” = application-level idempotency. Do not rely solely on FIFO deduplication for business-critical uniqueness.

SQS vs SNS vs EventBridge — Architecture Patterns

Key takeaway: SQS buffers work for competing consumers (one message → one worker). SNS broadcasts to all subscribers (one message → all subscribers), ideally through separate SQS queues for durable independent processing. EventBridge routes events by content to the right targets using rules (different events → different actions).

Exam Gotchas

1. Choosing SNS when the requirement is durable message buffering.

Wrong assumption: SNS can hold messages until workers are ready.

Correct behavior: SNS pushes immediately and does not buffer. Use SQS for durable work queues.

Exam clue: “Buffer,” “retain messages,” “workers process later” = SQS, not SNS.

Memory rule: SNS pushes; SQS buffers.

2. Choosing SQS when the requirement is fanout to multiple independent systems.

Wrong assumption: A single SQS queue delivers messages to all consumers.

Correct behavior: SQS delivers each message to one consumer (competing consumers). For fanout, use SNS → multiple SQS queues.

Exam clue: “Multiple systems must each receive the same message” = SNS fanout.

Memory rule: SQS = one consumer per message. SNS = all subscribers get a copy.

3. Choosing SNS instead of EventBridge for content-based routing.

Wrong assumption: SNS filter policies can handle complex event-field routing.

Correct behavior: SNS filters on message attributes (limited). EventBridge matches on any JSON field with complex patterns.

Exam clue: “Route based on event type/content/fields” = EventBridge.

Memory rule: Simple attribute filtering = SNS. Deep content-based routing = EventBridge.

4. Confusing EventBridge event buses with EventBridge Scheduler.

Wrong assumption: EventBridge Scheduler routes events from an event bus.

Correct behavior: The event bus routes events that happen. Scheduler invokes targets at scheduled times (cron/one-time).

Exam clue: “At 2 AM daily” = Scheduler. “When an order event arrives” = event bus.

Memory rule: Bus = reacts to events. Scheduler = reacts to the clock.

5. Assuming publishing a message means consumers completed their work.

Wrong assumption: A successful Publish/SendMessage means the business operation finished.

Correct behavior: It means the service accepted the message. Consumer processing is a separate, asynchronous step.

Memory rule: Message accepted ≠ business completed.

6. Assuming Standard SQS queues guarantee strict ordering.

Correct behavior: Standard queues offer best-effort ordering. For strict ordering, use SQS FIFO with message group IDs.

Memory rule: Standard = best-effort order. FIFO = strict order per group.

7. Assuming SQS Standard delivers every message exactly once.

Correct behavior: Standard queues provide at-least-once delivery. Duplicates are possible. Consumers must be idempotent.

Memory rule: Standard = at-least-once = duplicates possible.

8. Assuming FIFO makes downstream business effects exactly once automatically.

Correct behavior: FIFO deduplication prevents duplicate enqueueing (5-min window). If a consumer processes a message, fails to delete it, and receives it again, the business operation can repeat.

Memory rule: FIFO dedup = enqueueing protection. Business idempotency = your responsibility.

9. Confusing visibility timeout with message retention.

Correct behavior: Visibility timeout = how long a message is hidden during processing (default 30s, max 12h). Retention = how long the message exists in the queue (default 4 days, max 14 days).

Memory rule: Visibility = processing window. Retention = message lifespan.

10. Forgetting to delete successfully processed SQS messages.

Correct behavior: SQS does not auto-delete after delivery. Undeleted messages reappear after the visibility timeout and get reprocessed.

Memory rule: Receive → process → delete. Skip the delete = duplicate processing.

11. Assuming failed messages go to a DLQ automatically.

Correct behavior: A DLQ requires explicit configuration (redrive policy with maxReceiveCount). Without it, failed messages cycle forever until retention expires.

Memory rule: No redrive policy = no DLQ routing.

12. Confusing SQS processing failure with SNS delivery failure.

Correct behavior: SQS failure = consumer could not process. SNS failure = SNS could not deliver to subscriber. Different problems, different DLQ configurations.

Memory rule: SQS DLQ = processing failures. SNS DLQ = delivery failures.

13. Treating DLQ as automatic recovery.

Correct behavior: A DLQ quarantines problem messages. It does not fix or reprocess them. You must diagnose the failure, fix it, then redrive. Redriving without fixing = same failure again.

Memory rule: DLQ = quarantine. Fix first, redrive second.

14. Assuming SNS subscribers automatically have independent durable backlogs.

Correct behavior: SNS pushes to subscribers. For durable, independent backlogs, subscribe separate SQS queues to the SNS topic.

Memory rule: Durable per-subscriber backlogs = SNS → separate SQS queues.

15. Confusing competing consumers with pub/sub fanout.

Correct behavior: SQS competing consumers: one message → one worker. SNS fanout: one message → all subscribers.

Memory rule: Competing = distribute. Fanout = broadcast.

16. Assuming EventBridge routes to only one target per event.

Correct behavior: Multiple rules can match the same event, each sending it to different targets. A single rule can also have up to five targets.

Memory rule: One event can trigger multiple rules and multiple targets.

17. Assuming EventBridge matching a rule means the target completed its operation.

Correct behavior: EventBridge delivers the event to the target. Whether the target succeeds internally is a separate concern.

Memory rule: Rule matched ≠ target succeeded.

18. Ignoring event-pattern details when a rule fails to match.

Correct behavior: Event patterns must match the exact field names, structure, and values. A typo or wrong nesting means no match — events silently pass through.

Memory rule: No match = no delivery = no error. Test patterns carefully.

19. Assuming every service has identical retry and DLQ behavior.

Correct behavior: SQS retries via visibility timeout. SNS retries per delivery policy. EventBridge retries with exponential backoff up to 24h. Each has different DLQ configuration.

Memory rule: Retry behavior is service-specific. Know the differences.

20. Scaling consumers without considering downstream capacity.

Correct behavior: More workers + same database connection limit = connection pool exhaustion. Scale downstream resources too, or throttle consumers.

Memory rule: Scale consumers AND downstream capacity together.

21. Assuming visibility timeout prevents all duplicate processing.

Correct behavior: Visibility timeout prevents simultaneous processing by multiple consumers, but a consumer that finishes just as the timeout expires can still see the message redelivered to another consumer.

Memory rule: Visibility timeout reduces duplicates but does not eliminate them.

22. Forgetting idempotency when retries can trigger duplicate business effects.

Correct behavior: At-least-once delivery + no idempotency = duplicate charges, duplicate emails, duplicate records.

Memory rule: At-least-once = must design for idempotency.

23. Using FIFO when Standard satisfies the requirements.

Correct behavior: FIFO has lower throughput and higher cost. If ordering is not required, Standard is the better choice.

Exam clue: “Highest throughput” + “no ordering requirement” = Standard queue.

Memory rule: Don’t pay for FIFO ordering you don’t need.

24. Choosing a queue when the requirement is event-content filtering and routing.

Correct behavior: SQS has no content filtering. If the requirement is “route different events to different targets based on content,” use EventBridge.

Memory rule: Content-based routing = EventBridge. Buffered processing = SQS.

Practice Questions — SQS vs SNS vs EventBridge

Q1. A media company’s video-processing application receives thousands of upload requests during peak hours. Each uploaded video must be transcoded asynchronously by a fleet of EC2 worker instances. If a worker crashes during transcoding, the job must be retried automatically. Failed jobs that exceed five retry attempts must be isolated for investigation without blocking other jobs. Which architecture meets these requirements?

  • A. Publish upload events to an SNS topic. Subscribe the worker instances directly to the topic so each worker receives every job.
  • B. Send upload messages to an SQS Standard queue with a visibility timeout longer than the maximum transcoding time. Configure a dead-letter queue with a maxReceiveCount of 5. Workers poll the queue, transcode, and delete the message on success.
  • C. Send upload events to an EventBridge custom event bus. Configure a rule that invokes each worker instance directly as a target.
  • D. Send upload messages to an SQS FIFO queue with message group ID set to a single static value so all jobs are processed in strict order.

Correct Answer: B

SQS Standard provides durable message buffering, automatic retry via visibility timeout, and DLQ isolation for repeatedly failing jobs. Workers poll at their own pace, and if one crashes, the message reappears after the visibility timeout for another worker. A is wrong — SNS pushes every message to every subscriber; you need one worker per job, not all workers processing every job. C is wrong — EventBridge routes events but does not provide durable buffering or consumer-controlled polling. D is wrong — a single static message group ID forces strict serial processing, destroying parallelism; video transcoding does not require ordering.

Memory rule: “Async workers” + “retry on failure” + “isolate poison messages” = SQS queue + DLQ.

Q2. An e-commerce company needs to notify three independent downstream systems whenever an order is placed: a shipping service, an analytics pipeline, and a customer notification service. Each system processes at a different speed, and a failure in one system must not affect the others. Each system needs its own retry logic and failure isolation. Which architecture meets these requirements with the LEAST operational overhead?

  • A. Send the order event to a single SQS queue. Have all three systems poll the same queue.
  • B. Send the order event to three separate SQS queues from the order service, one for each downstream system.
  • C. Publish the order event to an SNS topic. Subscribe three separate SQS queues (one per system) to the topic. Each system polls its own queue independently.
  • D. Publish the order event to an SNS topic. Subscribe each downstream system’s HTTP endpoint directly to the topic.

Correct Answer: C

The SNS-to-SQS fanout pattern delivers a copy of each message to all three SQS queues. Each system polls its own queue independently, with its own visibility timeout, DLQ, and retry behavior. A failure in analytics does not affect shipping. A is wrong — a single SQS queue delivers each message to only one consumer, not all three. B is wrong — it works but requires the order service to send to three queues (tighter coupling and more code changes when adding a fourth system). C uses SNS for decoupled fanout with less operational overhead. D is wrong — direct HTTP subscriptions do not provide durable buffering; if an endpoint is down, messages may be lost without separate DLQ configuration.

Memory rule: “One event, multiple independent consumers, each with own retry” = SNS → separate SQS queues.

Q3. A financial services company publishes structured application events to a central system. When an event has type: “FraudDetected”, it must trigger a security investigation Lambda function. When an event has type: “TransactionCompleted” and amount greater than 10,000, it must send an alert to an operations SNS topic. Other event types require no action. Which service provides this content-based routing with the LEAST custom code?

  • A. Send all events to an SQS queue. A single Lambda consumer reads every message and uses application logic to route based on event type and amount.
  • B. Publish all events to an SNS topic with message filtering. Create subscription filter policies that match on event type and numeric amount thresholds.
  • C. Send events to an Amazon EventBridge custom event bus. Create one rule matching type: “FraudDetected” targeting the security Lambda, and another rule matching type: “TransactionCompleted” with a numeric condition on amount targeting the operations SNS topic.
  • D. Use Amazon EventBridge Scheduler to poll the event source every minute and invoke the appropriate targets based on the event content.

Correct Answer: C

EventBridge event patterns support matching on any JSON field, including numeric conditions (greater-than, less-than). Two rules handle both routing requirements with zero custom code. A is wrong — it works but requires custom routing logic inside a Lambda, adding code to maintain. B is wrong — SNS filter policies support basic attribute matching but do not natively support numeric greater-than conditions on message body fields the way EventBridge patterns do. D is wrong — EventBridge Scheduler triggers actions at scheduled times; it does not evaluate event content or route events from an event bus.

Memory rule: “Route by event content/fields” + “least custom code” = EventBridge rules with event patterns.
