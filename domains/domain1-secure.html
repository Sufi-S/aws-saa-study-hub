Learn from Zero

What Is IAM and Why Does AWS Need It?

When you first create an AWS account, you get a single root user with unlimited access to every service and resource. That is extremely dangerous for daily work. AWS Identity and Access Management (IAM) lets you create separate identities — users, groups, and roles — each with only the permissions they need. It is a free, global service (not region-specific) and underpins every interaction with AWS.

Core exam concept: IAM answers two questions for every API call — Who are you? (authentication) and What are you allowed to do? (authorization). Authentication proves identity; authorization checks permissions. Every AWS API request goes through both steps.

Users, Groups, Roles, and Principals

A principal is any entity that can make a request to AWS. The three main kinds of principals are:

  • IAM Users — represent a single person or application. Each user has permanent credentials (a password for the console or access keys for the API). Because the credentials are long-lived, they are a security risk if leaked.
  • IAM Groups — a collection of IAM users. You attach policies to the group, and every user in the group inherits those permissions. Groups cannot be nested, and a group cannot be a principal in a policy. Groups are purely an organizational convenience for managing user permissions.
  • IAM Roles — an identity that provides temporary credentials via AWS STS. Roles are not tied to a single person or machine. Anyone (or anything) that the role trusts can assume it and receive short-lived credentials. Roles are the recommended way for applications, services, and cross-account access.
Exam tip: Whenever the exam says "no long-term credentials" or "most secure", the answer almost always involves an IAM role, not an IAM user.

Authentication vs Authorization

Authentication is proving who you are. For an IAM user, that means signing in with a password or presenting access keys. For a role, it means calling STS and receiving temporary credentials. Authorization happens after authentication — AWS evaluates the policies attached to your identity (and to the resource) to decide whether your specific API call is allowed or denied.

IAM Policies — The Permission Rules

A policy is a JSON document that describes what actions are allowed or denied on which resources. Policies are the mechanism for authorization in AWS.

Identity-Based vs Resource-Based Policies

  • Identity-based policies are attached to a user, group, or role. They say: "This identity can do X on resource Y."
  • Resource-based policies are attached directly to a resource (for example, an S3 bucket policy or an SQS queue policy). They say: "Principal Z can do X on this resource." Resource-based policies have a Principal field to specify who they apply to.

When an identity-based policy and a resource-based policy in the same account both grant access, either one alone is enough — their permissions are combined (a union). For cross-account access, both sides must explicitly allow the action: the identity's account must allow the call, and the resource's account must allow the principal.

The Principle of Least Privilege

Grant only the minimum permissions needed to perform a task. Start with no permissions and add only what is required. AWS provides tools like IAM Access Analyzer and the last-accessed data to help you tighten policies over time.

Allow, Deny, and How Policy Evaluation Works

Understanding the deny/allow logic is critical for the exam.

  1. By default, all requests are implicitly denied (no permission = no access).
  2. An Allow in an applicable policy overrides the implicit deny.
  3. An explicit Deny in any applicable policy always overrides any Allow.
The golden rule: Explicit Deny > Allow > Implicit Deny. If any policy says "Effect": "Deny" for an action, that action is denied — period. No amount of Allow statements elsewhere can override it.

AWS evaluates all applicable policies together: identity-based policies, resource-based policies, permissions boundaries, SCPs, and session policies. The effective permission is the intersection of what is allowed across all of these layers (except for same-account resource-based policies, which are unioned with identity-based policies).

IAM Roles vs IAM Users — Why Temporary Credentials Win

IAM users have long-term access keys — an access key ID and a secret access key that never change until you manually rotate them. If these keys are committed to source code, leaked in logs, or stolen, an attacker has persistent access until you discover and revoke them.

IAM roles issue temporary security credentials through STS. These credentials have an access key, a secret key, and a session token, and they expire automatically (from 15 minutes to 12 hours, depending on how they were obtained). If temporary credentials are leaked, the window of exposure is limited to their lifetime.

What Is AWS STS?

AWS Security Token Service (STS) is the service that issues temporary security credentials. When someone (or something) assumes an IAM role, STS is what actually creates and returns the short-lived credentials. STS itself does not grant permissions — the role's permission policy determines what the caller can do once they have the credentials.

AssumeRole, Trust Policies, and Permission Policies

Every IAM role has two policies that work together:

  1. Trust policy (also called the role's assume role policy) — defines who is allowed to call sts:AssumeRole for this role. This is a resource-based policy on the role itself.
  2. Permission policy — defines what the role can do once assumed. This is an identity-based policy attached to the role.

Think of the trust policy as the door lock (who can get in) and the permission policy as the access badge (what they can do once inside).

When you call sts:AssumeRole, STS checks whether you are listed in the trust policy. If yes, it returns temporary credentials whose permissions are defined by the role's permission policy.

Cross-Account Access

A common pattern is granting an identity in Account A access to resources in Account B. This requires:

  1. A role in Account B with a trust policy that allows the principal in Account A to assume it.
  2. A permission policy on that role specifying what it can do in Account B.
  3. The principal in Account A must also have an IAM policy allowing sts:AssumeRole on the role in Account B (unless the calling principal is the root user of Account A, which is implicitly trusted by the trust policy).

Both accounts must cooperate — neither side can unilaterally grant cross-account access through roles alone.

IAM Roles for EC2 and Other AWS Workloads

When an application runs on EC2, you attach an IAM role to the instance through an instance profile. The EC2 instance metadata service automatically provides temporary credentials to any application running on the instance. The credentials are rotated automatically before they expire. The application never sees or stores long-term keys.

The same pattern applies to Lambda (execution role), ECS tasks (task role), and other AWS compute services. The key idea: the compute service manages credential delivery so your application code never handles secrets.

IAM Identity Center and Federation

IAM Identity Center (formerly AWS SSO) is the recommended way to give human users (employees) access to multiple AWS accounts and business applications from a single portal. Instead of creating IAM users in every account, you connect your corporate identity provider (Active Directory, Okta, etc.) to Identity Center, and users sign in once to access all their accounts.

Federation is the broader concept of letting external identities access AWS without creating IAM users. It includes SAML 2.0 federation, web identity federation (for mobile/web apps using Google, Facebook, or Amazon Cognito), and IAM Roles Anywhere (for on-premises workloads with X.509 certificates).

Exam relevance: If a question asks about providing workforce access to multiple accounts, the answer is IAM Identity Center. If a question asks about mobile or web application users signing in with social providers, the answer involves Cognito or web identity federation. You rarely need to know deep federation details — just which service matches which scenario.

MFA, Access Keys, and Credential Rotation

  • Multi-Factor Authentication (MFA) adds a second factor (usually a virtual device like Google Authenticator or a hardware key) to sign-in. AWS strongly recommends MFA for the root user and all human users. You can also write IAM policies that require MFA for sensitive actions (e.g., deleting S3 objects with MFA Delete, or stopping EC2 instances).
  • Access key rotation: If you must use long-term access keys (for example, for a legacy on-premises application), rotate them regularly. Create a new key, update the application, verify it works, then deactivate and delete the old key.
  • Never hard-code credentials: Embedding access keys in source code, configuration files, or AMIs is a critical security risk. Use IAM roles (for AWS workloads) or Secrets Manager / Parameter Store (for third-party credentials).

Permissions Boundaries (Supplementary)

A permissions boundary is an advanced feature that sets the maximum permissions an IAM user or role can have. It does not grant permissions on its own — it limits what identity-based policies can grant. It is conceptually similar to an SCP but applied at the individual identity level instead of the account level.

On the exam, permissions boundaries most often appear in questions about delegated administration: allowing a developer to create roles without exceeding their own privilege level.

When Real Architects Actually Use This

EC2 Application Accessing S3 Without Storing Keys

Requirement: A Python application on EC2 needs to read objects from an S3 bucket. The security team says no credentials in code or config files.

Solution: Create an IAM role with a policy allowing s3:GetObject on the target bucket. Attach the role to the EC2 instance through an instance profile. The AWS SDK automatically retrieves temporary credentials from the instance metadata service — no code changes required.

Why not an IAM user with access keys? Access keys are permanent, must be manually rotated, and are a liability if the instance is compromised. The role's temporary credentials rotate automatically and expire within hours.

Granting a Developer Read-Only Access

Requirement: A junior developer needs to view CloudWatch logs and read S3 objects in a staging account, but must not modify any production resources.

Solution: Create an IAM group called ReadOnlyDevelopers. Attach the AWS managed policy ReadOnlyAccess. Add the developer's IAM user to this group. For extra safety, attach an SCP at the OU level that denies write actions to production resources.

Why a group and not an inline policy on the user? Groups make policy management scalable. When the next developer joins, you add them to the group instead of duplicating policies. Managed policies are maintained by AWS and cover new services automatically.

Two AWS Accounts Sharing Access to a Resource

Requirement: The analytics team in Account B needs to read data from an S3 bucket owned by Account A.

Solution (role-based): Create a role in Account A with a trust policy allowing Account B's specific IAM role or user to assume it, and a permission policy allowing s3:GetObject on the bucket. In Account B, grant the analytics role permission to call sts:AssumeRole on the Account A role.

Alternative (bucket policy): Add a resource-based policy on the S3 bucket in Account A that directly grants s3:GetObject to the Account B principal. This is simpler for S3 specifically, but role-based cross-account access is more general and works for any service.

Why not share access keys between accounts? Sharing long-term credentials across organizational boundaries is an audit nightmare and a security risk. Cross-account roles provide traceable, temporary, revocable access.

Application Assuming a Role in Another Account

Requirement: A deployment pipeline in Account A (DevOps) needs to update Lambda functions in Account B (Production).

Solution: Create a DeploymentRole in Account B with a trust policy that allows the pipeline's role in Account A to assume it, and a permission policy with lambda:UpdateFunctionCode. The pipeline calls sts:AssumeRole, receives temporary credentials for Account B, and uses those to deploy.

Why this matters: The trust policy in Account B explicitly controls which external principals can access its resources. If the DevOps team is restructured or the pipeline role changes, Account B can update the trust policy without touching any of its own internal permissions.

Centralized Workforce Access to Multiple Accounts

Requirement: A company with 15 AWS accounts needs employees to sign in once and access only the accounts relevant to their role.

Solution: Set up IAM Identity Center connected to the corporate Active Directory. Define permission sets (collections of policies) and assign them to user groups for specific accounts. Employees sign in to the Identity Center portal and see only their authorized accounts.

Why not create IAM users in each account? With 15 accounts, you would need to manage hundreds of users, rotate credentials in every account, and handle offboarding in 15 places. Identity Center provides a single point for access management, auditing, and revocation.

Restricting Permissions Despite Broad Access Grants

Requirement: A security team needs to ensure that even users with AdministratorAccess cannot delete DynamoDB tables in production.

Solution: Attach an SCP (Service Control Policy) to the production OU that contains an explicit Deny for dynamodb:DeleteTable. Because explicit deny always wins, no identity-based policy in any member account can override it.

Why SCPs and not just IAM policies? IAM policies are managed per account. A determined admin in a member account could remove the deny from their own user. SCPs are controlled at the organization level and cannot be overridden by anyone in the member account — they are a guardrail from above.

SAA-C03 Exam Gotchas

Confusing the Trust Policy with the Permission Policy

The trust policy decides who can assume the role. The permission policy decides what the role can do. If a question says an application "cannot assume a role," the problem is in the trust policy. If it says the application "assumed the role but gets Access Denied," the problem is in the permission policy (or a deny elsewhere).

Exam clue: Look for whether the error happens at the assume step or the use step.

Assuming an IAM User Is Always the Right Choice

IAM users are appropriate for human console access in simple setups, but for applications, the answer is almost always an IAM role. If the question mentions EC2, Lambda, ECS, or any AWS compute service, use a role — not an IAM user with embedded access keys.

Exam clue: Watch for phrases like "most secure," "best practice," or "no long-term credentials." These all point to roles.

Confusing Long-Term Access Keys with STS Temporary Credentials

Access keys (an access key ID and secret access key) are permanent and belong to IAM users. Temporary credentials include those two plus a session token, and they expire. When the exam asks about "temporary security credentials," it means STS-issued credentials from a role, not IAM user access keys.

Exam clue: If a question mentions "session token" or "expiring credentials," the answer involves STS and roles.

Assuming Allow Always Grants Access

An Allow does not guarantee access if an explicit Deny exists anywhere in the evaluation chain — SCPs, permissions boundaries, identity policies, or resource policies. Explicit Deny always wins.

Exam clue: If a question describes a user who "has Allow * but still gets denied," check for an SCP or permissions boundary with an explicit Deny.

Forgetting Both Sides of Cross-Account Access

For cross-account role assumption, you need the trust policy in the target account to allow the caller, and the caller's own account must have an IAM policy allowing sts:AssumeRole on the target role. Missing either side causes access denial.

Exam clue: Cross-account questions often have one answer that only configures one side. That answer is incomplete and wrong.

Assuming Attaching a Policy to a User Grants Access Everywhere

An identity-based policy on a user grants access only within the boundaries set by applicable SCPs, permissions boundaries, and session policies. Also, for cross-account resource access, the resource account must also grant access. Attaching AdministratorAccess to a user does not bypass organizational guardrails in member accounts.

Exam clue: Questions about Organizations and SCPs often test this. "Has AdministratorAccess but cannot…" means an SCP or boundary is restricting.

Confusing Authentication with Authorization

Authentication = proving identity (login, keys, MFA). Authorization = checking permissions (policies). A user can be authenticated (successfully signed in) but still unauthorized (denied by policy) for a specific action. These are separate steps.

Exam clue: If a question says a user "can sign in but cannot access a resource," the issue is authorization (policy), not authentication.

Hard-Coding Credentials in Application Code

Storing AWS access keys in source code, environment variables baked into AMIs, or committed to version control is a critical security vulnerability. If the code is leaked, the keys provide long-lived access. The exam considers this a security anti-pattern.

Exam clue: Any answer choice that mentions "embed access keys in the code" or "store credentials in the application config" is almost always the wrong answer.

Forgetting Role Chaining Limits

When a role assumes another role (role chaining), the maximum session duration is capped at 1 hour, regardless of the role's configured maximum. Direct AssumeRole calls can last up to 12 hours, but chained calls cannot.

Exam clue: If a question mentions a session "timing out after 1 hour" despite the role having a longer max duration, role chaining is the cause.

Scenario-Based Practice Questions

Practice Questions — IAM & STS

Q1. A financial services company has two AWS accounts: a Development account and a Production account. The DevOps team in the Development account needs to deploy CloudFormation stacks in the Production account. The security team requires that no long-term credentials are shared between accounts and that Production retains full control over what the DevOps team can do. What is the MOST secure solution?

  • A. Create an IAM user in the Production account and share the access keys with the DevOps team securely via Secrets Manager.
  • B. Create an IAM role in the Production account with a trust policy allowing the DevOps role in the Development account to assume it, and attach a permission policy scoped to CloudFormation actions.
  • C. Create an S3 bucket policy in the Production account that grants the Development account full access to all resources.
  • D. Attach AdministratorAccess to the DevOps team's IAM users in the Development account and use an SCP to allow cross-account access.

Correct Answer: B

A cross-account IAM role in Production with a trust policy referencing the Development account's DevOps role provides temporary credentials with no long-term key sharing. The Production account retains full control through both the trust policy (who can assume) and the permission policy (what they can do).

Why not the others?

  • A uses long-term access keys, which violates the "no long-term credentials" requirement and creates a risk if the keys are leaked.
  • C is an S3-specific solution and does not address CloudFormation stack deployment. Also, "full access to all resources" violates least privilege.
  • D gives the DevOps team admin access (violates least privilege) and SCPs do not enable cross-account access — they only restrict permissions within an organization.

Key exam clue: "No long-term credentials between accounts" + "target account controls permissions" = cross-account IAM role with a trust policy.

Q2. A company has an IAM policy attached to a developer's IAM user that grants "Effect": "Allow", "Action": "s3:*", "Resource": "*". However, the developer cannot delete objects from a specific S3 bucket used for compliance logs. A permissions boundary is attached to the developer's user that allows all S3 actions. What is the MOST likely cause?

  • A. The S3 bucket has a bucket policy with an explicit Deny for s3:DeleteObject for all principals.
  • B. The permissions boundary overrides the identity-based policy and blocks deletion by default.
  • C. The developer's access keys have expired and STS is not issuing new credentials.
  • D. The IAM policy only applies to resources within the same Region as the IAM user.

Correct Answer: A

The identity-based policy allows all S3 actions and the permissions boundary also allows all S3 actions, so the block is not coming from either of those. A bucket policy with an explicit Deny on s3:DeleteObject would override the Allow — explicit Deny always wins, regardless of what identity-based policies permit.

Why not the others?

  • B is wrong because the permissions boundary allows all S3 actions, so it is not restricting anything here. Permissions boundaries limit what identity policies can grant — they don't override allows from resource policies.
  • C is wrong because the developer is an IAM user with long-term access keys, not using STS temporary credentials. Also, if keys had expired, all actions would fail, not just delete.
  • D is wrong because IAM policies are global — they are not region-specific.

Key exam clue: "Has Allow for an action but still gets denied on a specific resource" = look for an explicit Deny in a bucket/resource policy or SCP.

Q3. A startup is building a mobile application that allows users to sign in with their Google accounts and then upload photos to a specific S3 bucket. The application has millions of users. The company wants to avoid managing individual IAM users. Which approach should the solutions architect recommend?

  • A. Create an IAM user for each mobile app user and distribute access keys through the application.
  • B. Use Amazon Cognito identity pools to federate Google sign-in, and assign an IAM role with S3 upload permissions to authenticated users.
  • C. Create a single IAM user with S3 permissions and embed the access keys in the mobile application code.
  • D. Use IAM Identity Center to manage mobile app user access to the S3 bucket.

Correct Answer: B

Amazon Cognito identity pools provide web identity federation. Users sign in with Google (or other providers), and Cognito exchanges the identity token for temporary AWS credentials via STS. The IAM role attached to the identity pool defines what authenticated users can do (in this case, upload to S3). No IAM users are needed for the mobile users.

Why not the others?

  • A creates millions of IAM users — impractical, hard to manage, and IAM has a default limit of 5,000 users per account. Also distributes long-term credentials.
  • C embeds long-term credentials in client code — anyone who decompiles the app gets full S3 access. This is a critical security vulnerability.
  • D is designed for workforce (employee) access, not customer-facing mobile app users. It does not support social provider federation the way Cognito does.

Key exam clue: "Mobile/web app users" + "social sign-in" + "avoid IAM users" = Amazon Cognito identity pools with an IAM role.

AWS Organizations & SCPs

Multi-account governance, organizational structure, and service control policies.

Learn from Zero

What Is AWS Organizations and Why Use Multiple Accounts?

AWS Organizations is a free service that lets you group multiple AWS accounts under a single umbrella and manage them centrally. Instead of treating each account as an isolated island, Organizations gives you a hierarchy with shared billing, account-wide security guardrails, and centralized governance.

Why not put everything in one account? A single account means every team shares the same IAM namespace, the same service quotas, and the same blast radius. If a developer accidentally deletes a production database, there is no account boundary to contain the damage. Using separate accounts for production, development, testing, security, and shared services provides natural isolation:

  • Blast-radius containment — a mistake in a dev account cannot reach production resources.
  • Separate billing — you can track costs per team or environment.
  • Independent service quotas — one team's heavy usage does not exhaust another team's limits.
  • Clear security boundaries — each account has its own IAM principals, so cross-account access is explicit, auditable, and revocable.
Core exam concept: An AWS account is a billing and security boundary. An organization is a management layer above accounts that provides consolidated billing, policy-based governance, and centralized account creation.

Management Account vs Member Accounts

Every organization has exactly one management account (formerly called the "master account"). This is the account that created the organization. It pays the consolidated bill and has special privileges — including being exempt from SCP restrictions.

All other accounts are member accounts. They can be created inside the organization or invited from outside. Member accounts are subject to the SCPs that the management account attaches.

Best practice: Use the management account only for billing and organization management. Do not run workloads in it. Because SCPs cannot restrict the management account, any principal there operates without organizational guardrails.

Organizational Units (OUs) and Hierarchy

An organizational unit (OU) is a container for accounts within an organization. You can nest OUs inside other OUs to create a tree structure. A typical layout:

  • Root — the top-level container. Every account and OU lives under the root.
  • Production OU — contains production workload accounts.
  • Development OU — contains dev and test accounts.
  • Security OU — contains the security tooling account (GuardDuty, Security Hub, CloudTrail aggregation).
  • Shared Services OU — contains accounts for networking, DNS, CI/CD pipelines.

Example: TechCorp's Organization

TechCorp has one organization with the root at the top. Under the root are three OUs: Production (containing prod-web and prod-data accounts), Development (containing dev-team-a and dev-team-b), and Security (containing security-tooling). The management account sits at the root level and handles billing. SCPs attached at the root apply to all OUs and member accounts beneath it. An SCP attached to the Production OU applies only to production accounts.

Consolidated Billing

With Organizations, all member accounts roll their charges into a single bill paid by the management account. The main benefits:

  • Volume discounts — aggregated usage across accounts can trigger tiered pricing (for example, S3 or data transfer).
  • Reserved Instance sharing — RI pricing benefits apply across the entire organization unless you disable sharing.
  • Single payment — one invoice to the finance team instead of dozens.

Consolidated billing is a billing feature, not a security feature. It does not enforce any permissions or restrict actions. SCPs are what enforce guardrails.

What Is a Service Control Policy (SCP)?

An SCP is a type of organization policy that defines the maximum available permissions for IAM users and roles in affected member accounts. Think of it as a fence around a yard — you can move anywhere inside the fence, but you cannot cross it no matter what permissions your IAM policy grants.

Critical distinction: An SCP does not grant permissions. Even if an SCP contains an Allow statement, that Allow does not give anyone the ability to perform the action. The principal must also have an IAM policy (identity-based or resource-based) that grants the permission. The SCP only determines whether the IAM policy is allowed to take effect.

SCP Inheritance Through the Hierarchy

SCPs are attached at the root, OU, or individual account level. The effective SCP for any account is the intersection of all SCPs applied from the root down to that account. If the root SCP allows services A, B, C, and an OU SCP allows only A and B, then accounts in that OU can use only A and B — even if the account itself has a more permissive SCP.

This means a child can never have more permissions than its parent allows. Permissions can only be narrowed as you descend the hierarchy, never broadened.

Allow-List vs Deny-List Strategies

There are two main approaches to structuring SCPs:

  • Deny-list (default, recommended) — Keep the default FullAWSAccess SCP (which allows everything) and then attach additional SCPs with explicit Deny statements for the specific actions you want to block. This is simpler: everything is allowed unless you explicitly block it.
  • Allow-list — Remove the FullAWSAccess SCP and replace it with SCPs that explicitly Allow only the services you want to permit. Everything not listed is implicitly denied. This is more restrictive but requires careful maintenance — you must add new services to the allow-list before anyone can use them.

Common Mistake

A deny-list SCP does not automatically allow everything that it does not deny. The default FullAWSAccess SCP provides the broad Allow. If you remove FullAWSAccess without attaching a replacement Allow policy, all actions are implicitly denied for member accounts.

SCP JSON Example — Deny-List Strategy

This SCP prevents member accounts from leaving the organization or disabling CloudTrail:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLeaveOrg",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    },
    {
      "Sid": "DenyDisableCloudTrail",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail"
      ],
      "Resource": "*"
    }
  ]
}

Because this SCP uses only Deny statements and the default FullAWSAccess SCP provides the broad Allow, every action except these three is available (subject to IAM policies within the account).

Important Rules and Limitations

  • SCPs do not grant permissions. Even an Allow statement in an SCP only opens the ceiling — a principal must still have a matching IAM policy grant.
  • Effective permissions require the action to be permitted by the applicable SCPs and by the identity-based or resource-based policy. Both layers must align.
  • SCPs affect member account root users. Unlike IAM policies that cannot restrict the root user within an account, SCPs can restrict what the root user of a member account can do.
  • SCPs do not restrict the management account. No SCP, including those attached to the root OU, limits principals in the management account.
  • SCPs do not restrict service-linked roles. Service-linked roles are created by AWS services for internal integrations (e.g., the AWSServiceRoleForElasticLoadBalancing role). SCPs cannot block the actions they perform because those actions are controlled by the service, not by the account's principals.
  • OU placement matters for troubleshooting. Moving an account from one OU to another instantly changes the SCPs that apply to it. If users suddenly lose access, check whether the account was moved.
  • Changing an SCP affects many accounts at once. Modifying an SCP attached to the root OU can impact every member account in the organization. Always test in a sandbox OU first.

SCPs vs Permissions Boundaries

Both limit permissions without granting them, but at different levels:

  • SCPs apply to an entire account or OU. They are managed by the organization administrator in the management account. Individual account administrators cannot remove or modify them.
  • Permissions boundaries apply to a single IAM user or role. They are managed by the account administrator. They are commonly used for delegated administration — allowing developers to create roles without exceeding their own privilege level.

If both an SCP and a permissions boundary are present, the action must be permitted by both. They work as independent ceilings that stack.

SCPs vs IAM Identity Center Permission Sets

IAM Identity Center permission sets are collections of policies that define what a federated user can do when they access an account through the Identity Center portal. Permission sets are the grant mechanism — they give users permissions. SCPs are the guardrail mechanism — they cap what those grants can achieve. A permission set that allows ec2:* is useless if the account's SCP denies EC2 actions.

Worked Example: AdministratorAccess vs SCP

Why AdministratorAccess Cannot Beat an SCP

A user in a member account has the AdministratorAccess managed policy attached ("Effect": "Allow", "Action": "*", "Resource": "*"). The user tries to call organizations:LeaveOrganization. An SCP on the account's OU contains an explicit Deny for that action.

Result: Access denied. The SCP's explicit Deny overrides the IAM Allow. The user's AdministratorAccess policy can only grant permissions within the ceiling set by the SCP. The SCP is enforced by the organization at a level above the account, so no in-account policy can override it.

If there were no SCP deny but the SCP used an allow-list that did not include organizations:LeaveOrganization, the result would be the same — the action would be implicitly denied because it falls outside the SCP's allowed ceiling.

When Real Architects Actually Use This

Scenario A: Preventing Public S3 Access

Requirement: A company needs to ensure that no member account can make S3 buckets publicly accessible.

Solution: Attach an SCP to the root OU that denies s3:PutBucketPolicy and s3:PutBucketAcl when the request would enable public access. Use condition keys like s3:x-amz-acl to target only public grants.

Important nuance: The SCP provides an organization-wide guardrail, but it is not the only defense. You should also enable S3 Block Public Access at the account level (or organization level via the Organizations S3 settings) and use individual bucket policies as a defense-in-depth strategy. The SCP prevents IAM principals from changing the settings, but it does not directly inspect or validate existing bucket configurations.

Limitation: SCPs apply to IAM principals within the organization. If a bucket policy explicitly grants access to an external principal (account or user outside the organization), the SCP on the resource-owning account does not directly block that external principal's access. You must use the bucket policy or Block Public Access settings to control external access at the resource level.

Scenario B: Restricting AWS Regions

Requirement: A European company wants workloads to run only in eu-west-1 and eu-central-1 for data residency compliance.

Solution: Attach an SCP that denies all actions when the aws:RequestedRegion condition key is not one of the allowed Regions. Example:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNonEURegions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [
            "eu-west-1",
            "eu-central-1"
          ]
        }
      }
    }
  ]
}

Why this needs care: Some AWS services are global (IAM, Organizations, Route 53, CloudFront, STS global endpoint). Blocking all non-EU Regions would break these services. You must add exceptions for global services using NotAction or condition-key exclusions. Failing to do this is a common implementation mistake and a frequent exam trap.

Scenario C: Protecting Production Accounts

Requirement: A company separates production and development into different OUs. Production accounts need stricter controls: no one should be able to terminate EC2 instances without MFA, and no one should delete RDS snapshots.

Solution: At the root OU, attach an SCP that denies organizations:LeaveOrganization (a baseline guardrail for all accounts). At the Production OU, attach an additional SCP that denies ec2:TerminateInstances unless MFA is present (using the aws:MultiFactorAuthPresent condition key) and unconditionally denies rds:DeleteDBSnapshot. The Development OU does not receive these extra restrictions, allowing developers to iterate freely.

How inheritance works here: Production accounts inherit the root-level SCP (deny leave org) and the Production OU SCP (deny terminate without MFA, deny snapshot deletion). Development accounts only inherit the root-level SCP. This layered approach lets you apply progressively stricter controls as you descend the hierarchy.

Scenario D: Preventing Dangerous Actions

Requirement: A security team wants to prevent anyone in any member account from disabling AWS Config, stopping CloudTrail logging, or deleting GuardDuty detectors.

Solution: Attach an SCP at the root OU with explicit Deny statements for config:StopConfigurationRecorder, config:DeleteConfigurationRecorder, cloudtrail:StopLogging, cloudtrail:DeleteTrail, guardduty:DeleteDetector, and guardduty:DisassociateFromMasterAccount.

Why this is appropriate: Because the SCP's explicit Deny cannot be overridden by any IAM policy in member accounts — not even by the root user — these security services remain enabled regardless of what an account administrator does. The management account is exempt, so the organization administrator can still manage these services if needed.

Implementation risk: The exact API action names must be verified against current AWS documentation. AWS occasionally adds or renames actions, so the SCP should be reviewed periodically. Also, the SCP prevents IAM principals from performing these actions, but service-linked roles used by these services internally are not restricted.

Scenario E: Centralized Governance for Many Accounts

Requirement: A growing company has 40 AWS accounts across five departments. They need consistent security baselines, separate billing visibility, and the ability to onboard new teams quickly.

Solution: Structure the organization with OUs per department (Engineering, Finance, Marketing, etc.) plus cross-cutting OUs for Security and Shared Services. Apply baseline SCPs at the root (deny dangerous actions, restrict Regions). Apply department-specific SCPs at each department OU as needed. Use consolidated billing for volume discounts and cost tracking via Cost Allocation Tags. Use AWS Control Tower to automate account provisioning with pre-configured guardrails.

Why separate accounts per team? Each department gets its own IAM namespace, service quotas, and blast radius. A developer in Marketing cannot accidentally affect Engineering's production database. Consolidated billing still provides a single invoice. SCPs ensure organization-wide compliance without requiring each department to configure their own restrictions.

Limitation: Organizations and SCPs provide governance structure, but they do not replace account-level security configuration. Each account still needs properly configured IAM policies, VPC security, encryption settings, and logging. SCPs are guardrails, not a complete security solution.

SAA-C03 Exam Gotchas — Organizations & SCPs

Assuming an SCP Grants Permissions Because It Contains Allow

Wrong: "The SCP allows S3, so users can use S3." Correct: The SCP permits S3 actions to take effect, but each principal still needs an IAM policy that grants S3 access. An SCP Allow only opens the ceiling — it does not hand out keys.

Exam clue: If a question says "only an SCP is configured" and asks what a user can do, the answer is nothing — the user also needs an IAM policy.

Memory rule: SCP = ceiling, IAM policy = permission. You need both.

Assuming AdministratorAccess Can Bypass an SCP

Wrong: "The user has AdministratorAccess, so the SCP doesn't matter." Correct: In a member account, effective permissions are the intersection of the SCP and the IAM policy. AdministratorAccess allows everything at the IAM level, but the SCP caps what "everything" can be.

Exam clue: "User has AdministratorAccess but cannot perform X" = the SCP is blocking X.

Memory rule: AdminAccess ∩ SCP = whatever the SCP allows.

Assuming SCPs Restrict the Management Account

Wrong: "We attached a deny SCP to the root OU, so no one in any account can do this." Correct: The management account is always exempt from SCPs. If the exam asks what happens when the management account tries a denied action, the answer is: it succeeds.

Exam clue: Look for "management account" or "payer account" in the question. If the action originates there, SCPs do not apply.

Memory rule: Management account = above the law (for SCPs).

Forgetting That SCPs Affect the Member Account Root User

Wrong: "The root user can do anything, so SCPs don't apply." Correct: Within a member account, SCPs restrict the root user just like any other principal. The root user of the management account is not restricted, but the root user of a member account is.

Exam clue: "Root user of a member account" + "cannot perform action" = SCP is blocking it.

Memory rule: Member root user ≠ management root user.

Confusing an SCP with a Permissions Boundary

Wrong: "We applied a permissions boundary to the account." Correct: SCPs apply to accounts/OUs and are managed by the organization administrator. Permissions boundaries apply to individual IAM users/roles and are managed by the account administrator. They are different tools at different levels.

Exam clue: If the question says "organization-wide restriction," the answer is SCP. If it says "limit what a specific developer can grant," the answer is permissions boundary.

Memory rule: SCP = org-level fence. Permissions boundary = individual-level fence.

Confusing a Trust Policy with an SCP

Wrong: "We used an SCP to control who can assume the role." Correct: A trust policy on a role controls who can assume it. An SCP controls the maximum permissions available to principals. An SCP can prevent a principal from calling sts:AssumeRole, but the trust policy is the primary mechanism for controlling role assumption.

Exam clue: "Who can assume?" = trust policy. "What actions are permitted across the account?" = SCP.

Memory rule: Trust policy = door to the role. SCP = fence around the account.

Assuming a Deny-List Automatically Allows Everything Not Denied

Wrong: "Our SCP only has Deny statements, so everything else is allowed." Correct: The Deny statements block specific actions, but the broad Allow comes from the default FullAWSAccess SCP. If someone removes FullAWSAccess and only leaves Deny statements, everything is denied (no Allow + explicit Deny = total lockout).

Exam clue: If a question says the FullAWSAccess SCP was removed, the answer involves total access loss for member accounts.

Memory rule: Deny-list strategy = FullAWSAccess + explicit Deny. Remove FullAWSAccess and the deny-list becomes a deny-everything.

Assuming an OU-Level Restriction Disappears with a More Permissive Account Policy

Wrong: "The account has a FullAWSAccess SCP attached directly, so the OU restriction doesn't matter." Correct: Effective permissions are the intersection of SCPs at every level from root to account. An account-level SCP cannot expand beyond what its parent OU allows. The most restrictive applicable SCP always wins.

Exam clue: Questions about OU hierarchy where one level is restrictive = the restriction holds.

Memory rule: Child can never exceed parent's ceiling.

Assuming SCPs Alone Prevent All Public Resource Exposure

Wrong: "We have an SCP that blocks public access, so our buckets are safe." Correct: SCPs restrict IAM principals within the organization. They do not directly control access from external principals granted through resource-based policies, nor do they replace S3 Block Public Access settings. Defense in depth requires SCPs plus account-level controls.

Exam clue: If the question asks about preventing "all public access," SCPs are part of the answer but not the entire answer.

Memory rule: SCP = guards inside the fence. Bucket policy + Block Public Access = guards at the gate.

Assuming SCPs Restrict Service-Linked Roles

Wrong: "Our SCP denies elasticloadbalancing actions, so the ELB service-linked role can't function." Correct: Service-linked roles are not restricted by SCPs. These roles are created and managed by AWS services for their internal operations. An SCP that denies elasticloadbalancing:* prevents IAM users and roles from managing ELB, but it does not prevent the ELB service itself from performing its internal operations via its service-linked role.

Exam clue: Questions involving AWS-managed service operations continuing despite restrictive SCPs = service-linked role exception.

Memory rule: SCPs bind people and roles you create, not AWS's own service plumbing.

Confusing Consolidated Billing with Permission Enforcement

Wrong: "We enabled consolidated billing, so all accounts follow the same security rules." Correct: Consolidated billing is a cost management feature. It combines invoices and enables volume discounts. It has no effect on permissions, security controls, or access policies. Permission enforcement requires SCPs.

Exam clue: If a question mentions "consistent security policies across accounts," the answer involves SCPs or AWS Control Tower, not consolidated billing.

Memory rule: Billing = money. SCPs = permissions. Different problems, different tools.

Practice Questions — Organizations & SCPs

Q1. A company uses AWS Organizations and wants to prevent any member account from disabling AWS CloudTrail logging. Several member-account administrators have the AdministratorAccess IAM policy attached to their IAM users. Which approach ensures that CloudTrail cannot be disabled in any member account, even by administrators?

  • A. Remove the AdministratorAccess policy from all member-account administrators and replace it with a custom policy that excludes CloudTrail actions.
  • B. Attach an IAM permissions boundary to each administrator that denies cloudtrail:StopLogging and cloudtrail:DeleteTrail.
  • C. Attach an SCP to the organization root with an explicit Deny for cloudtrail:StopLogging and cloudtrail:DeleteTrail.
  • D. Configure CloudTrail as an organization trail and enable consolidated billing to protect it.

Correct Answer: C

An SCP with an explicit Deny attached at the organization root prevents all IAM principals in all member accounts from disabling CloudTrail. This includes users with AdministratorAccess and even the member account root user. The SCP cannot be overridden by any in-account policy.

Why not the others?

  • A is operationally complex, must be maintained per account, and a determined administrator could re-attach AdministratorAccess or create a new user with full permissions.
  • B requires attaching a permissions boundary to every individual administrator across every account. New administrators could be created without the boundary. This is not centrally enforceable.
  • D is wrong because consolidated billing is a cost feature, not a security control. An organization trail helps with centralized logging but does not prevent member-account administrators from stopping their account's logging.

Key exam clue: "Prevent action across all member accounts" + "even administrators" = SCP with explicit Deny.

Takeaway: SCPs are the only mechanism that centrally enforces restrictions that no in-account policy can override.

Q2. A company has an AWS Organization with two OUs: Production and Development. The security team wants production accounts to be restricted to only eu-west-1 and eu-central-1 Regions, while development accounts should be allowed to use any Region. An SCP attached to the organization root provides FullAWSAccess. How should the architect configure this?

  • A. Attach a Region-restricting SCP to the organization root so it applies to all accounts, then create an exception SCP on the Development OU that overrides the deny.
  • B. Attach a Region-restricting SCP with an explicit Deny for non-EU Regions only to the Production OU, leaving the Development OU with no additional SCP.
  • C. Remove FullAWSAccess from the organization root and create separate allow-list SCPs for each OU.
  • D. Configure IAM policies in each production account to deny non-EU Region actions instead of using SCPs.

Correct Answer: B

By attaching the Region-restricting SCP only to the Production OU, production accounts are limited to EU Regions while development accounts inherit only the root-level FullAWSAccess SCP and remain unrestricted. This is the simplest and most targeted approach.

Why not the others?

  • A is wrong because an explicit Deny in an SCP cannot be overridden by an Allow in a child SCP. Once the root SCP denies non-EU Regions, no child SCP can re-allow them. You cannot "override" an SCP deny.
  • C works in theory but is far more complex. Removing FullAWSAccess means you must explicitly list every allowed service in allow-list SCPs for both OUs. This is error-prone and hard to maintain.
  • D uses per-account IAM policies, which a local administrator could modify or remove. SCPs provide centrally enforced, tamper-proof restrictions.

Key exam clue: "Different restrictions for different OUs" = attach the restrictive SCP to only the OU that needs it.

Takeaway: SCP explicit Deny cannot be overridden by any Allow. Target SCPs at the specific OU level, not the root, when restrictions differ between OUs.

Q3. A company is setting up AWS Organizations for the first time. They need consolidated billing for cost tracking, centralized security guardrails across 12 member accounts, and a way for employees to access multiple accounts through a single sign-on portal. Which combination of services meets ALL three requirements?

  • A. AWS Organizations with consolidated billing, IAM policies in each account for security guardrails, and IAM users with cross-account roles for SSO.
  • B. AWS Organizations with consolidated billing and SCPs for centralized guardrails, plus AWS IAM Identity Center for single sign-on.
  • C. AWS Organizations with consolidated billing for both cost tracking and security enforcement, plus Amazon Cognito for employee SSO.
  • D. AWS Control Tower for account provisioning, AWS Config for security guardrails, and SAML 2.0 federation with an on-premises IdP for SSO.

Correct Answer: B

AWS Organizations provides consolidated billing (cost tracking) and SCPs (centralized security guardrails that no member account can override). IAM Identity Center provides workforce single sign-on across multiple accounts with a central portal. This combination directly addresses all three requirements with the simplest architecture.

Why not the others?

  • A uses per-account IAM policies for guardrails, which are manageable by local administrators and not centrally enforceable. Cross-account roles provide access but not a single sign-on portal experience.
  • C incorrectly assumes consolidated billing provides security enforcement — it is purely a billing feature. Amazon Cognito is for customer-facing application users, not workforce SSO.
  • D uses AWS Config for monitoring/compliance (it detects non-compliance but does not prevent actions the way SCPs do). SAML federation can provide SSO but is more complex than IAM Identity Center for multi-account workforce access.

Key exam clue: "Consolidated billing" + "centralized guardrails" + "single sign-on for employees" = Organizations + SCPs + IAM Identity Center.

Takeaway: Consolidated billing ≠ security. SCPs ≠ permissions grants. Cognito ≠ workforce SSO. Each service solves a specific problem.

AWS KMS & Encryption

Encryption at rest and in transit, KMS key types, envelope encryption, and encryption across AWS services.

Learn from Zero

Encryption Fundamentals

Encryption is the process of converting readable data (plaintext) into an unreadable format (ciphertext) using a mathematical algorithm and a secret value called a key. Decryption reverses the process — it converts ciphertext back into plaintext using the appropriate key. Without the correct key, the ciphertext is useless.

Symmetric vs Asymmetric Encryption

  • Symmetric encryption uses the same key for both encryption and decryption. It is fast and efficient for large amounts of data. The challenge is key distribution — both parties must securely share the secret key. Example: AES-256.
  • Asymmetric encryption uses a key pair: a public key (freely shared) and a private key (kept secret). Data encrypted with the public key can only be decrypted with the private key, and vice versa. It is slower than symmetric encryption but solves the key distribution problem. Examples: RSA, ECC.
Exam relevance: AWS KMS keys are symmetric by default (AES-256-GCM). KMS also supports asymmetric keys for use cases like digital signing or encryption outside AWS where you cannot call KMS directly. The exam most often tests symmetric KMS keys.

A complete security posture requires both. Encrypting data at rest does not protect it while it travels over the network, and encrypting data in transit does not protect it once it lands on disk.

TLS/HTTPS and Certificates

TLS (Transport Layer Security) is the protocol that encrypts data in transit. When you see https:// in a URL, the connection uses TLS. TLS relies on certificates issued by a Certificate Authority (CA) to verify the server's identity and establish an encrypted channel. AWS Certificate Manager (ACM) provides free public TLS certificates for use with AWS services like CloudFront, ALB, and API Gateway.

Encryption vs Hashing

  • Encryption is reversible — you can decrypt ciphertext back to plaintext with the key. It protects confidentiality.
  • Hashing is a one-way function — you cannot recover the original data from a hash. It protects integrity (detecting changes). Used for checksums, password storage, and digital signatures. Examples: SHA-256, MD5.

What Encryption Protects — and What It Does Not

Encryption protects confidentiality: even if an attacker obtains the encrypted data, they cannot read it without the key. However, encryption alone does not:

  • Authorize access — encrypting an S3 object does not replace the bucket policy or IAM permissions that control who can read or write it. A user with both the IAM permission to read the object and permission to use the encryption key can still access the data.
  • Guarantee integrity without additional mechanisms (though many encryption algorithms like AES-GCM include integrity checking).
  • Protect against an authorized insider who has legitimate access to both the data and the key.
Critical distinction: Encryption and authorization are separate layers. The exam will test whether you understand that encrypting data with KMS does not remove the need for proper IAM policies, bucket policies, or security group rules.

What Is AWS KMS?

AWS Key Management Service (KMS) is a managed service that lets you create, manage, and control cryptographic keys used to encrypt your data. KMS integrates with most AWS services that support encryption, so you can centrally manage the keys that protect your data across S3, EBS, RDS, DynamoDB, and many more.

A KMS key (formerly called a Customer Master Key or CMK) is the primary resource in KMS. It represents a logical key that contains the key material used for cryptographic operations. KMS keys never leave KMS unencrypted — all cryptographic operations happen inside the service.

KMS Key Policies vs IAM Policies

Every KMS key has a key policy — a resource-based policy attached directly to the key. Unlike most AWS resources, a KMS key's key policy is the primary access control mechanism. Without permission in the key policy (either directly or by enabling IAM policies), no one can use the key — not even the account root user.

  • Key policy — controls access to the KMS key itself. By default, the key policy grants the account root user full access and enables IAM policies to control access.
  • IAM policies — can grant KMS permissions only if the key policy allows it (by including the "kms:*" grant to the root account).

Key Administrators vs Key Users

  • Key administrators can manage the key (enable, disable, set policies, schedule deletion) but cannot use it for cryptographic operations.
  • Key users can use the key to encrypt and decrypt data but cannot manage the key's lifecycle or policies.

This separation enforces least privilege — the person who manages the key does not need to access the encrypted data, and the application that uses the key does not need to manage it.

Important KMS Permissions

  • kms:Encrypt — encrypt data directly under a KMS key (limited to 4 KB of data).
  • kms:Decrypt — decrypt ciphertext that was encrypted under a KMS key.
  • kms:GenerateDataKey — generate a plaintext data key and its encrypted copy for envelope encryption. This is the permission used when encrypting large data.

Key Rotation and Key Deletion

Key rotation creates new cryptographic material for a KMS key while keeping the same key ID and ARN. Old material is preserved so previously encrypted data can still be decrypted. Customer managed keys support optional automatic rotation (configurable interval); AWS managed keys rotate automatically every year.

Key deletion is irreversible and dangerous. When a KMS key is deleted, all data encrypted under that key becomes permanently unrecoverable. AWS enforces a mandatory waiting period (7–30 days) before deletion to prevent accidental data loss. During the waiting period, you can cancel the deletion.

Key Rotation vs Re-Encryption

Rotating a KMS key does not re-encrypt existing data. Old data remains encrypted under the old key material (which KMS preserves). Only new encryption operations use the new material. If compliance requires that existing data uses only current key material, you must re-encrypt it yourself.

Multi-Region KMS Keys

A multi-Region KMS key is a set of KMS keys in different Regions that share the same key material and key ID (with an mrk- prefix). Data encrypted in one Region can be decrypted in another without cross-Region API calls or re-encryption. You create a primary key in one Region and replicate it to others.

Multi-Region keys are useful for disaster recovery, global applications, and cross-Region data sharing. However, they are not global — you must explicitly replicate them to each Region you need, and each replica is billed separately.

Cross-Account KMS Access

To grant another account access to your customer managed KMS key, you need both:

  1. The KMS key policy must grant the external account (or a specific principal in it) permission to use the key.
  2. The external account must grant its own principal an IAM policy allowing KMS actions on your key ARN.

This mirrors the cross-account pattern for IAM roles — both sides must agree. AWS managed keys cannot be shared cross-account because you cannot modify their key policies.

Envelope Encryption

KMS has a 4 KB limit on data you can encrypt directly. For anything larger (which is almost everything in practice), you use envelope encryption:

  1. Call kms:GenerateDataKey. KMS returns a plaintext data key and an encrypted copy of that data key (encrypted under your KMS key).
  2. Use the plaintext data key to encrypt your data locally (in your application, SDK, or AWS service).
  3. Store the encrypted data and the encrypted data key together. Discard the plaintext data key from memory.
  4. To decrypt later, send the encrypted data key to KMS (kms:Decrypt). KMS returns the plaintext data key.
  5. Use the recovered plaintext data key to decrypt the data locally.
Why envelope encryption matters: Your actual data never leaves your environment — KMS only sees the small data key, not your large files. This reduces latency, avoids the 4 KB limit, and minimizes KMS API calls. This is how S3 SSE-KMS, EBS encryption, and most AWS encryption works internally.

EBS Volumes and Snapshots

EBS encryption is enabled per-volume. When you create an encrypted volume, EBS uses envelope encryption with a KMS key. All data on the volume, snapshots created from it, and volumes restored from those snapshots are encrypted. Encryption is transparent to the EC2 instance — no application changes needed.

  • You cannot remove encryption from an encrypted EBS volume or snapshot.
  • To encrypt an unencrypted volume, create a snapshot, copy the snapshot with encryption enabled, then create a new volume from the encrypted snapshot.
  • Snapshots of encrypted volumes are always encrypted with the same key (or you can re-encrypt with a different key during a snapshot copy).

RDS Encryption

RDS encryption at rest protects the database storage, automated backups, read replicas, and snapshots. It uses KMS envelope encryption.

  • Encryption must be enabled at creation time. You cannot encrypt an existing unencrypted RDS instance directly.
  • To encrypt an existing database: create a snapshot, copy the snapshot with encryption, then restore from the encrypted snapshot.
  • Read replicas of encrypted instances are always encrypted (same Region uses the same key; cross-Region requires a key in the destination Region).

EFS, SQS, DynamoDB, and CloudWatch Logs

  • EFS supports encryption at rest (KMS) and encryption in transit (TLS mount option). Both are independent settings.
  • SQS supports server-side encryption using KMS keys. Messages are encrypted at rest in the queue.
  • DynamoDB encrypts all tables at rest by default using an AWS owned key. You can choose an AWS managed key or a customer managed key instead.
  • CloudWatch Logs supports encryption using a customer managed KMS key at the log group level.

TLS for Data in Transit

Most AWS service endpoints use HTTPS (TLS) by default. For services where TLS is optional (such as RDS database connections or EFS mounts), you can enforce TLS through configuration. The exam expects you to know that encryption at rest and encryption in transit are separate concerns that require separate configurations.

Related Services Compared

KMS vs Secrets Manager

  • KMS manages encryption keys — it encrypts and decrypts data. It does not store your secrets or application data.
  • Secrets Manager stores and manages secrets (database credentials, API keys, tokens). It can encrypt those secrets using a KMS key and provides automatic rotation.

They often work together: Secrets Manager uses KMS to encrypt the secrets it stores. But they solve different problems.

KMS vs Certificate Manager (ACM)

  • KMS handles encryption keys for data at rest.
  • ACM manages TLS/SSL certificates for data in transit. ACM provides free public certificates for use with AWS services (CloudFront, ALB, API Gateway). ACM does not encrypt your stored data.

Encryption vs Authorization

Encryption protects confidentiality — even if someone accesses the ciphertext, they cannot read it. Authorization controls access — who can reach the resource in the first place. A properly secured system uses both: IAM policies and bucket policies control who can access a resource, and encryption protects the data if those controls are bypassed at the storage level.

When Real Architects Actually Use This

Scenario 1: Sensitive S3 Objects With Controlled Decryption

Requirement: A healthcare company stores patient records in S3. Only authorized applications in a specific account should be able to decrypt the data. The security team needs a CloudTrail audit trail for every decryption.

Solution: Encrypt objects using SSE-KMS with a customer managed key. Configure the KMS key policy to grant kms:Decrypt only to the authorized application role. The S3 bucket policy controls who can access the objects, and the KMS key policy controls who can decrypt them — two independent layers.

Why this works: Even if someone gains S3 read access through a misconfigured bucket policy, they cannot read the data without kms:Decrypt permission on the key. Every decryption call is logged in CloudTrail.

Limitation: KMS encryption adds a per-request cost and is subject to KMS request quotas (thousands of requests per second per Region). For extremely high-throughput reads, SSE-S3 with bucket-policy-only access control may be simpler, but you lose the key-level audit trail.

Scenario 2: Encrypted EBS Volumes for EC2 Applications

Requirement: A financial application on EC2 processes sensitive transaction data. All volumes must be encrypted, and the operations team needs to share encrypted snapshots with a disaster recovery account.

Solution: Create encrypted EBS volumes using a customer managed KMS key. Snapshots inherit the encryption. To share with the DR account, copy the snapshot and re-encrypt it with a KMS key that the DR account can access (grant the DR account's role in the key policy).

Why a customer managed key? AWS managed keys (aws/ebs) cannot be shared cross-account. A customer managed key lets you control the key policy and grant the DR account access.

Trade-off: Customer managed keys cost $1/month plus API call charges, and you are responsible for key lifecycle management. For single-account use, the AWS managed EBS key is simpler.

Scenario 3: Encrypted RDS Database With Protected Backups

Requirement: A retail company runs an RDS PostgreSQL database storing customer payment information. Compliance requires encryption at rest for the database and all backups. The existing database is currently unencrypted.

Solution: Since you cannot enable encryption on an existing RDS instance directly: (1) create a snapshot of the unencrypted database, (2) copy the snapshot with encryption enabled using a customer managed KMS key, (3) restore a new RDS instance from the encrypted snapshot, (4) update the application's connection string to point to the new instance. Automated backups and read replicas of the new instance will be encrypted automatically.

Why this matters: The migration requires a brief downtime window and a DNS/connection cutover. Planning the cutover is a real-world consideration that the exam tests — "you cannot simply enable encryption on an existing RDS instance."

Limitation: Cross-Region read replicas of encrypted databases require a KMS key in the destination Region. You cannot use the same key ARN across Regions (unless using multi-Region keys).

Scenario 4: Securing Web Application Data in Transit

Requirement: An e-commerce site transmits credit card information between the user's browser and the application. The security team requires all data in transit to be encrypted.

Solution: Terminate TLS at the Application Load Balancer using a certificate from AWS Certificate Manager (ACM). Configure the ALB listener to accept only HTTPS traffic on port 443. For end-to-end encryption, also enable TLS between the ALB and the backend EC2 instances.

Why ACM and not KMS? ACM handles TLS certificates (data in transit). KMS handles encryption keys (data at rest). They solve different problems. A common exam trap is conflating the two.

Trade-off: End-to-end TLS (ALB to backend) increases CPU overhead on the backend instances and requires managing certificates on those instances. Many architectures terminate TLS at the ALB and use the private VPC network for internal traffic.

Scenario 5: Centralized Key Governance

Requirement: A company with 20 AWS accounts wants all teams to use approved encryption keys and wants the security team to audit key usage across accounts.

Solution: Create customer managed KMS keys in a central security account. Configure key policies to grant specific roles in each member account kms:Encrypt, kms:Decrypt, and kms:GenerateDataKey permissions. Member accounts reference the central key ARN when encrypting their data. All key usage appears in the security account's CloudTrail logs.

Why centralized keys? It gives the security team a single place to audit, rotate, and revoke encryption access. If a member account is compromised, the security team can immediately revoke that account's key access from the central key policy.

Limitation: Cross-account KMS calls add latency and are subject to KMS request quotas in the key's home Region. High-throughput workloads may need keys in their own accounts with separate audit aggregation.

Scenario 6: Multi-Region Disaster Recovery

Requirement: A global application stores encrypted data in us-east-1 and must fail over to eu-west-1. After failover, the application in the DR Region must decrypt data replicated from the primary Region without calling back to us-east-1.

Solution: Create a multi-Region KMS key with the primary in us-east-1 and a replica in eu-west-1. Encrypt data in us-east-1 with this key. Replicate the encrypted data (via S3 CRR or database replication) to eu-west-1. The DR application in eu-west-1 decrypts using the local replica key — same key material, no cross-Region calls.

Why not separate keys per Region? If you use different keys, replicated data is encrypted under the source Region's key. The DR application would need to call KMS in us-east-1 to decrypt — which defeats the purpose of DR if that Region is down. Multi-Region keys solve this.

Trade-off: Multi-Region keys share key material, which means a compromise of the key in one Region affects all Regions. You must carefully manage key policies in every Region where the key is replicated.

SAA-C03 Exam Gotchas — KMS & Encryption

Confusing Encryption at Rest with Encryption in Transit

Misconception: "We enabled S3 SSE-KMS, so our data is encrypted everywhere." Correct: SSE-KMS encrypts data at rest in S3. Data traveling between the client and S3 is protected by HTTPS (TLS), which is a separate mechanism. You need both for complete protection.

Exam clue: If a question asks about protecting data "in transit," look for TLS/HTTPS/VPN answers, not KMS. If it asks about "at rest," look for KMS/SSE answers.

Memory rule: At rest = KMS/SSE. In transit = TLS/HTTPS. Different problems, different solutions.

Assuming SSE-S3 and SSE-KMS Are Interchangeable

Misconception: "Both encrypt the data, so it doesn't matter which one I choose." Correct: SSE-S3 uses AWS-managed keys with no visibility or control. SSE-KMS gives you CloudTrail logging of every key usage, access control through the KMS key policy, and the option to use a customer managed key.

Exam clue: "Audit key usage" or "control who can decrypt" = SSE-KMS with a customer managed key. "Simple default encryption" = SSE-S3.

Memory rule: Need audit or key control? SSE-KMS. Otherwise SSE-S3 is fine.

Assuming Resource Access Permission Includes Decrypt Permission

Misconception: "The user has s3:GetObject permission, so they can read encrypted S3 objects." Correct: If the object is encrypted with SSE-KMS, the user also needs kms:Decrypt permission on the KMS key. Without it, the GetObject call returns an Access Denied error — even though the S3 permission is correct.

Exam clue: "Has S3 read access but gets Access Denied on encrypted objects" = missing KMS Decrypt permission.

Memory rule: S3 permission gets the object. KMS permission decrypts it. You need both.

Confusing KMS Key Policies with IAM Policies

Misconception: "I'll just grant kms:Decrypt in an IAM policy and that's enough." Correct: KMS key policies are the primary access control. An IAM policy can grant KMS permissions only if the key policy delegates access to IAM (which it does by default for customer managed keys). If the key policy does not include the root account grant, IAM policies alone are insufficient.

Exam clue: If cross-account KMS access fails, check the key policy first.

Memory rule: Key policy is the gatekeeper. IAM policy is a secondary grant.

Confusing AWS Managed Keys with Customer Managed Keys

Misconception: "AWS managed keys can be shared across accounts." Correct: AWS managed keys (aliases like aws/ebs, aws/s3) can only be used within the account where they exist. You cannot modify their key policies or grant cross-account access. For cross-account encryption, you must use a customer managed key.

Exam clue: "Share encrypted snapshots cross-account" or "grant another account decrypt access" = customer managed key.

Memory rule: Cross-account = customer managed key. Always.

Confusing KMS Keys with Data Keys

Misconception: "The KMS key encrypts my data directly." Correct: KMS keys can directly encrypt only up to 4 KB of data. For anything larger, KMS generates a data key that encrypts the data locally. The KMS key protects the data key, not the data itself. This is envelope encryption.

Exam clue: "Encrypt large files with KMS" = envelope encryption via GenerateDataKey.

Memory rule: KMS key protects the data key. Data key protects the data.

Assuming Key Rotation Re-Encrypts Existing Data

Misconception: "We rotated the KMS key, so all our data now uses the new key material." Correct: Key rotation adds new cryptographic material for future encryption operations. Old material is preserved to decrypt data encrypted under previous versions. Existing encrypted data is not re-encrypted.

Exam clue: "Compliance requires all data encrypted with current key material" = you must re-encrypt existing data yourself.

Memory rule: Rotation creates new material. Old data keeps old material. Re-encryption is manual.

Deleting a KMS Key and Losing Access to Encrypted Data

Misconception: "I can always recover a deleted key." Correct: KMS key deletion is irreversible. All data encrypted under that key (and under its data keys) becomes permanently unrecoverable. AWS enforces a 7–30 day waiting period to help prevent accidental deletion, but once the waiting period expires, the key and all its material are gone.

Exam clue: "Data becomes inaccessible after a key is deleted" = this is the expected (and irreversible) outcome.

Memory rule: Delete the key, lose the data. No recovery. Ever.

Assuming Symmetric and Asymmetric KMS Keys Are Used Interchangeably

Misconception: "I'll use an asymmetric KMS key for S3 SSE-KMS." Correct: AWS services that integrate with KMS (S3, EBS, RDS, etc.) use symmetric KMS keys only. Asymmetric KMS keys are for use cases like digital signing or encrypting data outside AWS where the caller cannot call KMS directly (e.g., a client-side application using the public key).

Exam clue: If the question involves AWS-service-level encryption, the answer is a symmetric key. Asymmetric keys appear in digital signing or external encryption scenarios.

Memory rule: AWS services = symmetric KMS key. External signing/encryption = asymmetric.

Confusing KMS with Secrets Manager and Certificate Manager

Misconception: "KMS can store my database password" or "KMS provides TLS certificates." Correct: KMS manages encryption keys. Secrets Manager stores and rotates secrets (passwords, API keys). Certificate Manager manages TLS certificates. They solve different problems and often work together.

Exam clue: "Store and rotate credentials" = Secrets Manager. "TLS for an ALB" = ACM. "Encrypt data at rest" = KMS.

Memory rule: KMS = keys. Secrets Manager = secrets. ACM = certificates.

Assuming Multi-Region Keys Are Global

Misconception: "A multi-Region KMS key is automatically available everywhere." Correct: Multi-Region keys must be explicitly replicated to each Region you need. Each replica has its own ARN and is billed separately. They share the same key material and key ID prefix (mrk-), but you must set them up per Region.

Exam clue: "Same key across Regions without cross-Region API calls" = multi-Region key (but you must replicate it first).

Memory rule: Multi-Region ≠ global. Replicate explicitly.

Confusing Encryption with Authorization

Misconception: "Our S3 data is encrypted, so unauthorized users cannot access it." Correct: Encryption protects confidentiality at the storage level. If an unauthorized user has s3:GetObject permission and kms:Decrypt permission, encryption does not stop them. Access control (IAM policies, bucket policies, VPC endpoints) must be the first line of defense. Encryption is a second layer.

Exam clue: "Prevent unauthorized access" = fix IAM/bucket policies first. Encryption is defense-in-depth, not a replacement for authorization.

Memory rule: Authorization controls who gets in. Encryption protects what they find.

RDS Encryption Limitations

Misconception: "I can enable encryption on my existing RDS instance." Correct: RDS encryption must be enabled at creation time. To encrypt an existing database, you must: snapshot → copy snapshot with encryption → restore from encrypted snapshot → update your application to point to the new instance. This requires a migration with downtime.

Exam clue: "Encrypt an existing unencrypted RDS database" = snapshot, copy with encryption, restore.

Memory rule: RDS encryption is birth-only. Migrate to encrypt after the fact.

Practice Questions — KMS & Encryption

Q1. A company stores confidential financial reports in an S3 bucket encrypted with SSE-KMS using a customer managed key. A new analytics team in a different AWS account needs to read these reports. The analytics team's IAM role has been granted s3:GetObject on the bucket via a bucket policy. However, when the team tries to download a report, they receive an Access Denied error. What is the MOST likely cause and solution?

  • A. The bucket policy is incorrect. Add s3:Decrypt permission to the analytics team's role in the bucket policy.
  • B. The KMS key policy does not grant the analytics team's account kms:Decrypt permission. Update the key policy to grant kms:Decrypt to the analytics role, and add an IAM policy in the analytics account allowing kms:Decrypt on the key ARN.
  • C. SSE-KMS encrypted objects cannot be shared cross-account. Re-encrypt all objects with SSE-S3 and share the bucket.
  • D. The analytics team needs to use the same AWS managed key (aws/s3) as the source account. Configure the destination account to use the same key alias.

Correct Answer: B

With SSE-KMS, downloading an object requires both S3 read permission and kms:Decrypt permission on the KMS key. For cross-account access, the KMS key policy must grant the external account access, and the external account must also have an IAM policy allowing KMS actions on the key. Both sides must agree — this is the same cross-account pattern as IAM roles.

Why not the others?

  • A is wrong because s3:Decrypt is not a valid S3 action. Decryption is handled by KMS, not S3.
  • C is wrong because SSE-KMS objects can be shared cross-account when using a customer managed key with the correct key policy. You do not need to re-encrypt.
  • D is wrong because AWS managed keys (aws/s3) cannot be shared cross-account — they only work within the account that owns them. Each account has its own separate aws/s3 key.

Key exam clue: "Cross-account access to KMS-encrypted data" + "Access Denied" = missing kms:Decrypt in the key policy and/or the caller's IAM policy.

Takeaway: Accessing KMS-encrypted resources cross-account requires both the resource permission (S3) and the key permission (KMS) from both accounts.

Q2. A healthcare company stores patient records in an encrypted RDS PostgreSQL database (SSE enabled with an AWS managed KMS key). An auditor reports that database connections from the application servers are transmitting data in plaintext across the VPC. The security team needs to ensure data is protected both at rest and in transit with MINIMAL application changes. What should the solutions architect do?

  • A. Replace the AWS managed KMS key with a customer managed key. Customer managed keys encrypt data both at rest and in transit.
  • B. Enable SSL/TLS on the RDS instance by downloading the RDS CA certificate and configuring the application's database connection to require SSL.
  • C. Move the RDS instance into the same subnet as the application servers so the data never crosses a network boundary.
  • D. Enable VPC Flow Logs on the database subnet to encrypt the network traffic between the application and the database.

Correct Answer: B

RDS encryption at rest (KMS) and encryption in transit (TLS) are separate mechanisms. The database is already encrypted at rest. To protect data in transit, you configure the application to connect using SSL/TLS. RDS supports SSL natively — you download the RDS CA certificate bundle and configure the connection string to require SSL verification.

Why not the others?

  • A is wrong because changing the KMS key type has no effect on network traffic. KMS keys handle encryption at rest, not in transit. No KMS key type encrypts data on the wire.
  • C is wrong because data still travels over the network within a subnet. Moving to the same subnet does not encrypt the connection — it only reduces the network path. It also violates good architecture practice of separating tiers.
  • D is wrong because VPC Flow Logs record metadata about network traffic for monitoring. They do not encrypt traffic.

Key exam clue: "Data encrypted at rest but not in transit" = you need TLS/SSL for the connection, not more KMS configuration.

Takeaway: Encryption at rest (KMS) and encryption in transit (TLS) solve different problems and are configured independently.

Q3. A global media company stores large video files (up to 5 GB each) encrypted in S3 in us-east-1. They are building a disaster recovery site in eu-west-1 and will use S3 Cross-Region Replication (CRR) to copy the encrypted videos. After failover, applications in eu-west-1 must be able to decrypt and play the videos without making API calls back to us-east-1. The company wants to minimize operational overhead. Which encryption approach meets these requirements?

  • A. Use SSE-S3 for encryption. S3 CRR automatically re-encrypts objects in the destination Region using the destination Region's S3-managed key.
  • B. Create a customer managed KMS key in us-east-1, encrypt all videos with it, and grant the eu-west-1 application role kms:Decrypt permission. After failover, the eu-west-1 application calls KMS in us-east-1 to decrypt.
  • C. Create a multi-Region customer managed KMS key with the primary in us-east-1 and a replica in eu-west-1. Encrypt videos using this key. After CRR replicates the objects, the eu-west-1 application decrypts using the local replica key.
  • D. Use client-side encryption with a locally generated AES key stored in Secrets Manager. Replicate the secret to eu-west-1 using Secrets Manager cross-Region replication.

Correct Answer: C

Multi-Region KMS keys share the same key material across Regions. Data encrypted in us-east-1 can be decrypted in eu-west-1 using the local replica key — no cross-Region API calls needed. This is the ideal pattern for DR with encrypted data. S3 CRR preserves the KMS encryption, and the multi-Region key ensures the destination Region can decrypt independently.

Why not the others?

  • A works for simple cases, but SSE-S3 does not provide key-level audit trails or access control through key policies. If the company needs to audit decryption (common for media rights management), SSE-S3 is insufficient.
  • B violates the requirement — if us-east-1 is down during a disaster, the eu-west-1 application cannot call KMS in us-east-1, making the encrypted data inaccessible.
  • D works technically but introduces significant operational overhead: you must manage client-side encryption logic, key distribution, and ensure the Secrets Manager replication is synchronized. This is far more complex than a multi-Region KMS key.

Key exam clue: "Cross-Region DR" + "decrypt without calling back to the primary Region" = multi-Region KMS key.

Takeaway: Multi-Region KMS keys solve the cross-Region decryption problem for DR without requiring cross-Region API calls or re-encryption.

Security Groups vs Network ACLs

Instance-level stateful filtering, subnet-level stateless filtering, and how both work together to secure VPC traffic.

Learn from Zero

Network Security Fundamentals

A Virtual Private Cloud (VPC) is your isolated section of the AWS cloud. Inside a VPC, you launch EC2 instances, databases, load balancers, and other resources. Without network security rules, any device that can reach your VPC could send traffic to any resource on any port — which is extremely dangerous.

Every network packet has a source IP address (where the packet comes from) and a destination IP address (where it is going). A port is a numbered endpoint on a server that identifies a specific service:

  • Port 80 — HTTP (unencrypted web traffic)
  • Port 443 — HTTPS (encrypted web traffic)
  • Port 22 — SSH (remote Linux administration)
  • Port 3389 — RDP (remote Windows administration)
  • Port 3306 — MySQL/Aurora database

Inbound traffic flows into a resource (a client sending a request to your web server). Outbound traffic flows out from a resource (your server sending a response back, or initiating a call to an external API).

Good network security means each resource exposes only the ports and sources it needs. A web server should accept HTTPS on port 443 from the internet, but a database should accept connections only from the application servers that need it — never from the internet.

Core principle: AWS provides two layers of VPC network filtering: security groups (at the network interface level) and network ACLs (at the subnet level). They complement each other — traffic must pass both to reach a resource.

Consider a typical three-tier application:

  • A web server in a public subnet accepts HTTPS from the internet.
  • An application server in a private subnet accepts requests only from the web server.
  • A database in a private subnet accepts connections only from the application server.

Each tier needs different network rules. Security groups control what each individual resource allows. NACLs control what the entire subnet allows. Together they create a defense-in-depth architecture.

Security Groups

A security group is a virtual firewall that controls traffic at the network interface (ENI) level. When you associate a security group with an EC2 instance, it controls what traffic can reach and leave that specific instance. A security group is not applied to an entire subnet — it is attached to the network interfaces of individual resources.

Inbound and Outbound Rules

Each security group has separate inbound rules (controlling incoming traffic) and outbound rules (controlling outgoing traffic). Each rule specifies:

  • Protocol — TCP, UDP, ICMP, or all traffic.
  • Port range — a single port (443) or a range (1024–65535).
  • Source (for inbound) or Destination (for outbound) — a CIDR block (10.0.0.0/16), a specific IP (203.0.113.50/32), or another security group ID.

Stateful Behavior

Security groups are stateful. This means they track connections. If an inbound rule allows traffic in, the response traffic is automatically allowed out — you do not need a separate outbound rule for the response. Similarly, if an outbound rule allows traffic out, the response coming back in is automatically allowed.

What stateful means in practice: You allow inbound HTTPS on port 443. A client sends a request to your server. The server sends back a response on an ephemeral port. Because the security group is stateful, it remembers the inbound connection and automatically permits the response — no outbound rule needed for that specific response.

Allow Rules Only — No Explicit Deny

Security groups support only allow rules. You cannot write a rule that says "deny traffic from IP 10.0.1.50." If traffic does not match any allow rule, it is implicitly denied. This means security groups work on a whitelist model: everything is blocked unless you explicitly allow it.

All rules in a security group are evaluated together. If any rule allows the traffic, it is permitted. There is no rule ordering or priority — rules are combined as a union.

Multiple Security Groups

You can associate multiple security groups with a single network interface (up to 5 by default). When multiple security groups are attached, all their rules are aggregated. If any rule across any attached security group allows the traffic, it passes. Adding a more permissive security group expands what is allowed — it does not override or restrict rules from other attached security groups.

Default Security Group

Every VPC comes with a default security group. Its default rules:

  • Inbound: Allows all traffic from other resources associated with the same default security group (self-referencing rule). Denies all other inbound traffic.
  • Outbound: Allows all outbound traffic to any destination.

A new custom security group (one you create) has different defaults:

  • Inbound: Denies all inbound traffic (no rules).
  • Outbound: Allows all outbound traffic to any destination.

Default Outbound Rules

Both the default SG and new custom SGs allow all outbound traffic by default. This is convenient but may be too permissive for production environments. Review outbound rules and restrict them when the architecture requires it (for example, limiting a database server to only communicate with specific application servers).

Security Group References

Instead of specifying an IP address as a source, you can reference another security group. This is extremely powerful for multi-tier architectures:

Database Security Group — Inbound Rules:
Type        Port    Source
MySQL/Aurora  3306    sg-0abc123 (App Server SG)

This rule says: "Allow MySQL traffic on port 3306, but only from resources that have the App Server security group attached." If the app servers scale from 2 to 20 instances, the rule still works — no IP updates needed. This is the recommended approach for tier-to-tier communication.

Restricting Administrative Access

Never allow SSH (port 22) or RDP (port 3389) from 0.0.0.0/0 (the entire internet). Instead, restrict these ports to specific trusted CIDR blocks (your office IP range, a VPN endpoint, or a bastion host security group).

Network ACLs (NACLs)

A network access control list (NACL) is a firewall at the subnet level. Every subnet in a VPC is associated with exactly one NACL. The NACL filters all traffic entering and leaving the subnet, regardless of which resources are inside.

Inbound and Outbound NACL Rules

Like security groups, NACLs have separate inbound and outbound rule sets. Each rule specifies:

  • Rule number — determines evaluation order (lower numbers are evaluated first).
  • Protocol — TCP, UDP, ICMP, or all.
  • Port range — a single port or range.
  • Source (inbound) or Destination (outbound) — a CIDR block.
  • Action — ALLOW or DENY.

Stateless Behavior

NACLs are stateless. They do not track connections. Every packet is evaluated independently against the rules — both the request and the response. If you allow inbound traffic on port 443, you must also create an outbound rule allowing the response traffic. The response typically goes back on an ephemeral port (1024–65535), so you need to allow outbound traffic on that range.

Why ephemeral ports matter: When a client connects to your web server on port 443, the client picks a random high port (e.g., 52413) for its side of the connection. Your server sends the response to that ephemeral port. If the NACL's outbound rules do not allow traffic on ephemeral ports (1024–65535), the response is silently dropped — even though the security group would have allowed it.

Rule Numbering and First-Match Evaluation

NACL rules are evaluated in ascending order by rule number. The first rule that matches the traffic is applied, and no further rules are checked. This is fundamentally different from security groups, where all rules are combined.

Inbound NACL Rules:
Rule#   Type    Port    Source          Action
100     HTTPS   443     0.0.0.0/0       ALLOW
200     SSH     22      10.0.0.0/16     ALLOW
300     ALL     ALL     192.168.1.0/24  DENY
*       ALL     ALL     0.0.0.0/0       DENY

Traffic from 192.168.1.50 on port 443 hits rule 100 first (ALLOW HTTPS from anywhere), so it is allowed — rule 300 is never reached. But traffic from 192.168.1.50 on port 3306 does not match rules 100 or 200, reaches rule 300 (DENY from 192.168.1.0/24), and is denied.

The Final * Rule

Every NACL has an immutable * (asterisk) rule at the bottom with action DENY. If traffic does not match any numbered rule, this catch-all rule denies it. You cannot edit or remove this rule.

IPv4 and IPv6

NACL rules are address-family specific. If your VPC uses both IPv4 and IPv6, you need rules for both. An IPv4 ALLOW rule does not cover IPv6 traffic from the same source.

How Both Controls Work Together

Consider a request flowing through a three-tier architecture:

  1. Internet client → Internet Gateway → public subnet boundary: The public subnet's NACL inbound rules evaluate the packet. If allowed, it enters the subnet.
  2. Public subnet → web server ENI: The web server's security group inbound rules evaluate the packet. If allowed (e.g., TCP 443 from 0.0.0.0/0), the packet reaches the web server.
  3. Web server → private subnet boundary: The web server's SG outbound rules evaluate the request to the app server (stateful: if allowed, the return is auto-allowed). The public subnet's NACL outbound rules evaluate the departing packet. The private subnet's NACL inbound rules evaluate the arriving packet.
  4. Private subnet → app server ENI: The app server's security group inbound rules evaluate the packet (e.g., allow from the web server's SG).
  5. App server → database: Same pattern: app server SG outbound, private subnet NACL outbound, database subnet NACL inbound, database SG inbound (e.g., MySQL 3306 from app server SG).
  6. Response traffic flows back: Security groups automatically permit return traffic (stateful). NACLs require explicit outbound/inbound rules in the return direction, including ephemeral ports.
Critical point: An overly restrictive NACL can break otherwise valid security-group-authorized traffic. If the app server's security group allows inbound from the web server, but the private subnet's NACL blocks that source CIDR, the connection fails. Traffic must pass all network controls along its path.

Network controls are not the only cause of connectivity issues. Route tables, IGW/NAT configuration, DNS resolution, resource health, and VPC peering/endpoint configuration can all contribute. When troubleshooting, check the entire path — not just security groups and NACLs.

Practical Rule Examples

Example 1: Web Server Security Group

Web Server SG — Inbound Rules:
Type    Port    Source          Note
HTTPS   443     0.0.0.0/0       Public web traffic
HTTP    80      0.0.0.0/0       Redirect to HTTPS (optional)
SSH     22      10.0.5.0/24     Bastion host subnet only

Web Server SG — Outbound Rules:
Type    Port    Destination     Note
Custom  8080    sg-app-server   App server communication
HTTPS   443     0.0.0.0/0       External API calls

Port 80 is often included to redirect HTTP requests to HTTPS. If your ALB handles this redirect, you may not need port 80 on the instance at all. SSH is restricted to the bastion subnet — never open to 0.0.0.0/0.

Example 2: Private Database Security Group

Database SG — Inbound Rules:
Type          Port    Source              Note
MySQL/Aurora  3306    sg-app-server       App tier only

Database SG — Outbound Rules:
(None needed for responses — SG is stateful)

The database only allows connections from resources with the app server SG — not from the web tier, not from the internet. If the app tier scales, new instances automatically get access because the rule references the SG, not individual IPs.

Example 3: NACL Deny Rule for IP Blocking

Public Subnet NACL — Inbound Rules:
Rule#   Type    Port    Source          Action
 50     ALL     ALL     198.51.100.0/24 DENY     ← Block malicious range
100     HTTPS   443     0.0.0.0/0       ALLOW
200     SSH     22      10.0.5.0/24     ALLOW
  *     ALL     ALL     0.0.0.0/0       DENY

Rule 50 denies all traffic from 198.51.100.0/24 before rule 100 can allow HTTPS from that range. This is impossible with a security group alone because security groups cannot express deny rules. The NACL provides the subnet-level IP block.

Example 4: Stateless Return Traffic Failure

An application server initiates an HTTPS call to an external API. The security group allows outbound HTTPS (port 443). But the private subnet NACL has restrictive inbound rules that do not allow ephemeral ports (1024–65535) from the external API's IP range.

Result: The request goes out, but the API's response arrives on an ephemeral port and is dropped by the NACL. The application sees a timeout. The security group would have allowed the response (it is stateful), but the NACL evaluated the return packet independently and blocked it.

Fix: Add an inbound NACL rule allowing TCP on ports 1024–65535 from the relevant source CIDR.

When Real Architects Actually Use This

Scenario A: Secure Three-Tier Web Application

Requirement: A company hosts a web application with a public web tier (ALB + EC2), a private application tier, and a private RDS database. Only the web tier should be internet-facing. The database must never receive traffic from the internet.

Solution:

  • Web server SG: Allow inbound HTTPS (443) from the ALB security group or from 0.0.0.0/0 if directly internet-facing. Allow outbound to the app server SG on the application port.
  • App server SG: Allow inbound from the web server SG on the application port (e.g., 8080). Allow outbound to the database SG on port 3306.
  • Database SG: Allow inbound on port 3306 only from the app server SG. No internet-facing rules.
  • NACLs: The public subnet NACL allows HTTPS and ephemeral ports. The private subnets use NACLs that deny all internet-originating traffic as an additional guardrail.

Why SG references? If the app tier auto-scales from 2 to 50 instances, the database SG rule still works — it references the SG, not IPs. No rule updates needed during scaling events.

Trade-off: Security groups alone handle most filtering. NACLs add defense-in-depth but increase operational complexity because of their stateless nature.

Common mistake: Opening the database SG to the entire VPC CIDR (e.g., 10.0.0.0/16) instead of a specific SG reference. This allows every resource in the VPC to connect to the database, violating least privilege.

Scenario B: Allow HTTPS but Restrict Administrative Access

Requirement: A web server needs public HTTPS access, but SSH must be limited to the operations team's VPN IP range (10.100.0.0/16). The security team wants a subnet-level restriction as backup.

Solution:

  • Security group: Allow inbound TCP 443 from 0.0.0.0/0. Allow inbound TCP 22 from 10.100.0.0/16 only.
  • NACL (optional additional layer): Add a DENY rule for TCP 22 from 0.0.0.0/0 with a higher rule number than an ALLOW for TCP 22 from 10.100.0.0/16. This ensures even if someone misconfigures the security group to open SSH broadly, the NACL blocks it at the subnet level.

Why this matters: Unrestricted SSH (0.0.0.0/0 on port 22) is one of the most common AWS security misconfigurations. It exposes instances to brute-force attacks from the entire internet. AWS Security Hub and Trusted Advisor flag this automatically.

Trade-off: Using NACLs for SSH restriction adds a layer but requires maintaining rules in two places. Most teams rely on security groups plus a bastion host or AWS Systems Manager Session Manager (which eliminates SSH entirely).

Scenario C: Block a Specific IP Address Range

Requirement: A security team detects attack traffic from the CIDR range 198.51.100.0/24 and needs to block it immediately across all resources in the public subnet.

Solution: Add a NACL inbound DENY rule with a low rule number (e.g., 50) for all traffic from 198.51.100.0/24. Because NACLs evaluate rules in order, this DENY is processed before any ALLOW rules that might match the same source.

Why a NACL and not a security group? Security groups do not support deny rules. You could remove the offending IP from allow rules, but if the SG allows 0.0.0.0/0 (common for web servers), there is no way to carve out an exception. A NACL DENY is the correct tool for explicit IP blocking.

Trade-off: NACL changes take effect immediately for all resources in the subnet. For broader or more dynamic IP blocking (thousands of ranges), AWS WAF with IP sets on an ALB or CloudFront is more practical.

Common mistake: Adding the DENY rule with a high rule number (e.g., 500) after an ALLOW on rule 100 that matches the same traffic. The ALLOW on 100 fires first, and the DENY on 500 is never reached.

Scenario D: Troubleshoot Broken Application Connectivity

Requirement: An application server can send HTTP requests to an internal API in another subnet, but the connection times out. Both resources were working yesterday.

Systematic troubleshooting:

  1. Security group inbound: Does the API server's SG allow inbound on the API port from the app server's SG or CIDR?
  2. Security group outbound: Does the app server's SG allow outbound to the API server's port? (Usually yes by default, but check.)
  3. NACL inbound on API subnet: Does the API subnet's NACL allow inbound traffic from the app server's CIDR on the correct port?
  4. NACL outbound on app subnet: Does the app subnet's NACL allow outbound traffic to the API server's CIDR?
  5. NACL return traffic: Do both subnets' NACLs allow ephemeral port traffic in the return direction?
  6. Route tables: Does a route exist between the two subnets? Were any routes changed?
  7. Resource health: Is the API server running and the service listening on the expected port?
  8. VPC connectivity: If the subnets are in different VPCs, check peering connections or Transit Gateway routes.

Key insight: A connection timeout does not automatically prove a security group or NACL is blocking traffic. Missing routes, stopped services, DNS failures, and network interface issues produce the same symptom. Always check the full path.

Scenario E: Restrict East-West Traffic Between Subnets

Requirement: A company runs two application teams in separate private subnets. Team A's resources must not communicate with Team B's resources for compliance isolation.

Solution:

  • Security groups (primary): Each team's resources use a dedicated SG that only allows inbound from its own team's SG. Neither SG references the other.
  • NACLs (additional enforcement): Add NACL DENY rules on each subnet blocking traffic from the other subnet's CIDR. This provides subnet-level enforcement even if someone misconfigures a security group.

Why SGs are primary: Security groups provide resource-level granularity and are easier to manage with scaling. NACLs operate at the subnet level and cannot distinguish between individual resources within a subnet.

Trade-off: NACLs add administrative overhead because you must maintain DENY rules, handle ephemeral ports for legitimate traffic, and update rules when subnet CIDRs change. For strict isolation, consider separate VPCs instead of relying solely on network controls within a single VPC.

Scenario F: New Service Tier Causes Intermittent Failures

Requirement: A team adds a caching tier (ElastiCache) in a new subnet. Existing web and app servers can reach the cache, but responses are intermittent — some requests work, others time out.

Diagnosis:

  • Security group: The cache SG allows inbound on the Redis port from the app server SG — this is correct and stateful, so responses are auto-allowed.
  • NACL on the cache subnet: A newly created custom NACL was associated with the cache subnet. It has an inbound ALLOW for the Redis port, but no outbound rule allowing ephemeral ports back to the app servers.
  • Result: Inbound requests reach the cache (NACL inbound ALLOW + SG ALLOW). The SG allows the response (stateful). But the NACL is stateless and drops the response because there is no matching outbound rule for ephemeral ports.

Fix: Add a NACL outbound rule allowing TCP on ports 1024–65535 to the app server subnet CIDR.

Why intermittent? Some ephemeral ports may fall in a range that coincidentally matches another NACL rule, causing inconsistent behavior depending on which port the OS selects.

Lesson: When adding a new subnet with a custom NACL, always configure both inbound and outbound rules including ephemeral port ranges for return traffic.

SAA-C03 Exam Gotchas — Security Groups vs NACLs

1. Confusing Stateful (SG) with Stateless (NACL)

Wrong: "I allowed inbound HTTPS in the NACL, so the response is automatically permitted." Correct: NACLs are stateless — return traffic must be explicitly allowed by an outbound rule (including ephemeral ports). Only security groups are stateful and auto-allow responses.

Exam clue: "Traffic reaches the server but responses never arrive" = missing NACL outbound rule for ephemeral ports.

Memory rule: SG = stateful (tracks connections). NACL = stateless (every packet evaluated independently).

2. Assuming Security Groups Support Deny Rules

Wrong: "I'll add a deny rule to the SG to block that malicious IP." Correct: Security groups support allow rules only. To explicitly deny a specific IP, use a NACL deny rule. In a security group, anything not explicitly allowed is implicitly denied.

Exam clue: "Block a specific IP range" = NACL. "Allow only specific sources" = SG.

Memory rule: SG = allow list only. NACL = allow + deny.

3. Assuming NACLs Evaluate All Matching Rules

Wrong: "Rule 100 allows HTTPS from everywhere, and rule 200 denies a specific IP, so both apply." Correct: NACLs use first-match evaluation by ascending rule number. If traffic matches rule 100 (ALLOW), rule 200 (DENY) is never evaluated. To deny that IP, the DENY rule must have a lower number than the ALLOW.

Exam clue: "NACL deny rule exists but traffic still passes" = the deny has a higher rule number than a matching allow.

Memory rule: NACL = first match wins. Lower number = higher priority.

4. Forgetting the Final * Rule

Wrong: "I only added ALLOW rules to my custom NACL, so everything else passes." Correct: Every NACL has an immutable * rule at the bottom that denies all traffic not matched by earlier rules. If your custom NACL has no ALLOW rules, all traffic is denied.

Exam clue: "Created a custom NACL and associated it with a subnet, now nothing works" = only the * deny rule exists.

Memory rule: Default NACL = allow all. Custom NACL = deny all (until you add rules).

5. Assuming a Security Group Allow Overrides a NACL Deny

Wrong: "The SG allows port 443, so the NACL deny doesn't matter." Correct: Traffic must pass both the NACL and the security group. A NACL deny blocks traffic at the subnet boundary before it ever reaches the security group. The two are independent filters — neither overrides the other.

Exam clue: "SG allows the traffic but connection still fails" = check the NACL.

Memory rule: NACL + SG are independent. DENY at either layer = blocked.

6. Forgetting NACL Return Traffic Rules

Wrong: "I allowed inbound on port 80 in the NACL, so the web server can respond." Correct: The server's response uses an ephemeral port (1024–65535). The NACL needs an outbound rule allowing traffic on those ports. Without it, responses are silently dropped.

Exam clue: "Server receives requests but cannot send responses" + NACL mentioned = missing outbound ephemeral port rule.

Memory rule: NACL stateless = request AND response both need rules. Don't forget ephemeral ports.

7. Forgetting Ephemeral Port Requirements

Wrong: "I only need to allow port 443 inbound and outbound in the NACL." Correct: The client sends to port 443, but the server responds to the client's ephemeral port (1024–65535). The NACL outbound rule must allow this full range, not just port 443. Similarly, the client-side NACL must allow inbound on ephemeral ports.

Exam clue: "NACL allows the destination port but responses time out" = ephemeral ports not covered.

Memory rule: Request = known port. Response = ephemeral port (1024–65535). NACLs need both.

8. Confusing SG Scope with NACL Scope

Wrong: "The security group protects the entire subnet." Correct: A security group is associated with network interfaces (individual resources). A NACL is associated with a subnet (all traffic in/out of that subnet). Different resources in the same subnet can have different security groups.

Exam clue: "Subnet-level filtering" = NACL. "Instance-level filtering" = SG.

Memory rule: SG = per-resource. NACL = per-subnet.

9. Opening a Database SG to the Whole VPC or Internet

Wrong: "Allow MySQL 3306 from 10.0.0.0/16 so all app servers can connect." Correct: Use a security group reference (allow from sg-app-server) instead of the entire VPC CIDR. The VPC CIDR includes web servers, bastion hosts, and any other resource — far broader than necessary. A SG reference limits access to exactly the tagged resources.

Exam clue: "Least privilege for database access" = SG reference to the specific application tier SG.

Memory rule: Database SG source = app server SG ID, not a broad CIDR.

10. Confusing Default SG and Default NACL Behavior

Wrong: "The default SG and default NACL both allow all traffic." Correct: The default NACL allows all inbound and outbound traffic. The default security group allows all inbound only from itself (other resources with the same SG) and allows all outbound. They have different default rules.

Exam clue: "New instance can reach the internet but other instances can't reach it" = default SG only allows inbound from same SG.

Memory rule: Default NACL = open. Default SG = self-referencing inbound only.

11. Assuming a Permissive SG Overrides a Restrictive SG

Wrong: "I attached a restrictive SG, so I'll add an 'allow all' SG to override it." Correct: When multiple SGs are attached to a resource, all rules are aggregated as a union. The permissive SG expands what is allowed — it does not override the restrictive one. You now have all rules from both SGs active.

Exam clue: "More permissive SG was added but specific traffic is still allowed" = SGs aggregate, they don't override.

Memory rule: Multiple SGs = union of all rules. More SGs = more permissive (never more restrictive).

12. Ignoring IPv6 Rules

Wrong: "I allowed 0.0.0.0/0, so all traffic is permitted." Correct: 0.0.0.0/0 covers IPv4 only. If your VPC uses dual-stack (IPv4 + IPv6), you also need ::/0 rules. Forgetting IPv6 rules causes mysterious failures for IPv6-enabled clients.

Exam clue: "Some clients can connect but others cannot" + dual-stack VPC = missing IPv6 rules.

Memory rule: 0.0.0.0/0 = IPv4. ::/0 = IPv6. Dual-stack needs both.

13. Assuming a Timeout Proves SG/NACL Is Blocking

Wrong: "The connection times out, so the security group must be blocking it." Correct: Timeouts can also be caused by missing route table entries, IGW/NAT misconfiguration, DNS resolution failures, the target service being stopped, or VPC peering/endpoint issues. Check the entire path.

Exam clue: "Timeout" in a question = investigate SGs, NACLs, routes, and resource health.

Memory rule: Timeout ≠ SG problem. Check: SG → NACL → routes → service health.

14. Assuming a Higher NACL Rule Number Overrides a Lower One

Wrong: "I added rule 500 to deny traffic, which overrides rule 100 that allows it." Correct: NACL rules are evaluated in ascending order. Rule 100 (ALLOW) is evaluated before rule 500 (DENY). The allow takes effect and the deny is never reached. To override, the deny must have a lower number.

Exam clue: "DENY rule has a higher number than the matching ALLOW" = the deny is ineffective.

Memory rule: Lower rule number = evaluated first = wins for that traffic.

Scenario-Based Practice Questions

Practice Questions — Security Groups vs NACLs

Q1. A company hosts a web application on EC2 instances in a public subnet. The security group allows inbound HTTPS (port 443) from 0.0.0.0/0 and allows all outbound traffic. Users can access the site successfully. The network team then associates a custom NACL with the subnet. The custom NACL has one inbound rule allowing TCP 443 from 0.0.0.0/0 and one outbound rule allowing TCP 443 to 0.0.0.0/0. After this change, users report that the website no longer loads. What is the MOST likely cause?

  • A. The security group needs an explicit outbound rule for port 443 to match the NACL outbound rule.
  • B. The custom NACL is missing an outbound rule allowing traffic on ephemeral ports (1024–65535). The NACL is stateless and does not automatically allow response traffic.
  • C. The custom NACL needs an inbound rule allowing traffic on ephemeral ports (1024–65535) for the client's responses.
  • D. The security group's stateful tracking was disabled when the custom NACL was associated. The security group now needs an explicit outbound allow rule for ephemeral ports.

Correct Answer: B

NACLs are stateless — they do not track connections. The server's response goes back to the client on an ephemeral port (1024–65535), not on port 443. The NACL outbound rule only allows port 443, so the response is dropped at the subnet boundary. The fix is to add an outbound NACL rule allowing TCP on ports 1024–65535 to 0.0.0.0/0.

Why not the others?

  • A is wrong because security groups are stateful. The SG automatically allows the response to an inbound connection — no explicit outbound rule is needed for tracked responses.
  • C has the direction wrong. The inbound NACL rule needs to allow the client's request on port 443 (which it does). The outbound rule needs to allow the response on ephemeral ports.
  • D is wrong because associating a NACL does not disable security group connection tracking. SGs and NACLs are independent layers.

Key exam clue: "Custom NACL associated" + "site stops working" + "NACL only allows the service port" = missing ephemeral port outbound rule.

Takeaway: NACLs are stateless. Always include ephemeral port rules (1024–65535) in the return direction.

Q2. A security team has detected malicious traffic from the IP range 203.0.113.0/24 targeting a public-facing web application. The web server's security group allows inbound HTTPS from 0.0.0.0/0. The team needs to immediately block all traffic from this IP range while continuing to serve all other users. What is the MOST effective approach?

  • A. Remove the 0.0.0.0/0 inbound HTTPS rule from the security group and add individual allow rules for every legitimate IP range except 203.0.113.0/24.
  • B. Add an explicit deny rule in the security group for inbound traffic from 203.0.113.0/24.
  • C. Add a NACL inbound DENY rule for 203.0.113.0/24 with a rule number lower than any existing ALLOW rule that matches the same traffic.
  • D. Add a NACL inbound DENY rule for 203.0.113.0/24 with rule number 999 to ensure it is evaluated after all other rules.

Correct Answer: C

Security groups do not support deny rules, so the NACL is the correct tool. The NACL DENY rule must have a lower rule number than any ALLOW rule that would match the same traffic (e.g., an ALLOW for 0.0.0.0/0 on port 443). This ensures the DENY is evaluated first and blocks the malicious range before the ALLOW is reached.

Why not the others?

  • A is impractical. Listing every legitimate IP range individually is unmanageable for a public-facing web application with thousands of users from diverse locations.
  • B is wrong because security groups do not support explicit deny rules. They only support allow rules.
  • D is wrong because NACL rules are evaluated in ascending order. Rule 999 would be evaluated after a lower-numbered ALLOW rule (e.g., rule 100 ALLOW 443 from 0.0.0.0/0), so the DENY would never be reached for HTTPS traffic.

Key exam clue: "Block a specific IP" + "still allow all other traffic" = NACL DENY rule with a low rule number.

Takeaway: Use NACLs for explicit deny rules. Always ensure the DENY rule number is lower than any ALLOW that would match the same traffic.

Q3. A solutions architect is designing a three-tier application with a web tier in a public subnet, an application tier in a private subnet, and an RDS MySQL database in a separate private subnet. The architect needs to ensure that only the application tier can connect to the database on port 3306, and the web tier can communicate with the application tier on port 8443. Which security group configuration follows the principle of least privilege?

  • A. Database SG: allow inbound 3306 from the VPC CIDR (10.0.0.0/16). App SG: allow inbound 8443 from the VPC CIDR. Web SG: allow inbound 443 from 0.0.0.0/0.
  • B. Database SG: allow inbound 3306 from the app subnet CIDR (10.0.2.0/24). App SG: allow inbound 8443 from the web subnet CIDR (10.0.1.0/24). Web SG: allow inbound 443 from 0.0.0.0/0.
  • C. Database SG: allow inbound 3306 from the app server security group ID. App SG: allow inbound 8443 from the web server security group ID. Web SG: allow inbound 443 from 0.0.0.0/0.
  • D. All three tiers share a single security group that allows inbound on ports 443, 8443, and 3306 from 0.0.0.0/0.

Correct Answer: C

Security group references are the most precise way to restrict tier-to-tier communication. The database SG allows port 3306 only from resources tagged with the app server SG — not the entire VPC CIDR, not the entire subnet, and certainly not the internet. This scales automatically: new app servers with the correct SG get access immediately, and no other resources in the VPC can reach the database.

Why not the others?

  • A uses the entire VPC CIDR (10.0.0.0/16) as the source, which means every resource in the VPC — including web servers, bastion hosts, and test instances — can connect to the database. This violates least privilege.
  • B is better than A (subnet CIDR is narrower than VPC CIDR) but still allows any resource in the app subnet to connect to the database, not just the application servers. If a monitoring tool or a developer's test instance is in the same subnet, it also gets database access.
  • D shares a single security group across all tiers and opens all ports to the internet, completely defeating the purpose of a multi-tier architecture. This is a critical security vulnerability.

Key exam clue: "Least privilege" + "tier-to-tier communication" = security group references (SG IDs), not CIDR blocks.

Takeaway: Reference security group IDs instead of CIDR blocks for tier-to-tier rules. This provides the tightest access control and scales with Auto Scaling groups.
